第 7 课 · AI Agent 2.0 实战

Agent 评测

从「我觉得它能用」到「我有数据证明它好用」· 约 16 分钟

为什么这一课很重要

前 6 课你做出了一个能跑的 Agent。但当你拿给别人用、或者想把它做成产品时，会遇到一连串回答不了的问题：

  • 「换了个系统提示，Agent 是变好了还是变差了？」
  • 「gpt-4o-mini 够用，还是该上 gpt-4o？多花 10 倍钱值得吗？」
  • 「用户反馈 Agent 答错了，是哪一步错的？工具选错？参数错？还是最终回答错？」
  • 「我加了第 3 个工具，会不会让前两个工具的选择准确率下降？」

这些问题靠「跑几次凭感觉」答不了。评测（evals）就是给你一套结构化的方法，用数据回答这些问题。这是 Agent 工程和「调 prompt 玄学」的分水岭。

一句话：评测就是给 Agent 一组固定输入，用预先定义的标准给输出打分。和你小时候做的标准化考试是一回事--题目一样、评分规则一样、可以横向比较。

评测什么？先分清三层

Agent 的输出分三层，每层评测方式不同：

层评什么怎么评本课对应
工具选择 LLM 选对工具了吗？参数对吗？ 精确匹配（有标准答案） 简单、必做
最终回答 给用户的回复正确吗？完整吗？ LLM 当裁判（无标准答案时） 主流做法
过程质量 路径合理吗？有没有多余调用？ 启发式 + 人工抽检 进阶，先了解

本课重点做前两层--它们覆盖了 80% 的实际需求。

第一层：工具选择评测（精确匹配）

这一层最好做--因为有标准答案。你准备一组输入，预先标注「期望调用的工具名和参数」，然后跑 Agent，看实际调用和期望是否一致。 

# evals_tool.py
from agent import WeatherAgent, SYSTEM_PROMPT, get_weather, calculate
import json

# --- 测试用例：每个用例 = (输入, 期望的工具调用列表) ---
TEST_CASES = [
    {
        "input": "北京今天天气怎么样？",
        "expected_tools": [{"name": "get_weather", "city": "北京"}],
    },
    {
        "input": "北京和上海温差多少？",
        "expected_tools": [
            {"name": "get_weather", "city": "北京"},
            {"name": "get_weather", "city": "上海"},
            # 是否调 calculate 由 LLM 决定，这里不强校验
        ],
    },
    {
        "input": "今天星期几？",  # 和天气无关
        "expected_tools": [],  # 期望不调任何工具
    },
    {
        "input": "计算 123 乘以 456",
        "expected_tools": [{"name": "calculate", "expression": "123*456"}],
    },
]

# --- 改造 Agent，让它把工具调用轨迹暴露出来 ---
def run_agent_and_get_trace(input_text: str) -> list[dict]:
    """跑一遍 Agent，返回这一轮的工具调用轨迹"""
    agent = WeatherAgent(system_prompt=SYSTEM_PROMPT, memory_file="eval_tmp.json")
    agent.register_tool(
        name="get_weather", description="查询某个城市的实时天气",
        params={"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]},
        fn=get_weather,
    )
    agent.register_tool(
        name="calculate", description="计算数学表达式",
        params={"type": "object", "properties": {"expression": {"type": "string"}}, "required": ["expression"]},
        fn=calculate,
    )

    before = len(agent.messages)
    agent.chat(input_text)
    new_msgs = agent.messages[before:]

    trace = []
    for m in new_msgs:
        if m.get("role") == "assistant" and m.get("tool_calls"):
            for call in m["tool_calls"]:
                trace.append({
                    "name": call["function"]["name"],
                    "args": json.loads(call["function"]["arguments"]),
                })
    return trace

# --- 评分函数 ---
def score_tool_selection(expected: list[dict], actual: list[dict]) -> dict:
    """对比期望和实际的工具调用，返回得分和细节"""
    expected_names = [t["name"] for t in expected]
    actual_names = [t["name"] for t in actual]

    # 简化评分：工具名集合是否一致（不要求顺序，因为 LLM 调用顺序可能变）
    names_match = set(expected_names) == set(actual_names)

    # 参数是否匹配（只检查期望里明确指定的字段）
    args_match = True
    for exp in expected:
        for act in actual:
            if act["name"] == exp["name"]:
                for k, v in exp["args"].items():
                    if k in act["args"] and act["args"][k] != v:
                        args_match = False

    return {
        "pass": names_match and args_match,
        "names_match": names_match,
        "args_match": args_match,
        "expected": expected,
        "actual": actual,
    }

# --- 跑评测 ---
def run_evals():
    results = []
    for tc in TEST_CASES:
        trace = run_agent_and_get_trace(tc["input"])
        score = score_tool_selection(tc["expected_tools"], trace)
        results.append({
            "input": tc["input"],
            "pass": score["pass"],
            "detail": score,
        })

    # 汇总
    passed = sum(1 for r in results if r["pass"])
    total = len(results)
    print(f"\n工具选择准确率：{passed}/{total} = {passed/total*100:.0f}%\n")
    for r in results:
        status = "✓" if r["pass"] else "✗"
        print(f"{status} {r['input']}")
        if not r["pass"]:
            print(f"    期望: {r['detail']['expected']}")
            print(f"    实际: {r['detail']['actual']}")

if __name__ == "__main__":
    run_evals()

看--你立刻发现了一个问题：问「今天星期几」时，LLM 错误地调了 get_weather。这不是凭感觉能发现的，是评测帮你抓出来的。

第二层：最终回答评测（LLM 当裁判）

工具选择有标准答案，但最终回答没有。「北京今天晴，25°C」和「北京今天晴朗，气温 25 度」都对，没法精确匹配。怎么办？

主流方案是用 LLM 当裁判（LLM-as-a-Judge）：让另一个 LLM 看着问题和回答，按你定的标准打分。听起来玄，其实是工业界标准做法--OpenAI、Anthropic 内部评测都这么干。 

# evals_answer.py
from openai import OpenAI
import json

client = OpenAI()

# --- 评测用例：输入 + 评判标准（rubric） ---
ANSWER_TEST_CASES = [
    {
        "input": "北京今天天气怎么样？",
        "rubric": """
- 回答必须包含「晴」这个天气状况
- 回答必须包含温度数值（25°C 或 25 度都算对）
- 回答必须用中文
- 不超过两句话
""",
    },
    {
        "input": "北京和上海温差多少？",
        "rubric": """
- 必须给出温差数值（3°C 或 3 度都算对）
- 必须基于真实天气数据（25 和 28），不能编造
- 回答用中文，不超过两句话
""",
    },
    {
        "input": "推荐我今天穿什么？我在北京。",
        "rubric": """
- 必须基于查询到的北京天气（晴，25°C）给建议
- 建议要和天气匹配（25°C 晴天不该推荐穿羽绒服）
- 回答用中文
""",
    },
]

# --- LLM 裁判 prompt ---
JUDGE_PROMPT = """你是一个严格的评分员。请根据以下标准给 Agent 的回答打分。

评分标准：
{rubric}

用户问题：{input}
Agent 回答：{answer}

请按以下 JSON 格式返回（只返回 JSON，不要其他文字）：
{{
  "pass": true 或 false,
  "score": 1 到 5 的整数,
  "reason": "一句话说明为什么这个分"
}}"""

def judge_answer(input_text: str, answer: str, rubric: str) -> dict:
    """用 LLM 当裁判，给 Agent 的回答打分"""
    resp = client.chat.completions.create(
        model="gpt-4o-mini",  # 裁判用便宜模型就行
        messages=[{
            "role": "user",
            "content": JUDGE_PROMPT.format(
                rubric=rubric, input=input_text, answer=answer
            )
        }],
        response_format={"type": "json_object"},  # 强制返回 JSON
    )
    return json.loads(resp.choices[0].message.content)

# --- 跑回答评测 ---
def run_answer_evals():
    from agent import WeatherAgent, SYSTEM_PROMPT, get_weather, calculate

    results = []
    for tc in ANSWER_TEST_CASES:
        # 跑 Agent 拿回答
        agent = WeatherAgent(system_prompt=SYSTEM_PROMPT, memory_file="eval_tmp.json")
        agent.register_tool("get_weather", "查询城市天气",
            {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}, get_weather)
        agent.register_tool("calculate", "计算数学表达式",
            {"type": "object", "properties": {"expression": {"type": "string"}}, "required": ["expression"]}, calculate)

        answer = agent.chat(tc["input"])

        # 让裁判打分
        judge_result = judge_answer(tc["input"], answer, tc["rubric"])
        results.append({
            "input": tc["input"],
            "answer": answer,
            "judge": judge_result,
        })

    # 汇总
    passed = sum(1 for r in results if r["judge"]["pass"])
    avg_score = sum(r["judge"]["score"] for r in results) / len(results)
    print(f"\n回答评测：{passed}/{len(results)} 通过，平均分 {avg_score:.1f}/5\n")
    for r in results:
        status = "✓" if r["judge"]["pass"] else "✗"
        print(f"{status} [{r['judge']['score']}/5] {r['input']}")
        print(f"    回答: {r['answer']}")
        print(f"    评语: {r['judge']['reason']}\n")

if __name__ == "__main__":
    run_answer_evals()

看，第 2 个用例被裁判扣分了--回答没错但不完美。这种细粒度反馈是凭感觉跑几次得不到的。

评测的三个原则

1. 固定输入，可重复。测试用例一旦定下，不要轻易改。这样每次改 prompt、换模型、加工具后跑同一套用例，得分变化才有意义。评测是 baseline，不是验收。

2. 分层评测，定位问题。工具选择层和回答层分开评。如果工具选择准确率掉到 60%，问题在 prompt 或工具描述；如果工具选对了但回答通过率低，问题在最终生成。不分层就只知道「变差了」，不知道「哪里变差了」。

3. LLM 裁判有偏差，但够用。LLM 当裁判不是完美方案--它可能对自己同类的回答更宽容、可能被回答的语气影响判断。但比起人工评测（慢、贵、主观），它快、便宜、可重复。生产级做法是：LLM 裁判做初筛 + 人工抽检 5-10% 校准。

动手实验

  1. 把工具选择评测跑通，记录基准准确率（比如 75%）。然后改 SYSTEM_PROMPT，加一句「与天气无关的问题不要调工具」，再跑一次，看准确率有没有提升。这是评测最直接的用法：用数据验证改动。
  2. 给回答评测加一个用例：「广州会下雨吗？」，rubric 写「必须查询广州天气，必须基于『雷阵雨』这个事实回答」。跑一下，看 Agent 能不能基于工具结果正确推断「会下雨」。
  3. 对比模型：把 WeatherAgent(model="gpt-4o-mini") 改成 model="gpt-4o"，跑同一套用例。比较准确率和平均分。多花 10 倍成本值不值？数据说话。（注意：gpt-4o 比 mini 贵很多，跑完记得切回来）
  4. 成本评测：在 agent.chat 里记录每次调用的 token 数（resp.usage.total_tokens），跑完一套用例汇总总 token 和估算成本。这是产品化必备指标。

一个容易忽略的陷阱：评测用例污染

如果你把评测用例直接放进系统提示或 few-shot 示例，Agent 会在评测里表现很好，但真实场景下一样烂。这叫数据泄漏--评测用例必须是 Agent 没见过的。

规则：

  • 评测用例不要出现在 system prompt 里
  • 评测用例不要作为 few-shot 示例喂给 Agent
  • 真实用户提问和评测用例分开维护，避免 LLM 见过评测题

小测验

检查你的理解

你改了系统提示后跑评测，发现工具选择准确率从 75% 升到 90%，但回答评测平均分从 4.3 掉到 3.8。这说明什么？

  • 整体变好了，准确率提升更重要
  • 整体变差了，平均分下降更关键
  • 工具选择变好了，但最终回答质量下降--可能是新提示让 LLM 选对工具但生成回答时受影响。需要看具体用例定位问题
  • 评测系统坏了，结果不可信

应用一下

你发现评测结果和真实用户反馈对不上--评测 95% 通过，但用户总抱怨答不好。最可能的原因是？

  • 评测系统写错了，代码有 bug
  • 评测用例不代表真实用户问题--你出的题太简单、太规整，真实用户问的五花八门。需要扩充用例覆盖真实分布
  • LLM 裁判太宽松，应该换更强的模型
  • 用户在骗你
