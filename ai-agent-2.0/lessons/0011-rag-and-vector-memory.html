RAG 与向量记忆

让 Agent 查海量知识，而不只是记对话 · 约 18 分钟

前 10 课的记忆有什么局限？

到目前为止，你的 Agent 只有一种记忆：messages 列表。它存的是对话流水账--你说一句、它答一句、工具调用的结果。这种记忆在两类场景下会撞墙：

  1. 知识太多：你想让 Agent 能回答「公司 HR 政策」「产品文档」「去年的客户邮件」--这些加起来可能几十万字，全塞进 messages 既贵又超 token 上限。
  2. 对话太长：第 4 课的滑动窗口会丢老消息，摘要压缩也丢细节。用户 50 轮前说过的关键事实，第 51 轮可能就找不到了。

这两个问题的共同点是：你需要的信息存在，但 LLM 看不到。RAG（Retrieval-Augmented Generation，检索增强生成）就是解法--不把所有东西塞给 LLM，而是先检索出和当前问题最相关的几段，只把这些喂给 LLM。

类比：你写开卷考试，不会把整本教材带进去翻--太大、太慢。你会先查目录、找到相关章节、只读那几页再答题。RAG 就是给 LLM 配一个「能查目录的图书管理员」。

RAG 的三步

所有 RAG 系统都做三件事：

  1. 切分（Chunking）：把长文档切成小段（几百字一段），方便检索
  2. 向量化（Embedding）：把每段文本转成一个数字向量，语义相近的文本向量也相近
  3. 检索（Retrieval）：用户提问时，把问题也向量化，找出向量最相近的几段，塞进 LLM 上下文

下面逐步实现。

第一步：Embedding 是什么？

Embedding 是把一段文本映射成一组数字（比如 1536 个浮点数）。关键性质：语义相近的文本，向量也相近。 

# 用 OpenAI 的 embedding 模型
from openai import OpenAI
client = OpenAI()

resp = client.embeddings.create(
    model="text-embedding-3-small",
    input="今天北京天气晴朗"
)
vector = resp.data[0].embedding  # 长度 1536 的浮点数列表
# [0.0123, -0.0456, 0.0789, ...]

# 语义相近的文本，向量距离近
import math
def cosine_similarity(v1, v2):
    """两个向量的余弦相似度，越接近 1 越相似"""
    dot = sum(a * b for a, b in zip(v1, v2))
    norm1 = math.sqrt(sum(a*a for a in v1))
    norm2 = math.sqrt(sum(b*b for b in v2))
    return dot / (norm1 * norm2)

v1 = client.embeddings.create(model="text-embedding-3-small", input="今天北京天气晴朗").data[0].embedding
v2 = client.embeddings.create(model="text-embedding-3-small", input="北京今日晴").data[0].embedding
v3 = client.embeddings.create(model="text-embedding-3-small", input="我想吃火锅").data[0].embedding

print(cosine_similarity(v1, v2))  # ~0.85 高相似
print(cosine_similarity(v1, v3))  # ~0.3 低相似

这个性质是 RAG 的基础--用向量距离判断「这段文本和用户问题相不相关」。

第二步：切分文档

假设你有一份产品文档，要让 Agent 能回答相关问题。先切成小段： 

# chunking.py
def chunk_text(text: str, chunk_size: int = 500, overlap: int = 50) -> list[str]:
    """把长文本切成有重叠的小段。
    
    chunk_size: 每段字符数。500 字左右适合中文。
    overlap: 相邻段重叠多少字符。避免把完整句子切断。
    """
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunk = text[start:end]
        chunks.append(chunk)
        start = end - overlap  # 往后退一点，下一段和这段有重叠
    return chunks

# 示例
doc = """
产品名称：智询天气
版本：2.3.0
发布日期：2026-07-01

## 功能概述
智询天气是一个基于 AI 的天气助手，支持查询全球城市的实时天气、未来 7 天预报、空气质量。

## 定价
- 免费版：每天 50 次查询
- 专业版：每月 19 元，无限查询，支持历史数据
- 企业版：按 API 调用量计费，联系销售

## 退款政策
购买后 7 天内无理由退款。需要提供订单号，退款将在 3-5 个工作日到账。

## 常见问题
Q: 支持哪些城市？
A: 全球 10 万+ 城市，包括所有省会和地级市。

Q: 数据来源是什么？
A: 我们聚合了多家气象服务，包括国家气象局、Weather API 等。
"""

chunks = chunk_text(doc)
print(f"切成 {len(chunks)} 段")
for i, c in enumerate(chunks):
    print(f"-- 段 {i} --\n{c[:80]}...\n")

切分有两个要点：

  • chunk_size：太小会丢上下文，太大会检索不准。中文 300-800 字是常见范围。
  • overlap：相邻段重叠 50-100 字，避免把关键句子正好切断。

第三步：向量化并存进向量库

我们用 Chroma，一个轻量的本地向量数据库。pip install chromadb 就能跑，无需服务器。 

# vector_store.py
import chromadb

client = chromadb.PersistentClient(path="./vector_db")  # 数据存磁盘
collection = client.get_or_create_collection(name="product_docs")

from openai import OpenAI
oa_client = OpenAI()

def embed_and_store(chunks: list[str], source: str = "doc"):
    """把文本段向量化后存进 Chroma"""
    # 批量生成 embedding
    embeddings = []
    for chunk in chunks:
        resp = oa_client.embeddings.create(
            model="text-embedding-3-small",
            input=chunk
        )
        embeddings.append(resp.data[0].embedding)

    # 存进 Chroma
    collection.add(
        ids=[f"{source}_{i}" for i in range(len(chunks))],
        documents=chunks,
        embeddings=embeddings,
        metadatas=[{"source": source, "chunk_index": i} for i in range(len(chunks))]
    )

# 把刚才切的段存进去
embed_and_store(chunks, source="product_doc")

第四步：检索

用户提问时，把问题向量化，找最相似的几段：

def retrieve(query: str, n_results: int = 3) -> list[dict]:
    """检索和 query 最相关的 n 段文本"""
    # 问题向量化
    query_resp = oa_client.embeddings.create(
        model="text-embedding-3-small",
        input=query
    )
    query_vector = query_resp.data[0].embedding

    # 在 Chroma 里找最相似的
    results = collection.query(
        query_embeddings=[query_vector],
        n_results=n_results
    )

    return [
        {
            "text": doc,
            "source": meta["source"],
            "distance": dist
        }
        for doc, meta, dist in zip(
            results["documents"][0],
            results["metadatas"][0],
            results["distances"][0]
        )
    ]

# 测试
for r in retrieve("退款政策是什么？"):
    print(f"[相似度 {1-r['distance']:.2f}] {r['text'][:80]}...")

输出：

[相似度 0.78] 产品名称：智询天气...
[相似度 0.74] ## 退款政策
购买后 7 天内无理由退款。需要提供订单号...
[相似度 0.71] ## 定价
- 免费版：每天 50 次查询...

看--它准确地把「退款政策」那一段排到了前面。这就是语义检索的威力：问题里没出现「退款」两个字（如果用户问的是「能退钱吗」），向量相似度也能找到相关段落。

把 RAG 接进 Agent

现在让 Agent 在回答前先检索。两种集成方式：

方式 A：作为工具（Agent 自己决定何时检索）

# 把检索做成一个工具，让 Agent 自己调
def search_docs(query: str) -> str:
    """检索产品文档，返回最相关的几段"""
    results = retrieve(query, n_results=3)
    if not results:
        return "没找到相关内容"
    return "\n---\n".join([r["text"] for r in results])

# 注册成工具
agent.register_tool(
    name="search_docs",
    description="当用户问产品功能、定价、退款、使用方法等问题时，检索产品文档获取答案",
    params={"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]},
    fn=search_docs,
)

方式 B：作为前置步骤（每次都先检索）

def chat_with_rag(user_input: str) -> str:
    """每次对话前先检索，把相关文档塞进 system 消息"""
    # 1. 检索
    results = retrieve(user_input, n_results=3)
    context = "\n---\n".join([r["text"] for r in results])

    # 2. 把检索结果作为上下文塞进 messages
    augmented_system = SYSTEM_PROMPT + f"\n\n参考以下文档回答（如果相关）：\n{context}"

    # 3. 正常调用 Agent
    messages = [
        {"role": "system", "content": augmented_system},
        {"role": "user", "content": user_input}
    ]
    # ... 调 LLM

两种方式的取舍：

维度方式 A（作为工具）方式 B（前置检索）
何时检索 LLM 决定（灵活但可能漏检） 每次都检索（保证有，但浪费）
实现复杂度 低（加个工具） 低（改 system 拼接）
成本 只在需要时检索 每次都调 embedding
适用场景 通用 Agent，问题类型多样 固定领域的问答（如客服）

Agent 工程的常见误区：上来就 RAG。很多人听到 RAG 就兴奋，所有问题都套。但 RAG 有成本（embedding 调用、向量库维护）、有误差（检索不准会误导 LLM）、有复杂度。先想清楚：你的场景真的需要检索外部知识吗？如果信息量小、能直接塞进 system prompt，就别上 RAG。

用 RAG 替代对话历史摘要

除了检索外部文档，RAG 还能解决第 4 课遗留的问题：对话历史太长怎么压缩。思路：把每轮对话存进向量库，下次提问时只检索相关的几轮，不喂完整历史。 

# 每轮对话后存进向量库
def save_turn_to_vector_store(user_input: str, reply: str):
    """把一轮对话作为一段文本存进向量库"""
    text = f"用户: {user_input}\n助手: {reply}"
    embed_and_store([text], source="conversation")

# 下次提问时检索相关历史
def get_relevant_history(query: str, n: int = 5) -> list[str]:
    """检索和当前问题最相关的 n 轮历史对话"""
    results = retrieve(query, n_results=n)
    return [r["text"] for r in results if r["source"] == "conversation"]

# chat 时用检索到的历史替代完整历史
def chat_with_vector_memory(user_input: str) -> str:
    relevant = get_relevant_history(user_input, n=5)
    context = "\n---\n".join(relevant)
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT + f"\n\n相关历史：\n{context}"},
        {"role": "user", "content": user_input}
    ]
    # ... 调 LLM，存这一轮到向量库

这是「长期记忆-知识型」的实现方式：不再保留完整对话流水，而是按语义检索相关片段。适合超长对话（几百轮）的场景。

RAG 的常见坑

坑 1：检索不准，LLM 被误导

如果检索回来的内容其实不相关，LLM 还是会基于它回答--产生「看似合理但错误」的答案。这是 RAG 最常见的问题。

缓解方式：

  • 调相似度阈值：距离太大的结果直接丢弃，返回「没找到相关内容」
  • 让 LLM 自己判断：在 prompt 里加「如果检索内容不相关，就忽略它，基于自己知识回答」
  • rerank：先用向量检索粗筛 10 条，再用一个小模型对这 10 条按相关度精排，取前 3 条

坑 2：切分不当丢上下文

如果一段关键信息正好被切到两段里（比如「退款需要订单号」和「7 天内可退」），检索可能只命中一段，LLM 拿到不完整信息。

缓解：overlap 重叠、按段落/标题切分（而非纯按字符数）、chunk_size 设大一点。

坑 3：embedding 过期

文档更新了，但向量库里还是旧的。用户问「现在定价多少」，检索到的是老价格。

缓解：建立更新流程，文档改了就重新切分、重新 embedding、覆盖旧数据。

动手实验

  1. 把一份你自己的文档（产品说明、个人笔记、公司 wiki 导出）切分、向量化、存进 Chroma。然后写几个问题测试检索效果，看相似度排序合不合理。
  2. 把 RAG 作为工具接进 Agent（方式 A）。问「智询天气能退款吗？」「专业版多少钱？」，观察 Agent 会不会主动调 search_docs。
  3. 对比 RAG vs 直接塞进 system：如果文档只有 2000 字，直接塞进 system prompt 也能用。对比两种方式在准确率、延迟、成本上的差异。你会理解为什么小文档不该上 RAG。
  4. （进阶）用 rerank 提升准确率：用 cohere 的 rerank API，或用 LLM 自己对 10 条候选精排。对比前后准确率。

小测验

检查你的理解

RAG 的核心思路是？

  • 把所有知识都塞进 LLM 的 system prompt
  • 把文档切成小段向量化存进向量库，用户提问时检索最相关的几段塞进 LLM 上下文，让 LLM 基于这些片段回答
  • 训练一个专门的模型来记忆所有知识
  • 让 LLM 自己上网搜索

应用一下

你给 Agent 接了 RAG，但用户反馈「经常答错，而且答得很自信」。最可能的原因和解决？

  • LLM 太笨，换更大的模型
  • RAG 不靠谱，去掉就行
  • 检索准确率低--检索回来的内容其实不相关，但 LLM 还是基于它编造答案。需要调相似度阈值、改切分策略、加 rerank，并在 prompt 里告诉 LLM「不相关就忽略」
  • 向量库坏了，重启
