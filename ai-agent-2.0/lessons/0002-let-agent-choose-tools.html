让 Agent 自己选工具

从一把锤子到工具箱 · 约 10 分钟

上节回顾

第 1 课 我们写了一个只会一件事的 Agent：查天气。它已经具备 Agent 的三要素（LLM + 工具 + 循环），但只有一个工具，所以 LLM 没什么可"选"的——每次都得调 get_weather。

这一课我们再加一个工具——计算器。然后你会亲眼看到一件让很多人第一次「啊原来 Agent 是这么回事」的事：LLM 在两个工具之间自己挑，有时候甚至选择不用工具。

加一个工具有几步？

就两步：

  1. 写一个 Python 函数（和平时写函数一模一样）
  2. 给它写一份"说明书"，加到 tools 列表里

我们来加一个 calculate 工具：

# 工具 2：算术计算
def calculate(expression: str) -> str:
    """安全地计算一个数学表达式，如 '28 - 25' 或 '(25+28+31)/3'"""
    # 只允许数字和基本运算符，防止注入
    allowed = set("0123456789+-*/.() ")
    if not all(c in allowed for c in expression):
        return "错误：只支持数字和 + - * /"
    try:
        return str(eval(expression))  # 教学示例，生产环境别用 eval
    except Exception as e:
        return f"错误：{e}"

然后是它的说明书。注意 description 这一行——这是整堂课最关键的地方，下面会专门讲：

{
    "type": "function",
    "function": {
        "name": "calculate",
        "description": "计算一个数学表达式，如 '28 - 25' 或 '(25+28+31)/3'。当需要精确数值计算时使用。",
        "parameters": {
            "type": "object",
            "properties": {"expression": {"type": "string"}},
            "required": ["expression"]
        }
    }
}

完整代码

在上一课基础上改两处：① tools 列表多一项；② 用一个 tool_map 把函数名映射到函数，循环里就不用写一堆 if 了。

from openai import OpenAI
import json

client = OpenAI()

# --- 工具定义 ---
def get_weather(city: str) -> str:
    weather = {"北京": "晴，25°C", "上海": "多云，28°C", "广州": "雷阵雨，31°C"}
    return weather.get(city, "未知")

def calculate(expression: str) -> str:
    allowed = set("0123456789+-*/.() ")
    if not all(c in allowed for c in expression):
        return "错误：只支持数字和 + - * /"
    try:
        return str(eval(expression))
    except Exception as e:
        return f"错误：{e}"

# --- 工具说明书（给 LLM 看的） ---
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询某个城市的实时天气，返回形如 '晴，25°C' 的字符串",
            "parameters": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "calculate",
            "description": "计算一个数学表达式，如 '28 - 25' 或 '(25+28+31)/3'。当需要精确数值计算时使用。",
            "parameters": {
                "type": "object",
                "properties": {"expression": {"type": "string"}},
                "required": ["expression"]
            }
        }
    }
]

# --- 函数名 → 函数 的映射，循环里好调度 ---
tool_map = {
    "get_weather": get_weather,
    "calculate": calculate,
}

# --- Agent 循环 ---
messages = [{"role": "user", "content": "北京、上海、广州今天的平均温度是多少？"}]

while True:
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=messages,
        tools=tools,
    )
    msg = resp.choices[0].message
    messages.append(msg)

    if not msg.tool_calls:
        print("\n【最终回答】", msg.content)
        break

    for call in msg.tool_calls:
        args = json.loads(call.function.arguments)
        result = tool_map[call.function.name](**args)
        print(f"→ {call.function.name}({args}) = {result}")  # 打印调度轨迹
        messages.append({
            "role": "tool",
            "tool_call_id": call.id,
            "content": result
        })

跑一下，看 Agent 在干什么

运行 python agent.py，你会看到类似这样的输出（具体行数和顺序由 LLM 决定，可能略有不同）：

→ get_weather({'city': '北京'}) = 晴，25°C
→ get_weather({'city': '上海'}) = 多云，28°C
→ get_weather({'city': '广州'}) = 雷阵雨，31°C
→ calculate({'expression': '(25+28+31)/3'}) = 28.0

【最终回答】 北京、上海、广州今天的平均温度约为 28.0°C。

看着这四行调度轨迹，停一秒钟体会一下发生了什么：LLM 自己规划了路径——「先查三个城市，再做平均」。这段路径不是你写死的，是你给它工具和问题之后，它自己想出来的。

这就是 Agent 的"啊哈时刻"。 第 1 课我们用文字定义了 Agent，这一课你第一次看见它。注意那行 calculate({'expression': '(25+28+31)/3'})——LLM 自己决定把三个数字塞进一个表达式，然后调你给的计算器。你没有在代码里任何地方写过「先查三个城市再算平均」。

关键观察：LLM 会偷懒

多跑几次，或者把问题换成「北京比上海低几度？」，你可能会看到不同的轨迹： 

→ get_weather({'city': '北京'}) = 晴，25°C
→ get_weather({'city': '上海'}) = 多云，28°C

【最终回答】 北京比上海低 3°C。

注意——这次 LLM 没有调 calculate，它自己心算 28 - 25 = 3 直接答了。这不是 bug，这是正确行为。

洞察： 工具不是越多越好，LLM 会自己判断什么时候需要工具。简单的减法它能心算，就不调计算器；如果是「(25+28+31)/3」这种它不太信任自己心算的，它才会调 calculate 拿一个确定结果。

这引出 Agent 工程的一条重要原则——给工具，不是逼工具。你提供能力，LLM 决定用不用。强迫 LLM 每次都调某个工具（比如在系统提示里写"必须先调 calculate"），通常会让它变慢、变贵、还容易出错。

为什么 description 这么重要？

LLM 选工具时，它看不到你的函数实现，只能看到三样东西：

  1. 函数名（name）
  2. 说明文字（description）
  3. 参数结构（parameters 的 JSON Schema）

这就意味着——description 是写给 LLM 看的接口文档。写得烂，LLM 就会用错工具、用错参数、或者干脆不用。

写法结果
"description": "计算" 太模糊。LLM 不知道能算什么、参数长什么样，大概率不会用它。
"description": "计算一个数学表达式，如 '28 - 25' 或 '(25+28+31)/3'。当需要精确数值计算时使用。" 有例子、有适用场景。LLM 能判断"现在该不该调它"。
"description": "本工具接收任意 Python 表达式并返回结果。" 危险。LLM 可能会塞 __import__('os').system('rm -rf /') 进来。

写 description 的口诀：说清楚它能干什么、什么时候该用、给一两个例子。把它当成给一个聪明但不了解你代码库的新同事写接口文档。

动手实验

把代码跑起来后，依次试这几个问题，观察调度轨迹的不同：

  1. "北京和上海今天温差多少？" —— LLM 会调 calculate 吗？
  2. "北京、上海、广州三座城市温度的方差是多少？" —— 这次它大概率会调 calculate。
  3. "今天该穿什么衣服？我在北京。" —— 看它会不会主动查天气（这是个判断题：任务里没明说"查天气"，但隐含需要）。

第 3 个问题特别有意思。如果 LLM 没主动查天气，你可以在系统提示里加一句引导（下一课会讲系统提示的设计）。先把现象记下来。

小测验

检查你的理解

你给 Agent 加了一个 search_web 工具，但 LLM 从来不调它，哪怕问它"最新新闻"也自己编。最可能的原因是？

  • LLM 太笨，需要换更大的模型
  • description 写得不清楚，LLM 不知道这个工具该在什么时候用，或者不知道它存在
  • tools 列表里工具太多，LLM 选不过来
  • Python 函数没有 type hint

应用一下

你希望 Agent 帮用户管理待办事项。下面哪个工具集最合理？

  • 一个大工具 do_everything(action, params)，所有操作都走它
  • 100 个细粒度工具，每个数据库操作（增删改查）都单独一个
  • 几个语义清晰的工具：add_todo、list_todos、complete_todo、delete_todo
  • 只给一个 query_database(sql) 工具，让 LLM 自己写 SQL
