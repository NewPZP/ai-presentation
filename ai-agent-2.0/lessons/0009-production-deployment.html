生产化部署

从「本地能跑」到「真上线给人用」· 约 18 分钟

前 8 课的代码离上线还差什么？

你的 Agent 已经能做很多事：查天气、算数、流式回答、有记忆、能评测。但它还有几个「玩具特征」让它没法真上线：

问题现状本课目标
记忆存储 内存 dict + JSON 文件 Redis（跨进程、可扩展、带过期）
认证 谁都能调 API Key 中间件
限流 无 按 user_id 限速，防滥用
部署 本地 uvicorn Docker 容器，可上任何云
配置 硬编码在代码里 环境变量分离

这一课逐项解决，最后用一个 Dockerfile 把整个服务打包成可部署的镜像。

第一项：用 Redis 替代内存 dict + JSON

为什么要换？

前几课的 agents: dict + memory_*.json 有三个硬伤：

  1. 多进程不共享：生产环境通常跑多个 worker（Gunicorn 起多个进程），每个进程的 dict 是独立的--用户 A 的请求被进程 1 处理，下一次被进程 2 处理，进程 2 没有 A 的 Agent 实例。
  2. 内存无限增长：用户多了 dict 会 OOM。JSON 文件也会越堆越多，磁盘爆掉。
  3. 文件 I/O 慢：每次读写 memory_*.json 都要打开文件、解析 JSON。高并发下是瓶颈。

Redis 是标准解法：内存数据库、跨进程共享、原生支持过期（TTL）、读写极快。把 messages 存成 Redis 里的一个 list，按 user_id 做 key。

实现

# memory.py - 抽象出记忆层，方便后续换实现
import json
import redis

class RedisMemory:
    """用 Redis 存 messages，按 user_id 隔离"""

    def __init__(self, redis_url: str = "redis://localhost:6379", ttl: int = 86400 * 7):
        """
        ttl: 记忆保留 7 天，过期自动清理。避免老用户数据永远占空间。
        生产环境可以根据用户活跃度动态调整。
        """
        self.client = redis.from_url(redis_url, decode_responses=True)
        self.ttl = ttl

    def _key(self, user_id: str) -> str:
        return f"agent:messages:{user_id}"

    def load(self, user_id: str) -> list[dict]:
        """读用户的 messages。没有就返回空列表。"""
        data = self.client.get(self._key(user_id))
        if data:
            return json.loads(data)
        return []

    def save(self, user_id: str, messages: list[dict]):
        """存 messages，刷新 TTL"""
        self.client.set(
            self._key(user_id),
            json.dumps(messages, ensure_ascii=False),
            ex=self.ttl,
        )

    def clear(self, user_id: str):
        """手动清除某用户的记忆（调试或 GDPR 删除请求时用）"""
        self.client.delete(self._key(user_id))

然后改造 WeatherAgent，把 _load_messages / _save_messages 换成调 RedisMemory：

class WeatherAgent:
    def __init__(self, user_id: str, memory: RedisMemory, ...):
        self.user_id = user_id
        self.memory = memory
        # ...
        self.messages = self._load_messages()

    def _load_messages(self) -> list:
        msgs = self.memory.load(self.user_id)
        if not msgs:
            msgs = [{"role": "system", "content": self.system_prompt}]
        return msgs

    def _save_messages(self):
        self.memory.save(self.user_id, self.messages)

注意关键变化：Agent 不再持有 memory_file，而是接受一个 RedisMemory 实例。user_id 从构造时传入。这样 Agent 实例变成无状态的--每次请求都可以新建一个，记忆全在 Redis 里。多进程、多机器都没问题。

这是工程化的核心思路：把状态外置。前 8 课的 Agent 是「有状态对象 + 状态在内存」；生产化是「无状态对象 + 状态在 Redis」。后者才是云原生时代的标准姿势。无状态 = 可水平扩展、可重启不丢数据、可灰度发布。

第二项：API Key 认证

没认证的服务上线就是灾难--有人写个脚本扫到你的 /chat 接口，一夜把你 API 余额刷光。最低限度的保护是API Key 认证。 

# auth.py
from fastapi import HTTPException, Security
from fastapi.security import APIKeyHeader

api_key_header = APIKeyHeader(name="X-API-Key")

# 真实项目从环境变量或数据库读，不要硬编码
import os
VALID_API_KEYS = os.environ.get("VALID_API_KEYS", "").split(",")

async def verify_api_key(api_key: str = Security(api_key_header)):
    if api_key not in VALID_API_KEYS:
        raise HTTPException(status_code=401, detail="Invalid API Key")
    return api_key

在端点上加依赖：

from fastapi import Depends

@app.post("/chat")
async def chat(req: ChatRequest, api_key: str = Depends(verify_api_key)):
    # ...

@app.post("/chat/stream")
async def chat_stream(req: ChatRequest, api_key: str = Depends(verify_api_key)):
    # ...

调用方必须在 header 里带 X-API-Key: xxx：

curl -X POST http://localhost:8000/chat \
  -H "X-API-Key: your-secret-key" \
  -H "Content-Type: application/json" \
  -d '{"user_id": "alice", "message": "北京天气"}'

没带 key 或 key 错，返回 401。FastAPI 的 /docs 页面右上角会出现「Authorize」按钮，输入 key 后所有请求自动带上。

进阶：JWT vs API Key

API Key 适合「服务对服务」或「给开发者用」。如果是面向终端用户的产品（用户登录后才能用），应该用 JWT（JSON Web Token）--用户登录后拿一个 token，每次请求带在 header 里，服务端验证 token 的签名和过期时间。FastAPI 生态有 python-jose 库，逻辑和上面类似，只是验证更复杂。

本课先做 API Key 版本，等做用户系统时再升级 JWT。

第三项：限流

即使有认证，一个付费用户也可能写脚本疯狂调你的接口，把你 LLM 余额耗光。限流是兜底保护。

最简单的做法：按 user_id 限速，比如每分钟最多 20 次请求：

# rate_limit.py
from fastapi import HTTPException
import time
import redis

class RateLimiter:
    """滑动窗口限流：按 user_id 限制每分钟请求数"""

    def __init__(self, redis_client, max_requests: int = 20, window: int = 60):
        self.redis = redis_client
        self.max_requests = max_requests
        self.window = window  # 秒

    async def check(self, user_id: str):
        key = f"rate:{user_id}"
        current = time.time()
        # 用 Redis 的 sorted set 实现滑动窗口
        # 移除窗口外的旧请求
        self.redis.zremrangebyscore(key, 0, current - self.window)
        # 看当前窗口内有多少请求
        count = self.redis.zcard(key)
        if count >= self.max_requests:
            raise HTTPException(
                status_code=429,
                detail=f"请求太频繁，每分钟最多 {self.max_requests} 次"
            )
        # 记录这次请求
        self.redis.zadd(key, {str(current): current})
        # 设置 key 过期，避免冷用户永久占内存
        self.redis.expire(key, self.window)

在端点上加这个检查：

@app.post("/chat")
async def chat(
    req: ChatRequest,
    api_key: str = Depends(verify_api_key),
    limiter: RateLimiter = Depends(get_limiter),
):
    await limiter.check(req.user_id)
    # ...

超过限制返回 429 状态码--这是 HTTP 标准的「Too Many Requests」。前端可以根据 429 显示「请求太频繁，请稍后再试」。

第四项：环境变量分离配置

生产代码不能把 API Key、Redis URL 这些硬编码进去。用 .env 文件 + pydantic-settings 管理： 

# .env（gitignore，绝不提交）
OPENAI_API_KEY=sk-xxx
REDIS_URL=redis://localhost:6379
VALID_API_KEYS=key1,key2,key3
LOG_LEVEL=info
MAX_TURNS=20
# config.py
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    openai_api_key: str
    redis_url: str = "redis://localhost:6379"
    valid_api_keys: str = ""
    log_level: str = "info"
    max_turns: int = 20

    class Config:
        env_file = ".env"

settings = Settings()

代码里用 settings.openai_api_key 访问，不再有硬编码。不同环境（开发/测试/生产）用不同 .env 文件。

第五项：Docker 打包

所有东西就位后，用 Docker 把整个服务打包成一个镜像，任何云都能跑：

# Dockerfile
FROM python:3.11-slim

WORKDIR /app

# 先装依赖（利用 Docker 层缓存）
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 再复制代码（代码变时不重装依赖）
COPY . .

# 暴露端口
EXPOSE 8000

# 生产用 gunicorn + uvicorn worker，多进程 + 异步
CMD ["gunicorn", "server:app", \
     "-w", "4", \
     "-k", "uvicorn.workers.UvicornWorker", \
     "-b", "0.0.0.0:8000"]
# requirements.txt
fastapi>=0.110
uvicorn[standard]>=0.27
gunicorn>=21
openai>=1.12
redis>=5.0
pydantic-settings>=2.1

配合 docker-compose.yml 把 Agent 和 Redis 一起跑：

# docker-compose.yml
version: "3.8"
services:
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    volumes:
      - redis-data:/data

  agent:
    build: .
    ports:
      - "8000:8000"
    env_file:
      - .env
    depends_on:
      - redis

volumes:
  redis-data:

一行命令启动整个服务：

docker-compose up -d
# redis 和 agent 都跑起来了，访问 http://localhost:8000

动手实验

  1. 本地跑 Redis：docker run -d -p 6379:6379 redis:7-alpine，然后改 Agent 用 RedisMemory。确认多用户、跨会话记忆还正常。
  2. 多进程测试：用 gunicorn server:app -w 4 -k uvicorn.workers.UvicornWorker 起 4 个 worker。用同一个 user_id 连续发请求，确认每次都能拿到完整历史--这验证了状态外置到 Redis 后多进程共享。
  3. 测认证和限流：不带 API Key 调 /chat，确认返回 401。带正确 Key 但一分钟内发 25 次请求，确认第 21 次开始返回 429。
  4. Docker 部署：docker-compose up -d，确认 http://localhost:8000/docs 能访问。然后试着 docker-compose down 再 up，确认 Redis 里的记忆还在（因为有 volume）。
  5. （进阶）部署到云：把镜像推到 Docker Hub 或阿里云容器镜像服务，然后在任意云服务器（阿里云 ECS、AWS EC2、Fly.io、Railway）上 docker-compose up。这是真正的「上线」。

小测验

检查你的理解

生产环境为什么必须把 Agent 的状态（messages）外置到 Redis，而不是放在内存 dict 里？

  • 内存 dict 有 bug，不能用
  • 生产通常多进程/多机器部署，进程间不共享内存；外置到 Redis 后任何进程都能访问同一份记忆，且进程重启不丢数据
  • Redis 比 Python dict 快
  • OpenAI API 要求必须用 Redis

应用一下

你的 Agent 服务上线后，用户反馈「每次重启服务我的对话历史就没了」。最可能的原因和解决方案？

  • LLM 记忆能力差，换更强的模型
  • 系统提示写错了，加一句「请记住历史」
  • messages 存在进程内存里，重启就丢。应该外置到 Redis（或数据库），进程无状态化
  • FastAPI 不支持持久化，换 Django
