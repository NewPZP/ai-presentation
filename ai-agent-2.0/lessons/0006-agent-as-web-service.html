第 6 课 · AI Agent 2.0 实战

把 Agent 变成 Web 服务

用 FastAPI 给 Agent 包一层 HTTP · 约 15 分钟

为什么要做这一步？

到目前为止，你的 Agent 只能通过命令行 input() 用——你自己跑可以，但别人没法用。创业产品、Side Project、给同事试用，都得让别人能通过网络调用你的 Agent。

这一课用 FastAPI 给上一课的 WeatherAgent 类包一层 HTTP 接口，让它变成一个别人能 curl 或者写前端调用的 Web 服务。这是从「我自己能跑」到「能给别人用」的最小一步，也是任何 Agent 产品的交付形态。

选 FastAPI 不选 Flask/Django 的理由：异步原生（LLM 调用是 I/O 密集型，异步能并发处理多用户）、类型提示自动生成文档（/docs 页面开箱即用）、对单文件服务足够轻量。LangChain 这类重型框架的"Agent as a Service"底层也是这么包的，没什么神秘。

核心设计问题：HTTP 是无状态的，Agent 是有状态的

这是这堂课最关键的设计点，先想清楚再写代码。

HTTP 协议本身无状态——每个请求都是独立的，服务器不记得上次谁问过什么。但你的 Agent 有状态——它需要 messages 历史才能"记住"对话。

这意味着你必须在两者之间架一座桥。主流方案有三种：

方案怎么做适用场景
A. 每次请求带完整历史 客户端把整段 messages 作为请求体发过来，服务器无状态地处理一轮 最简单，但客户端负担重、请求体大
B. 会话 ID + 服务端存储 客户端只发 user_id 和消息，服务端按 user_id 存取 messages 本课采用。生产级主流方案
C. 完全无状态 + 客户端管理 服务器不存任何东西，每次请求都从客户端拿完整上下文 无状态服务，但客户端复杂、隐私风险

本课用方案 B——它和上一课的 memory.json 思路一致，只是从「单文件单用户」升级到「按 user_id 多文件」。

最小可用版本

假设上一课的 WeatherAgent 类已经写好（在 agent.py 里）。我们新建一个 server.py：

# server.py
from fastapi import FastAPI
from pydantic import BaseModel
from agent import WeatherAgent, SYSTEM_PROMPT, get_weather, calculate

app = FastAPI(title="天气助手 API")

# --- 请求 / 响应模型（Pydantic 自动校验） ---
class ChatRequest(BaseModel):
    user_id: str
    message: str

class ChatResponse(BaseModel):
    reply: str
    trace: list[dict]  # 调度轨迹，方便调试

# --- Agent 工厂：按 user_id 创建或复用 Agent ---
agents: dict[str, WeatherAgent] = {}  # 简化：内存里缓存。生产环境用 Redis 或 DB

def get_or_create_agent(user_id: str) -> WeatherAgent:
    if user_id not in agents:
        agent = WeatherAgent(
            system_prompt=SYSTEM_PROMPT,
            memory_file=f"memory_{user_id}.json",  # 每用户一个文件
            max_turns=20,
        )
        # 注册工具
        agent.register_tool(
            name="get_weather",
            description="查询某个城市的实时天气",
            params={"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]},
            fn=get_weather,
        )
        agent.register_tool(
            name="calculate",
            description="计算数学表达式，如 '28 - 25'",
            params={"type": "object", "properties": {"expression": {"type": "string"}}, "required": ["expression"]},
            fn=calculate,
        )
        agents[user_id] = agent
    return agents[user_id]

# --- 主接口：POST /chat ---
@app.post("/chat", response_model=ChatResponse)
async def chat(req: ChatRequest):
    agent = get_or_create_agent(req.user_id)
    # 记录调用前的 messages 长度，算出这一轮新增的轨迹
    before = len(agent.messages)
    reply = agent.chat(req.message)
    new_msgs = agent.messages[before:]
    # 简化轨迹：只保留工具调用
    trace = [
        {"tool": m.get("function", {}).get("name"), "args": m.get("function", {}).get("arguments")}
        for m in new_msgs
        if m.get("role") == "assistant" and m.get("tool_calls")
    ]
    return ChatResponse(reply=reply, trace=trace)

# --- 健康检查 ---
@app.get("/health")
async def health():
    return {"status": "ok"}

pip install fastapi uvicorn
uvicorn server:app --reload --port 8000

看到 Uvicorn running on http://127.0.0.1:8000 就成了。打开 http://localhost:8000/docs，FastAPI 已经自动生成了一个交互式文档页——你可以直接在浏览器里点 "Try it out" 测试接口。

试一下

用 curl 或在 docs 页面里发请求：

# 第一轮对话
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"user_id": "alice", "message": "我在北京"}'

# 返回
{
  "reply": "好的，已记下你在北京。",
  "trace": []
}

# 第二轮（同一个 user_id）
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"user_id": "alice", "message": "我这儿天气怎么样？"}'

# 返回——注意 trace 里能看到工具调用
{
  "reply": "北京今天晴，气温 25°C。",
  "trace": [{"tool": "get_weather", "args": "{\"city\": \"北京\"}"}]
}

# 换个用户
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"user_id": "bob", "message": "我在哪？"}'

# Bob 是新用户，什么都不知道
{
  "reply": "我还不了解你的位置，请告诉我你在哪个城市。",
  "trace": []
}

注意第三个请求——bob 是新用户，get_or_create_agent 给他新建了一个 Agent 实例和独立的 memory_bob.json。这就是多用户隔离的最小实现。

关键设计点拆解

1. 为什么用 agents: dict 缓存 Agent 实例？

如果每个请求都 new WeatherAgent()，会反复读 memory_*.json 文件——慢，且浪费内存。用字典缓存后，第一次访问某 user_id 时加载，后续直接复用。

但这只是教学简化版。生产环境有两个问题：① 多进程/多机器部署时，dict 不共享；② 内存无限增长，活跃用户多了会 OOM。生产方案是把 messages 存到 Redis/PostgreSQL，Agent 实例按需创建用完丢弃。本课先享受「能用」，第 8 课左右再讲生产化。

2. async def 但 Agent 内部是同步的——矛盾吗？

FastAPI 的 async def 让这个端点能被并发调用，但 agent.chat() 内部调 OpenAI 是同步阻塞的。这意味着：如果一个请求正在等 LLM 响应，其他请求会被卡住。

两种解法：

  • 简单版（本课采用）：直接同步调用。单机并发量不大（10-50 并发）时够用。FastAPI 会把 async def 里同步阻塞的部分放到线程池，不会完全卡死。
  • 进阶版：用 httpx.AsyncOpenAI 替代 OpenAI，把 _call_llm_with_retry 改成 async def，整个链路都异步。能撑更高并发，但代码复杂度上升。等你的服务真扛不住时再换。

3. Pydantic 模型自动校验请求

class ChatRequest(BaseModel) 不是装饰——FastAPI 会自动校验请求体：少字段、类型错、JSON 不合法，都会返回清晰的 422 错误，不需要你写任何 if 校验。比如： 

# 少发 message 字段
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"user_id": "alice"}'

# 返回
{
  "detail": [{
    "type": "missing",
    "loc": ["body", "message"],
    "msg": "Field required"
  }]
}

这是 FastAPI 相比 Flask 的核心优势之一——类型提示驱动校验和文档，省掉大量样板代码。

动手实验

  1. 跑通服务，在 /docs 页面里交互测试，确认能正常对话。
  2. 用两个不同的 user_id（如 alice / bob）分别聊几轮，确认各自记忆隔离。退出服务重启，再发请求，确认历史还在（从 memory_*.json 加载回来了）。
  3. 写个最小前端：新建 index.html，用 fetch 调用 /chat，把回复显示在页面上。这一步让你第一次体会「我的 Agent 有了界面」。代码框架： 
    <!-- index.html，放在项目根目录 -->
<input id="msg" placeholder="说点什么...">
<button onclick="send()">发送</button>
<div id="log"></div>
<script>
async function send() {
  const msg = document.getElementById('msg').value;
  const r = await fetch('/chat', {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify({user_id: 'web', message: msg})
  });
  const data = await r.json();
  document.getElementById('log').innerHTML += `<p>你: ${msg}</p><p>助手: ${data.reply}</p>`;
}
</script>
    要让 FastAPI 能返回这个 HTML，在 server.py 加一句： 
    from fastapi.responses import FileResponse
@app.get("/")
async def index():
    return FileResponse("index.html")
    然后访问 http://localhost:8000/，你就有了一个能聊天的网页。这是后面做产品的起点。
  4. 并发测试：开两个终端窗口，同时用 curl 发请求（一个 alice 一个 bob），观察会不会互相干扰。这是验证多用户隔离的最直接方式。

小测验

检查你的理解

HTTP 是无状态协议，但你的 Agent 需要记忆对话历史。本课采用的关键设计是？

  • 让 LLM 自己记住历史，不靠服务器
  • 用 user_id 作为 key，服务端按用户存取 messages，每个用户一个独立的 Agent 实例和记忆文件
  • 每次请求都让客户端把完整历史发过来，服务端完全不存
  • 把所有用户的历史混在一起存一个文件

应用一下

你的服务上线后，用户 A 抱怨「我和 Agent 说了我在北京，但下次它忘了」。最可能的原因是？

  • LLM 记忆能力太差
  • 系统提示没写好
  • 每次请求的 user_id 不一致（比如前端生成了随机 ID），导致服务端把 A 当成不同用户，每次都新建空 Agent
  • FastAPI 不支持持久化
