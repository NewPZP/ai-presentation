流式输出

让回复一字一字出现，像 ChatGPT 那样 · 约 14 分钟

为什么要做流式输出？

你用 ChatGPT 时有没有注意过--它的回答不是一次性蹦出来的，而是一字一字、一句一句冒出来的。这不是花架子，是一个对产品体验影响巨大的工程细节。

对比两种体验：

非流式（前 7 课的做法）流式
用户发问 → 等 3-15 秒 → 一次性看到完整回答 用户发问 → 0.5 秒内开始看到字 → 边生成边显示
等待期间界面卡住，用户怀疑是不是坏了 立即有反馈，用户知道「在动」
长回答时尤其痛苦（10 秒+） 用户可以边看边思考，提前决定要不要打断

交互设计有条老原则：100ms 内有反馈，用户觉得「即时」；1 秒内有反馈，觉得「流畅」；10 秒没反馈，觉得「坏了」。LLM 生成慢（几秒到几十秒），非流式必然撞 10 秒墙。流式是唯一的解。

流式的本质：Server-Sent Events

HTTP 通常是「请求 → 等响应 → 一次性返回」--客户端发请求，等服务端把整个回答准备好，再一次性收回来。这对 LLM 不合适，因为 LLM 是逐 token 生成的，每生成一个字就可以发给用户，没必要等整句生成完。

流式的做法是 Server-Sent Events（SSE）：

  1. 客户端发一个普通 POST 请求
  2. 服务端不一次性返回，而是保持连接打开，有新内容就推一段
  3. 客户端边收边显示，直到服务端关闭连接

浏览器原生支持 SSE（EventSource 或 fetch + ReadableStream），FastAPI 也原生支持--不用装额外依赖。

第一件事：LLM 调用改成流式

OpenAI SDK 支持流式--加个 stream=True，返回的就不是完整 response，而是一个迭代器，每个 chunk 包含一小段（通常 1-3 个字）。 

# 非流式（前 7 课）
resp = client.chat.completions.create(model=..., messages=..., tools=...)
msg = resp.choices[0].message  # 一次性拿到完整消息

# 流式
stream = client.chat.completions.create(model=..., messages=..., tools=..., stream=True)
for chunk in stream:
    delta = chunk.choices[0].delta  # 每个 chunk 的增量
    if delta.content:
        print(delta.content, end="", flush=True)  # 边收边打印

注意 delta 这个词--它代表「这次新增的内容」，不是完整内容。第一个 chunk 可能是「北」，第二个是「京」，第三个是「今天」……拼起来才是完整回答。

第二件事：Agent 循环的流式改造

这里有个棘手的地方：Agent 是循环的。一轮对话里可能要先调工具、再生成回答。流式时要分清两种情况：

  1. LLM 要调工具 → tool_call 不是流式的（要拿到完整参数才能执行），这部分悄悄做，不给用户看
  2. LLM 在生成最终回答 → 这部分流式给用户看

改造后的 chat_stream 方法：

def chat_stream(self, user_input: str):
    """流式版 chat：yield 出每个 token，调用方边收边显示"""
    self.messages.append({"role": "user", "content": user_input})

    while True:
        messages_to_send = self._trim(self.messages)

        # 流式调用 LLM
        stream = self.client.chat.completions.create(
            model=self.model,
            messages=messages_to_send,
            tools=self.tools,
            stream=True,
        )

        # 累积本次 LLM 的完整回复（要存进 messages）
        content_parts = []
        tool_calls_parts = []  # tool_call 是分 chunk 来的，要拼

        for chunk in stream:
            delta = chunk.choices[0].delta

            # 1. 文本内容 -> 流式 yield 给用户
            if delta.content:
                content_parts.append(delta.content)
                yield {"type": "token", "content": delta.content}

            # 2. tool_call -> 累积起来，不 yield（用户不需要看）
            if delta.tool_calls:
                for tc in delta.tool_calls:
                    idx = tc.index
                    while len(tool_calls_parts) <= idx:
                        tool_calls_parts.append({"id": "", "name": "", "args": ""})
                    if tc.id:
                        tool_calls_parts[idx]["id"] = tc.id
                    if tc.function:
                        if tc.function.name:
                            tool_calls_parts[idx]["name"] += tc.function.name
                        if tc.function.arguments:
                            tool_calls_parts[idx]["args"] += tc.function.arguments

        # 把这次 LLM 回复存进 messages
        msg = {"role": "assistant", "content": "".join(content_parts) or None}
        if tool_calls_parts:
            msg["tool_calls"] = [{
                "id": tc["id"],
                "type": "function",
                "function": {"name": tc["name"], "arguments": tc["args"]}
            } for tc in tool_calls_parts]
        self.messages.append(msg)

        # 没工具调用 -> 这次是最终回答，结束
        if not tool_calls_parts:
            self._save_messages()
            yield {"type": "done"}
            return

        # 有工具调用 -> 执行，把结果喂回去，继续循环
        for tc in tool_calls_parts:
            yield {"type": "tool_start", "name": tc["name"]}
            args = json.loads(tc["args"]) if tc["args"] else {}
            result = self._execute_tool_with_retry_tc(tc)
            self.messages.append({
                "role": "tool",
                "tool_call_id": tc["id"],
                "content": result,
            })
            yield {"type": "tool_end", "name": tc["name"], "result": result}

def _execute_tool_with_retry_tc(self, tc, max_retries=2):
    """tool_call 字典版的工具执行（和第 5 课逻辑一致）"""
    for attempt in range(max_retries):
        try:
            args = json.loads(tc["args"]) if tc["args"] else {}
            if tc["name"] not in self.tool_map:
                return f"没有叫 '{tc['name']}' 的工具"
            return str(self.tool_map[tc["name"]](**args))
        except Exception as e:
            if attempt == max_retries - 1:
                return f"工具执行失败：{e}"

看 yield 这个关键字--它把方法变成了「生成器」。调用方 for event in agent.chat_stream(msg): 时，每 yield 一次就收到一个事件。这就是流式的本质：把一个长任务拆成无数小事件，生产一个发一个，消费一个收一个。

第三件事：FastAPI 端点改成 SSE

FastAPI 用 StreamingResponse 把生成器包成 SSE 流：

# server.py 新增流式端点
from fastapi.responses import StreamingResponse
import json

@app.post("/chat/stream")
async def chat_stream(req: ChatRequest):
    agent = get_or_create_agent(req.user_id)

    def event_stream():
        """把 Agent 的事件转成 SSE 格式"""
        for event in agent.chat_stream(req.message):
            # SSE 格式：每个事件以 "data: " 开头，两个换行结尾
            yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"

    return StreamingResponse(
        event_stream(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",  # 关闭 nginx 缓冲，否则流被攒着
        }
    )

每个事件是 JSON 序列化后塞进 data: ...\n\n 的 SSE 帧里。客户端用 fetch + ReadableStream 解析。

前端怎么接收

浏览器的 EventSource 只支持 GET，POST 得用 fetch。下面是个最小可用的流式前端：

<input id="msg" placeholder="说点什么...">
<button onclick="send()">发送</button>
<div id="log"></div>

<script>
async function send() {
  const msg = document.getElementById('msg').value;
  document.getElementById('log').innerHTML += `<p><b>你:</b> ${msg}</p><p id="cur"><b>助手:</b> <span id="typing"></span></p>`;

  const r = await fetch('/chat/stream', {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify({user_id: 'web', message: msg})
  });

  const reader = r.body.getReader();
  const decoder = new TextDecoder();
  let buffer = '';
  const typing = document.getElementById('typing');

  while (true) {
    const {done, value} = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, {stream: true});

    // SSE 帧以 \n\n 分隔
    const events = buffer.split('\n\n');
    buffer = events.pop();  // 最后一段可能不完整，留着

    for (const e of events) {
      if (!e.startsWith('data: ')) continue;
      const data = JSON.parse(e.slice(6));

      if (data.type === 'token') {
        typing.textContent += data.content;  // 一字一字追加
      } else if (data.type === 'tool_start') {
        typing.innerHTML += `<i>[调用 ${data.name}]</i>`;
      } else if (data.type === 'tool_end') {
        typing.innerHTML += `<i>[完成]</i>`;
      } else if (data.type === 'done') {
        typing.innerHTML += ' ✓';
      }
    }
  }
}
</script>

跑起来，你会看到回答真的一字一字冒出来--和 ChatGPT 一样的体验。这个细节会让你的产品质感上一个台阶。

关键设计点

1. 为什么用生成器（yield）而不是回调？

Python 的生成器是流式的天然表达方式。调用方 for event in agent.chat_stream(...) 写起来和普通循环一样，但内部是流式的。同步代码的简洁 + 流式的实时性。回调写法（传一个 on_token 函数进来）也可以，但嵌套深、错误处理麻烦。

2. tool_call 的流式拼接

这是最容易踩坑的地方。非流式时 tool_calls 是一个完整的列表，直接用就行。流式时它是分 chunk 来的--第一个 chunk 给 id 和函数名，后面的 chunk 给 arguments 的一段。你必须自己拼起来，否则 json.loads 会失败。

代码里这段是关键：

if delta.tool_calls:
    for tc in delta.tool_calls:
        idx = tc.index  # 用 index 对齐同一个 tool_call 的不同 chunk
        # ...累加 arguments 字符串...

3. 事件类型设计

注意我们 yield 的事件有 4 种 type：

  • token - 文本内容，前端追加显示
  • tool_start - 工具开始执行，前端可以显示「正在查询…」
  • tool_end - 工具结束，前端可以显示结果或隐藏 loading
  • done - 整轮对话结束

这种结构化事件比纯文本流更强大--前端可以根据类型做不同 UI 反馈。比如 tool_start 时显示一个 spinner，token 时追加文字。这是 Agent 流式和普通 ChatGPT 流式的区别：Agent 有工具调用，需要额外的事件类型。

动手实验

  1. 把流式端点跑通，在前端体验「一字一字冒出来」的感觉。故意问一个需要调工具的问题（「北京天气」），看前端能不能显示「[调用 get_weather]」然后接着流式回答。
  2. 对比体验：同时保留 /chat（非流式）和 /chat/stream（流式）两个端点，前端各做一份。问同一个长问题（「详细解释下天气对穿衣的影响」），对比等待体验。你会直观感受到流式的价值。
  3. 断线处理：故意在流式过程中关掉服务，看前端会卡在哪。生产环境需要前端检测连接断开并提示用户「连接中断，请重试」--这是流式的代价：复杂度上升。
  4. （进阶）取消功能：加一个「停止」按钮，用 AbortController 中断 fetch。后端会收到连接断开，Agent 循环可以检测到并停止。这是 ChatGPT 都有的功能，但实现要前后端配合。
