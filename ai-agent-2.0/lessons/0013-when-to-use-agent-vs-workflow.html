第 13 课 · AI Agent 2.0 实战

何时用 Agent / 何时用 Workflow

不是所有问题都该上 Agent · 约 15 分钟

前 12 课的一个副作用

学到这里，你已经有能力做很复杂的 Agent 系统了：多工具、多 Agent 委托、RAG、流式、生产化部署。但这个能力有个危险的副作用--你看什么问题都像「该上 Agent」。

举个真实场景：你老板说「帮我把每天的销售额汇总成一段话，发到飞书群」。你的第一反应可能是：

# 错误的本能反应：上 Agent！
agent = Agent(
    tools=[query_database, calculate_summary, format_text, send_feishu_msg],
    system_prompt="你是销售汇总助手..."
)
agent.run("把今天的销售汇总发到飞书")

但这其实是个固定流程--每天都是「查数据库 → 算汇总 → 格式化 → 发飞书」这四步，路径完全可预测。用 Agent 反而是杀鸡用牛刀：LLM 调用贵、可能出错、还不可预测。正确做法是直接写代码：

# 正确做法：Workflow（固定代码流程）
def daily_sales_report():
    data = query_database("SELECT * FROM sales WHERE date = TODAY")
    summary = f"今日销售 {len(data)} 单，总额 {sum(d.amount for d in data)} 元"
    send_feishu_msg("销售群", summary)

# 每天定时跑这个函数就行，不需要 LLM

这一课就是讲这个判断：什么时候该上 Agent，什么时候该用 Workflow，什么时候两者都不需要。

核心区分：Workflow vs Agent

Anthropic 在《Building effective agents》里给了清晰的定义，这是业界共识：

类型路径谁决定特点
Workflow 代码写死 路径固定、可预测、便宜、可靠。LLM 只在固定步骤里被调用。
Agent LLM 自己决定 路径灵活、能处理意外、但贵、慢、不可预测。

一句话：路径可预测就用 Workflow，路径需要 LLM 灵活决定才用 Agent。Agent 的核心价值是「自主决策」，如果你的任务路径是固定的，这个价值就用不上，反而成了累赘。

常见 Workflow 模式

Anthropic 总结了五种常用 Workflow 模式，都不需要完整的 Agent 循环：

1. Prompt Chaining（提示链）

把一个任务拆成固定步骤，每步调一次 LLM，串起来：

# 写文档 → 翻译 → 校对
draft = llm("写一段产品介绍")
translated = llm(f"翻译成英文: {draft}")
final = llm(f"校对这段英文: {translated}")

适用：任务能清晰拆成固定步骤，每步独立。比让一个 Agent 「写+翻译+校对」更可控。

2. Routing（路由）

先分类，再走不同分支：

def handle(msg):
    category = llm(f"分类这个客户问题：技术/账单/售后。只返回类别名。问题: {msg}")
    if category == "技术":
        return tech_handler(msg)
    elif category == "账单":
        return billing_handler(msg)
    else:
        return support_handler(msg)

适用：问题类型有限且可枚举。比让一个 Agent 处理所有类型更准（每个 handler 可以有专门的 prompt 和工具）。

3. Parallelization（并行）

多个子任务并行跑，汇总结果：

import asyncio

async def analyze(doc):
    # 三个维度并行分析
    sentiment, summary, keywords = await asyncio.gather(
        llm(f"情感分析: {doc}"),
        llm(f"摘要: {doc}"),
        llm(f"关键词: {doc}"),
    )
    return {"sentiment": sentiment, "summary": summary, "keywords": keywords}

适用：子任务互相独立。比串行让一个 Agent 做快 3 倍。

4. Orchestrator-Workers（编排-执行）

一个编排器拆任务，多个执行器并行干活，编排器汇总：

# 写一篇多章节报告
outline = llm("给出报告大纲：1. 背景 2. 现状 3. 建议")
chapters = await asyncio.gather(*[
    llm(f"写第{i}章: {topic}") for i, topic in enumerate(outline)
])
report = llm(f"把这些章节拼成连贯报告: {chapters}")

这看起来像多 Agent，但区别是编排逻辑是代码写死的，不是 LLM 自主决定。适合「任务结构固定但内容需要 LLM 生成」的场景。

5. Evaluator-Optimizer（评估-优化）

生成 → 评估 → 不合格就重新生成：

def write_until_good(task):
    for _ in range(3):
        draft = llm(f"写: {task}")
        score = llm(f"打分 0-10: {draft}")
        if int(score) >= 8:
            return draft
        task = f"{task}\n上次得分 {score}，请改进"
    return draft

适用：有明确质量标准的生成任务。比让 Agent 自己判断「够不够好」更可控。

决策框架

面对一个新需求，按这个顺序问自己：

  1. 路径能预先写死吗？
    • 能 → Workflow（代码写流程，LLM 只在固定步骤用）
    • 不能，要 LLM 看情况决定 → 继续问
  2. 需要调几个工具？
    • 1 个 → 直接调，不用 Agent 循环
    • 2-5 个，且选择逻辑简单 → Workflow + Routing
    • 5+ 个，或选择逻辑复杂、要看中间结果决定下一步 → Agent
  3. 能容忍多少不可预测性？
    • 要求 100% 可预测（如金融交易）→ Workflow，别用 Agent
    • 能容忍偶尔跑偏、有人兜底 → Agent 可以
  4. 延迟和成本能接受吗？
    • 要亚秒级响应 → 别用 Agent，LLM 调用就秒级了
    • 能接受 3-30 秒 → Agent 可以

三个反模式

反模式 1：为了用 Agent 而用

最常见的坑。听到「Agent 很厉害」就把所有 LLM 应用都做成 Agent。结果是简单问题复杂化、成本翻倍、还不可控。

自查：你的 Agent 如果去掉循环、每次固定调一次 LLM，结果会差多少？如果差不多，就不该用 Agent。

反模式 2：把固定流程硬塞给 Agent

明明路径固定，却让 Agent 「自主决定」--然后又用超长的 system prompt 告诉它「必须先做 A 再做 B 再做 C」。这等于用 LLM 模拟一个 if-else，又贵又不可靠。

自查：你的 system prompt 里是不是写了「必须按以下步骤」？如果是，考虑改成 Workflow。

反模式 3：Agent 工具太多

给一个 Agent 塞 20 个工具，期待它「什么都能干」。结果是工具选择准确率暴跌，LLM 经常选错。

解法：用第 12 课的多 Agent 委托，按领域拆分。或者用 Routing 先分类，再走专用 Workflow。

一个真实案例：智能客服

用这个案例串起所有判断。需求：「做一个客服系统，能回答产品问题、处理退款、查订单」。

错误做法：一个大 Agent，工具包括 [search_docs, process_refund, query_order, ...]，system prompt 写一堆规则。

正确做法：分层架构。

# 第一层：Routing（Workflow）
def handle(user_msg):
    intent = llm(f"分类意图：product_question/refund/order/other。只返回类别。消息: {user_msg}")

    if intent == "product_question":
        # 第二层：Workflow + RAG（固定流程）
        docs = retrieve(user_msg, n=3)
        return llm(f"基于文档回答: {docs}\n问题: {user_msg}")

    elif intent == "refund":
        # 第二层：Agent（需要多步：查订单 → 验证资格 → 执行退款）
        return refund_agent.run(user_msg)  # 工具：query_order, check_policy, process_refund

    elif intent == "order":
        # 第二层：Workflow（查订单就是一次调用）
        order = query_order(extract_order_id(user_msg))
        return format_order(order)

    else:
        return "转人工客服"

看这个架构：外层是 Workflow（Routing），内层按需选 Workflow 或 Agent。产品问答用 RAG Workflow（路径固定），退款用 Agent（需要多步且路径灵活），查订单用纯 Workflow。这就是「分而治之」--每个子问题用最合适的方案。

这是工程成熟的标志：不是「全 Agent」或「全 Workflow」，而是按子问题的特性混合使用。新手倾向于一个方案套所有问题，老手会拆解后分别选最合适的。

动手实验

  1. 拿你身边的一个真实需求（工作或生活中的），用决策框架判断该用 Workflow 还是 Agent。写出判断过程：路径能不能写死？要几个工具？能容忍多少不可预测性？
  2. 改造实验：找一个你之前用 Agent 做的场景，试着改成 Workflow。对比两者的准确率、延迟、成本。很多场景你会惊讶地发现 Workflow 又快又准又便宜。
  3. 混合架构：实现上面那个客服案例的分层架构。体会「外层 Routing + 内层按需选 Workflow/Agent」的设计。
  4. （思考题）找反例：想一个「看着像 Workflow 但其实该用 Agent」的场景。提示：路径在大多数情况下固定，但偶尔需要灵活处理。这种「95% 固定 + 5% 灵活」的场景怎么设计？

小测验

检查你的理解

Workflow 和 Agent 的核心区别是？

  • Workflow 用 OpenAI，Agent 用 Claude
  • Workflow 的路径由代码写死（可预测、便宜、可靠），Agent 的路径由 LLM 自主决定（灵活、但贵、慢、不可预测）。路径能写死就用 Workflow
  • Workflow 是命令行的，Agent 是 Web 的
  • Agent 比 Workflow 更先进，应该优先用

应用一下

需求：「每天早上把昨日的销售数据汇总成一段话，发到飞书群」。该用什么？

  • 多 Agent 系统，一个查数据一个写汇总一个发飞书
  • 单 Agent，工具包括 query_db + format + send_feishu
  • Workflow（甚至不用 LLM）--路径完全固定：查数据库 → 算汇总 → 发飞书。用代码写死最可靠、最便宜。LLM 只在需要「写一段自然语言汇总」时调一次
  • RAG，检索历史销售数据
