第 12 课 · AI Agent 2.0 实战

多 Agent 委托

让主 Agent 把活分给专家 Agent · 约 16 分钟

单个 Agent 的极限

到第 11 课为止，你的 Agent 已经很能干了--能查天气、能算数、能检索文档、能流式回答。但随着能力增多，你会撞到一个新问题：单个 Agent 的系统提示越来越长，工具越来越多，LLM 开始选错工具、忘规则、注意力涣散。

举个具体场景：你做一个企业助手，要支持「查天气 + 查公司 HR 政策 + 查产品文档 + 写代码 + 发邮件」。单个 Agent 会变成这样：

tools = [
    get_weather, search_hr_docs, search_product_docs,
    write_code, send_email, calculate, search_calendar, ...
]  # 20 个工具，LLM 选不过来

system_prompt = """
你是企业助手。
HR 问题用 search_hr_docs，产品问题用 search_product_docs...
（规则越写越长，LLM 记不住）
"""

这是单 Agent 的天花板：工具多了，选择准确率下降；规则多了，遵循率下降。解决方案不是加更多规则，而是把一个万能 Agent 拆成多个专家 Agent。

核心模式：Handoff（委托）

多 Agent 最常见的模式叫 Handoff（委托）：一个「主 Agent」（也叫 triage / router）接收用户请求，判断该交给谁，然后把整个对话移交给目标专家 Agent。专家处理完后，可以再交回主 Agent。 

用户：帮我查下北京天气，然后写封邮件告诉老板明天团建改室内

主 Agent（Router）：
  分析请求 -> 包含「查天气」和「写邮件」两部分
  
  步骤 1：委托给「天气专家 Agent」
    -> 天气专家调 get_weather("北京") -> 返回「晴，25°C」
    -> 交回主 Agent
  
  步骤 2：委托给「邮件专家 Agent」
    -> 邮件专家用天气结果写邮件 -> 调 send_email
    -> 交回主 Agent
  
  主 Agent：完成，回复用户「邮件已发送」

关键点：用户只和主 Agent 对话，看不到子 Agent 的存在。主 Agent 像前台，专家像后台部门--用户找前台，前台把活分派给对应部门。

两种实现方式

实现多 Agent 有两种主流方式：

方式 A：用工具调用模拟委托（最简单）

把每个专家 Agent 包装成一个工具，主 Agent 调用工具时实际是调用了子 Agent：

# weather_agent.py - 专家 Agent
class WeatherAgent:
    def __init__(self):
        self.system_prompt = "你是天气专家，只负责查天气和比较天气。"
        self.tools = [get_weather, calculate]  # 工具少，选择准

    def run(self, query: str) -> str:
        """独立完成一个天气相关任务"""
        # 内部是个完整的 Agent 循环（第 5 课的 WeatherAgent）
        # 处理完返回最终文本
        ...

# email_agent.py - 另一个专家
class EmailAgent:
    def __init__(self):
        self.system_prompt = "你是邮件专家，负责起草和发送邮件。"
        self.tools = [send_email, search_contacts]

    def run(self, query: str) -> str:
        ...

# main_agent.py - 主 Agent
weather_agent = WeatherAgent()
email_agent = EmailAgent()

# 把专家包装成工具
def delegate_to_weather(query: str) -> str:
    """委托给天气专家处理"""
    return weather_agent.run(query)

def delegate_to_email(query: str) -> str:
    """委托给邮件专家处理"""
    return email_agent.run(query)

main_tools = [
    {
        "name": "delegate_to_weather",
        "description": "把天气相关的问题交给天气专家处理",
        "parameters": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}
    },
    {
        "name": "delegate_to_email",
        "description": "把邮件相关的问题交给邮件专家处理",
        "parameters": {"type": "object", "properties": {"query": {"type": "string"}, "required": ["query"]}}
    }
]

tool_map = {"delegate_to_weather": delegate_to_weather, "delegate_to_email": delegate_to_email}

# 主 Agent 的循环和第 5 课一模一样，只是工具变了
def main_chat(user_input: str) -> str:
    # ... 标准 Agent 循环
    # LLM 会调 delegate_to_weather 或 delegate_to_email
    # 主 Agent 把任务描述传给子 Agent，子 Agent 独立处理完返回结果
    # 主 Agent 拿到结果后继续（可能再委托或直接回复用户）
    ...

这个方式的好处：不用新框架，用前 5 课的知识就能实现。每个子 Agent 就是一个独立的 WeatherAgent 实例，主 Agent 只是把它们当工具调。

方式 B：用 OpenAI Agents SDK（原生支持）

OpenAI 2024 年推出了 Agents SDK，原生支持 Handoff。它把 Agent、工具、委托都抽象成一等公民： 

from agents import Agent, Runner

# 定义专家 Agent
weather_agent = Agent(
    name="天气专家",
    instructions="你只负责天气相关问题，调 get_weather 工具。",
    tools=[get_weather_tool],
)

email_agent = Agent(
    name="邮件专家",
    instructions="你只负责邮件起草和发送。",
    tools=[send_email_tool],
)

# 主 Agent，通过 handoffs 声明可以委托给谁
main_agent = Agent(
    name="企业助手",
    instructions="你是企业助手。把天气问题交给天气专家，邮件问题交给邮件专家。",
    handoffs=[weather_agent, email_agent],  # ← 关键
)

# 运行
result = Runner.run_sync(main_agent, "北京天气怎么样？")
print(result.final_output)

Agents SDK 会自动处理委托：主 Agent 判断该交给谁，SDK 把对话上下文转给目标 Agent，目标 Agent 处理完后（可能调工具、可能再委托），把最终结果返回。

方式 A vs 方式 B 怎么选？ 学习阶段先用方式 A--它让你看透「委托」的本质就是「把子 Agent 当工具调」。理解了之后再用方式 B--SDK 帮你处理了上下文传递、流式、并行委托等细节，生产环境更省事。但不理解原理直接用 SDK，出问题时你会无从下手。

关键设计问题

1. 怎么切分 Agent？

不是工具越多越该拆。拆分的依据是：「这群工具是否共享同一套心智模型和规则」。

该拆不该拆
天气工具 + 邮件工具 + 代码工具（领域差异大） get_weather + calculate + search_weather_news（都是天气领域）
HR 问答 + 财务问答 + 技术问答（知识源不同） get_weather + format_weather_report + suggest_clothing（一个流程）
需要不同 system prompt 的能力 能用一个 system prompt 覆盖的能力

原则：宁少勿多。两个 Agent 能解决就别拆成五个。每多一个 Agent，就多一层委托的开销（多一次 LLM 调用）、多一个出错点（主 Agent 可能委错）。

2. 主 Agent 怎么决定委托给谁？

三种策略：

  1. LLM 判断（最常用）：在 system prompt 里描述每个子 Agent 的职责，让 LLM 根据用户问题选。灵活但偶尔选错。
  2. 关键词路由：写 if-else 规则，「天气」-> 天气 Agent，「邮件」-> 邮件 Agent。快、准、但不灵活，新问题没法处理。
  3. 分类器路由：用一个小模型或 embedding 分类，再路由。比 LLM 便宜、比关键词灵活。适合量大场景。

学习阶段用方式 1（LLM 判断）就行，量大了再优化成方式 3。

3. 上下文怎么传？

委托时，主 Agent 要把足够的信息传给子 Agent，但不能把整个对话历史都倒过去（太贵、太乱）。

常见做法：主 Agent 调用委托工具时，把任务描述作为参数传给子 Agent。子 Agent 用自己的 system prompt + 任务描述开始独立处理。

# 主 Agent 调用委托工具
delegate_to_email(query="帮我写邮件告诉老板明天团建改室内，北京今天晴 25 度")

# 邮件 Agent 收到的是任务描述，不是完整对话历史
# 它用自己的 system prompt 处理这个任务

主 Agent 的职责之一是把上下文压缩成清晰的任务描述。这其实是个好事--强制主 Agent 梳理清楚「我要子 Agent 做什么」，而不是把一堆乱七八糟的对话扔过去。

完整示例：三 Agent 协作

下面是个完整可跑的示例，用方式 A 实现一个「天气 + 邮件 + 计算」三专家协作的助手：

from openai import OpenAI
import json

client = OpenAI()

# ===== 专家 Agent 基类 =====
class SubAgent:
    """一个独立的子 Agent，有自己的 system prompt 和工具"""
    def __init__(self, system_prompt: str, tools: list, tool_map: dict):
        self.system_prompt = system_prompt
        self.tools = tools
        self.tool_map = tool_map

    def run(self, task: str) -> str:
        """处理一个任务，返回最终文本"""
        messages = [
            {"role": "system", "content": self.system_prompt},
            {"role": "user", "content": task}
        ]
        for _ in range(5):  # 最多 5 轮工具调用
            resp = client.chat.completions.create(
                model="gpt-4o-mini",
                messages=messages,
                tools=self.tools,
            )
            msg = resp.choices[0].message
            messages.append(msg)
            if not msg.tool_calls:
                return msg.content
            for tc in msg.tool_calls:
                args = json.loads(tc.function.arguments)
                result = self.tool_map[tc.function.name](**args)
                messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(result)})
        return "处理超时"

# ===== 定义三个专家 =====
def get_weather(city): return {"北京": "晴 25°C", "上海": "多云 28°C"}.get(city, "未知")
def calculate(expr): return str(eval(expr))
def send_email(to, subject, body): return f"已发送给 {to}：{subject}"

weather_agent = SubAgent(
    system_prompt="你是天气专家。只处理天气查询和比较。回答简洁。",
    tools=[{"type": "function", "function": {
        "name": "get_weather", "description": "查城市天气",
        "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}
    }}],
    tool_map={"get_weather": get_weather}
)

calc_agent = SubAgent(
    system_prompt="你是计算专家。只处理数学计算。",
    tools=[{"type": "function", "function": {
        "name": "calculate", "description": "计算表达式",
        "parameters": {"type": "object", "properties": {"expr": {"type": "string"}}, "required": ["expr"]}
    }}],
    tool_map={"calculate": calculate}
)

email_agent = SubAgent(
    system_prompt="你是邮件专家。负责起草和发送邮件。",
    tools=[{"type": "function", "function": {
        "name": "send_email", "description": "发邮件",
        "parameters": {"type": "object", "properties": {
            "to": {"type": "string"}, "subject": {"type": "string"}, "body": {"type": "string"}
        }, "required": ["to", "subject", "body"]}
    }}],
    tool_map={"send_email": send_email}
)

# ===== 主 Agent =====
def delegate_weather(query): return weather_agent.run(query)
def delegate_calc(query): return calc_agent.run(query)
def delegate_email(query): return email_agent.run(query)

main_tools = [
    {"type": "function", "function": {"name": "delegate_weather", "description": "委托天气专家处理天气问题", "parameters": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}}},
    {"type": "function", "function": {"name": "delegate_calc", "description": "委托计算专家处理数学问题", "parameters": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}}},
    {"type": "function", "function": {"name": "delegate_email", "description": "委托邮件专家处理邮件问题", "parameters": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}}},
]

main_tool_map = {"delegate_weather": delegate_weather, "delegate_calc": delegate_calc, "delegate_email": delegate_email}

def main_chat(user_input: str) -> str:
    messages = [
        {"role": "system", "content": "你是企业助手。把天气问题交给天气专家，数学问题交给计算专家，邮件问题交给邮件专家。复杂任务可以拆解后多次委托。"},
        {"role": "user", "content": user_input}
    ]
    for _ in range(10):
        resp = client.chat.completions.create(model="gpt-4o-mini", messages=messages, tools=main_tools)
        msg = resp.choices[0].message
        messages.append(msg)
        if not msg.tool_calls:
            return msg.content
        for tc in msg.tool_calls:
            print(f"-> 委托: {tc.function.name}({tc.function.arguments})")
            args = json.loads(tc.function.arguments)
            result = main_tool_map[tc.function.name](**args)
            print(f"<- 结果: {result[:80]}")
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(result)})
    return "处理超时"

# 测试多步委托
print(main_chat("查下北京和上海天气，算下两地温差，然后发邮件给 boss@company.com 告诉他结果"))

输出：

-> 委托: delegate_weather({"query": "查询北京和上海的天气"})
<- 结果: 北京：晴 25°C；上海：多云 28°C
-> 委托: delegate_calc({"query": "计算 28 - 25"})
<- 结果: 3
-> 委托: delegate_email({"query": "发邮件给 boss@company.com，主题：天气对比，正文：北京 25°C，上海 28°C，温差 3 度"})
<- 结果: 已发送给 boss@company.com：天气对比
已完成。邮件已发给老板，内容包括两地天气和 3°C 的温差。

看这个执行轨迹--主 Agent 把一个大任务拆成三步，分别委托给三个专家，最后汇总回复用户。这就是多 Agent 协作的核心。

多 Agent 的代价

多 Agent 不是免费的，它带来三个新成本：

  1. LLM 调用次数变多：每次委托都是一次独立的 LLM 调用。上面那个例子调了 4 次 LLM（1 主 + 3 子），单 Agent 可能 2 次就够。
  2. 延迟变高：串行委托是累加的。3 个子 Agent 各 2 秒，总延迟 6 秒+。
  3. 委托可能出错：主 Agent 可能委错对象，或任务描述写不清，子 Agent 做错。

这就是为什么下一课（第 13 课）要讲「何时用 Agent / 何时用 Workflow」。多 Agent 是个强大的模式，但也是最容易过度使用的。很多人觉得「多 Agent 听起来很厉害」，就什么问题都拆--结果成本翻倍、延迟变高、还没单 Agent 准。先问自己：单 Agent 真的搞不定吗？

动手实验

  1. 把上面的三 Agent 示例跑通。然后故意问一个「查天气 + 写代码」的混合问题，看主 Agent 怎么拆解和委托。
  2. 对比单 Agent vs 多 Agent：把三个专家的工具和规则合并到一个单 Agent 里，用第 7 课的评测脚本对比两者的工具选择准确率、回答质量、成本。你会第一次用数据回答「这个场景该不该拆」。
  3. 用 OpenAI Agents SDK 重写：用方式 B（官方 SDK）实现同样的三专家协作。对比代码量、可读性、控制粒度。SDK 帮你省了什么，又限制了你什么？
  4. （进阶）并行委托：如果两个子任务互不依赖（如「查北京天气」和「查上海天气」），可以并行委托，不串行等待。用 asyncio.gather 或 Agents SDK 的并行能力实现。这是降低延迟的关键技巧。

小测验

检查你的理解

多 Agent 委托（Handoff）模式的核心思路是？

  • 训练多个模型，投票决定答案
  • 主 Agent 接收请求后判断该交给谁，把任务委托给专家 Agent 处理，专家处理完交回。每个 Agent 工具少、规则短，选择更准
  • 把一个 LLM 调多次，每次问不同问题
  • 让用户选要和哪个 Agent 对话

应用一下

你做了个多 Agent 系统，但发现「延迟比单 Agent 还高，成本翻倍，准确率没提升」。最可能的原因？

  • LLM 太笨，换更贵的模型
  • 子 Agent 数量不够，再加几个
  • 过度拆分--这个场景本不需要多 Agent。应该先用单 Agent 评测，确认单 Agent 真的搞不定（工具选择准确率低、规则记不住）再拆。拆分要有数据依据，不是「听起来更厉害」
  • 网络问题，加机器就行
