Harness 选型对比

Pi / DSH / OpenCode 等 · 含同模型实测 · 打印友好

数据截至 2026-09。对比口径为 OpenCode 1.18.30 / pi 0.85.1 / DSH 0.1.5-rc.1。生态变化快，选型前请复核最新版本。

一句话

Harness 都共享同一个五步循环；差异全在循环外面：规划、记忆、沙箱、子代理。选型不是选谁更强，是选它优化的是哪种失败模式。

Harness 的五个部分

Agent = Model + Harness。模型只做一件事：给定文本和工具列表，预测下一句话或下一个工具调用。其余全是 harness： 

① 循环      —— 反复调模型直到任务完成
② 工具路由   —— 把调用分发到文件系统 / shell / 外部 API
③ 记忆      —— 决定哪些上下文留到下一轮
④ 规划      —— 动工前把大任务拆成步骤
⑤ 沙箱边界   —— 约束工具能碰什么

任何 harness 都实现这五个；好不好的分界在 ③④⑤ 和「能不能派子代理且不污染主对话」。

哲学代表优化 against

四种都对，只是赌的失败模式不同。先问自己「今天哪种失败模式在烧我的时间」，答案会指向正确的 harness。

核心对比：Pi vs DSH

两者是最鲜明的两个极端。一句话概括：DSH 把「缺什么」交给插件；Pi 把「多什么」直接砍掉。

Pi 砍掉每样东西都有理由

README 里写明各自的替代方案：MCP → 用 CLI 工具或 extension；子代理 → 用 tmux 或 extension；权限 → 用容器。

Pi 的官方安全声明（原文要点）： Pi 不包含用于限制文件系统、进程、网络或凭据访问的内置权限系统，默认以启动它的用户和进程的权限运行。需要更强边界就自己容器化——官方给了三条路径：Gondolin 扩展（工具进本地 Linux 微 VM，auth 留在宿主）、纯 Docker、OpenShell。

顺带：Oh-My-Pi 是反方向

omp 是 Pi 的极大化 fork：用 Rust 重写引擎、60+ 模型供应商、31 个内建工具，把 IDE 能力（LSP 诊断、DAP 调试器、持久执行内核）直接烤进去。同一份「四工具内核」可以被推向两个相反极端，这本身说明内核的边界划得干净。

同模型实测：差异有多大

一份第三方实测把三个 harness 接到同一个模型（Fireworks 的 DeepSeek V4 Flash，经 NeMo Switchyard 的 OpenAI 兼容端点，并核对 session log 的 responseModel 确认一致），跑同一个任务：修一个 Python CLI 的两个 bug + 加 --top N + 写 pytest + 跑通。

OpenCodePiDSH
用时68 秒45 秒71 秒
模型请求次数19613
工具调用19714
首个请求输入 tokens8,0841,7447,626
输入 tokens 合计238,85619,899148,638
输出 tokens 合计4,6172,0074,277

pytest 结果8 passed6 passed8 passed

三个都完成了任务，报告与实际结果也一致。 作者明确声明这是各跑一次，不是用来评优劣的。

但数字的含义很清楚：

  • 首个请求的大小 = 系统提示词 + 工具定义。 任务文本三者相同，所以 8,084 vs 1,744 的差距纯粹是 harness 塞给模型的「前言」。
  • 这个差距每次请求都累积：总输入 tokens 上 OpenCode 约是 Pi 的 12 倍。
  • 能用 prompt caching 的路径费用影响小，但跑本地模型时，这个差值直接加到每次的 prefill 时间上。

Pi 的省 token 不是优化出来的，是结构上就没有那么多东西要发。 这与模型与成本速查里的「每次调用重发整个 surface」是同一件事的两面。

一个反直觉事实：DSH 依赖 Pi

DSH 的多供应商接入层就是 Pi 的包：dsh-llm-pi-ai 插件依赖 Pi 仓库的 @earendil-works/pi-ai，OpenAI 兼容 / Anthropic 兼容端点的连接都在那里处理；DeepSeek 自家模型另有专用适配器。

这解释了两件事：为什么 DSH 的配置键叫 llm-pi-ai、api: openai-completions 的命名和 Pi 一模一样；以及为什么它这么快就支持一堆第三方供应商——它没重造这块。

所以更准确的定位是：Pi 是最小的 harness 内核 + 可复用的 LLM 接入层；DSH 是最大的 harness 框架，而它在底层用了 Pi 的零件。 官方分类把 DSH 归在「模型公司自研 harness」与「模型无关 OSS harness」中间。

模型 × Harness 的适配问题

这是选型时最容易忽略、但影响很大的一点：模型是在自家 harness 上做过事后训练的，工具词汇刻进了权重。

维度Codex CLIClaude Code
编辑工具形态apply_patch（patch 格式）Edit 传 old_string / new_string（字符串替换）
上下文文件名AGENTS.mdCLAUDE.md

给模型一套它不熟悉的工具格式，它会多花推理 token、多犯错。

证据

条件Terminal-Bench 2.1
Claude Opus 4.6 + Claude Code（纯正组合）70.1%
Claude Opus 4.6 + Terminus 2（通用 harness）63.8%

同一个模型，6 个百分点纯粹来自 harness。arXiv 的 Harness-Bench 用 5,194 次运行得出同向结论：模型 × harness 的组合不同，完成率和失败方式都差很多。

⚠️ 因果是推断，不是实测。 「事后训练导致差异」这个解释在公开范围内没有能切分原因的对照实验。差异被测量到了，原因没有。引用时请分开说。

实用推论

  • 把 Claude / GPT 放到非纯正 harness 上，性能要重新测，不能假设不变。
  • 没有专用 harness、或没有围起来的 open-weight 模型（GLM、Kimi、DeepSeek、Qwen）与模型无关 harness 搭配最自然。
  • DSH 内置了分别读取 Claude Code 和 Codex 的 hooks.json 的插件——已有 harness 的配置资产可以搬过来。

治理差异：谁能用订阅

流传的「不该把 Claude/OpenAI 模型放到第三方 harness」不准确——限制只来自一家，而且方向相反。

值得单独学的：Pi 的供应链硬化

这是 Pi 相对 DSH 最被低估的优势——它把依赖安全做成了制度，而 DSH 是把决定权交给用户（见Tool 插件开发速查里的 allowBuilds）。

措施作用
直接外部依赖精确锁版本（内部 workspace 才用范围）消除版本漂移
.npmrc 设 save-exact=true、min-release-age=2避免解析到当天发布的依赖（供应链攻击高发窗口）
lockfile 是唯一真相，pre-commit 拦截 lockfile 改动依赖变更＝需评审的代码变更
发布的 CLI 包内附 npm-shrinkwrap.json为 npm 用户钉死传递依赖
全链路 --ignore-scripts安装期不执行包代码
定时 npm audit --omit=dev + npm audit signatures持续扫描 + 验签
生命周期脚本依赖走显式白名单新的脚本依赖必须评审后才放行

一条不变的选型原则

看曲线的形状，不只看当前高度。 陡峭尖峰 + 走平的尾巴＝社区正在形成，值得关注后再投入生产；长而浅、不中断的爬升＝工程师在热度退去后还留着它，是更强的慢信号。

配套的两条硬提醒：

  • star 是收藏数，不是安装量。
  • 无论选哪个，可观测性不是可选项。 一个在第 30 轮失败的无人值守任务，没有 trace 就是灾难。
