DSH 架构思想速查

六个可迁移的设计模式 · 附「防的是什么故障」 · 打印友好

对应 DSH 0.1.2-rc.1 / 0.1.5-rc.1（2026-09）。这些思想的价值高于当前成熟度——developer preview 会变，模式不会。

一句话

这六个思想可以归成三类：控制流怎么组织（1、2）、契约划在哪（3、4）、证据怎么留（5、6）。

总纲：自由度分布是一等设计决策

母题。opencode 把脊柱写死、自由度给到边缘扩展点；DSH 把自由度给到每一层，包括 agent loop 本身。这不是成熟度之差，是范式之差。

关键在于怎么让「loop 也是插件」不变成灾难。官方能力表里 ctx.agentLoop 的说明给出了答案：

唯一的具体循环插件；扩展包依赖 dsh-agent 的事件和服务，而不依赖此包。

即：扩展契约挂在抽象服务层，而不是实现包上。 换掉 loop，扩展不会碎。

自检：你的插件化是真货还是表演？看扩展 import 的是接口包还是实现包。如果扩展 import 了具体实现，「可替换」就只是理论上的。

一、可逆副作用：让「换脊柱」在工程上安全

口号谁都会喊，难点是卸载后不留垃圾。Cordis 用两条性质解决：

性质含义
注册即可逆副作用 提示词片段、工具 schema、适配器、监听器全部通过 ctx.effect() / ctx.on() 安装，reload 与 teardown 时按预期撤销
依赖即启动顺序 用 inject 声明所需服务，加载顺序通过服务依赖表达，而非手动编排启动序列。依赖未满足就停在 PENDING，服务方退出时依赖方按序卸载

Fiber 六态生命周期，清理按 LIFO（后注册的清理先执行）：

PENDING → LOADING → ACTIVE / FAILED → UNLOADING → DISPOSED

这两条合起来，才是「一个组件摘掉后进程里不留半激活服务」的保证——agent loop 能以普通插件身份注册，靠的就是这个工程条件。

它不负责什么（同样重要）

disposer 只回收通过 ctx.effect() 注册的进程内资源。注册过什么才清理什么：

  • 文件写了就是写了，业务动作的回滚不归它管
  • 拦恶意代码也不归它管，那是 sandbox 包的事

二、seam / core 的分类纪律

官方把每个服务显式分类，这张表本身就是最好的设计文档。

类型含义例子
seam 有可替换实现 llm、fs、shell、sandbox、storage、session-persistence、subagents、jobs、skills、compaction、approval、codeRuntime
core 单一所有者，无替代实现 sessions、tools、systemPrompt、agentLoop、tokenMeter、invariants、goals、planMode、sandboxPolicy

三种角色，缺一不成缝

任何单一角色都不是 seam。 完整能力才构成其 seam。 

┌─────────────┐     ┌──────────────────┐     ┌──────────────┐
│  dsh-shell  │────▶│  dsh-bash-local  │     │ dsh-tool-bash│
│(definition) │     │    (provider)    │     │(consumer/tool)│
└─────────────┘     └──────────────────┘     └──────────────┘
       ▲                                            │
       └────────────────────────────────────────────┘
                    inject: ['shell']

Provider 和 Consumer 互不依赖，都只依赖 Definition。Definition 拥有 Request/Result 类型。

一条教科书级的设计自觉

ctx.sandboxPolicy 被定为 core，官方说明：

统一保存部署默认模式和工作区根目录……两类强制执行组件都读取该服务，因此 bash 与 fs 不会限制到不同的根目录。

它在防一个非常具体、也非常容易发生的 bug：两条执行路径各自持有沙箱策略，结果围栏宽度不一致。 解法是设立唯一的策略所有者。

不要预防性拆分。 官方明确说：只有角色需要独立演进时才拆成不同包。一个简单的工具插件就写在一个包里。

三、策略与执行分离：工具执行流水线

工具调用的完整链路：

tools/pre-execute    (waterfall)
      ↓
  单调守卫 (monotonic guard)
      ↓
tools/execute        (waterfall)   # 环绕分发可在此加超时/重试
      ↓
tools/post-execute   (waterfall)
      ↓
  finalizeContent    (定义自身控制)
      ↓
tools/result         (观察不可变结果)

核心价值一句话：

钩子便可跨越不同工具系列，而无需让工具与某个策略服务耦合。

对比朴素写法：每个工具自己去问「这个操作允许吗」——策略散落在 N 个工具里，改一次要动 N 处。DSH 让策略挂在水位上，工具完全不知道策略存在。

细节规则
守卫是单调的一旦拒绝，后续监听器无法撤销——防止后注册的插件偷偷放行
审批在守卫之前ctx.approval 先处理询问；但「不得重新排序的所有者策略」仍作为已注册的守卫
三个 waterfall 可改写调用pre / execute / post 各能改一次

Cordis 的五个分发模式

模式await?顺序有返回值?
emit否按注册顺序观察否
waterfall否按注册顺序观察是（环绕中间件）
parallel是所有监听器并行否
serial是按注册顺序是
bail否直到某个监听器返回 bail 值是

分发模式是事件公开约定的一部分——新事件用 @mode 标签记录，生成的目录可以拿声明和调用点做交叉校验。waterfall 接收 (...args, next)：调用 next() 走下游，不调用直接返回＝短路；对单决策事件，短路是设计意图。

四、事件溯源 + 运行时不变量：可审计性做成断言

大多数系统的「可追溯」＝记日志。DSH 多做一步，而且这步是关键：

它在 llm/stream 上挂监听器，对每个即将发出的请求做断言——请求里的 messages 必须与从日志独立折叠出的结果逐字节一致，不一致就报 desync： 

const expected = session.deriveMessages()
if (JSON.stringify(options.messages) !== JSON.stringify(expected)) {
  fail(`llm request ... diverges from the dispatch-time durable derivation`)
}

这把「模型可见即入日志」从口号变成了运行时断言。UI 轨迹、fork 出的会话、事后回放，与模型实际收到的请求共用同一条日志源，漂移会被当场抓住。

日志形态：append-only，每条事件是 { type, seq, time, data } 的信封（seq 会话内单调递增）。

压缩是视图变换，不是数据销毁

  • 日志 append-only，旧事件永不删除
  • compaction 本身是一个新追加的事件，用 SurfaceOp 替换派生历史里的一段区间
  • 被遮蔽的节点必须全部在 sourceEventSeqs 里被引用

所以「模型看到的压缩历史」与「日志里的全量事实」同时存在。

代价与边界（必须知道）

代价：每次生产派发要把全量消息历史序列化两遍，属于热循环上的税。他们选择付这个税换审计性。

边界：这条不变量兜住的是「一致」，不是「正确」。 日志能证明模型看见了什么，不能证明它看见的东西是对的。所以——把日志当观测与归因工具，而不是验收工具；生成物的验收要留在 Harness 之外。

顺带：ctx.invariants 本身也是一个服务——各包在配套子路径注册本包本地的检查，该服务负责选择、唯一性、子 fiber，以及标明所属包的失败。

五、Fail-closed：默认拒绝，而不是默认降级

场景行为
找不到可用沙箱后端抛 SANDBOX_UNAVAILABLE，绝不降级裸跑
审批没有应答方以 unavailable 关闭失败
图片能力未证实初始化时为 false，提示词准入时重查实时路由

最后一条的官方论证特别典型：

「只要 ACP SDK 具有图片块就公布图片支持」——不予采用，因为协议词汇不能证明当前部署可以持久化字节，也不能证明配置的确切路由接受视觉输入。

「结构上有字段」≠「部署上真能做到」。 这个区分很多系统都没做。

并发写入：乐观并发控制

export type FsWriteIntent =
  | { kind: 'createIfAbsent' }
  | { kind: 'replaceIfVersion'; version: FsVersion }

配合 fs-observation-policy 的先读后编辑强制：模型读过文件才能改，读后被外部改过就不能盲写。防的是基于过期读改写、静默覆盖别人的修改——一类很常见的 Agent 事故。

六、PTC / Code Mode：工具面的第二种表示

配置 tools: mode: native | code | both。code 模式下，工具注册表只贡献一个 run_code 入口加一份生成的 TypeScript SDK；直接调其它工具名会得到 UNKNOWN_TOOL。

收益不在「少几次往返」，而在中间状态的存放位置变了：

程序里的中间结果只是 worker 里的局部变量，从头到尾不进对话历史；只有程序跑完后的最终结果回到模型上下文。

对长上下文项目，这是从「每一步的输入输出都在上下文里进出一次」变成「只付最终结果」——从结构上压掉了累积成本（见模型与成本速查）。

治理没有被绕过，且边界写得很明白：

  • 每个 SDK 子调用仍进调度池，仍产生 tool/code-dispatch 事件对
  • 每次运行新建 Node worker thread、空环境变量、堆/输出/时间上限、硬终止
  • 信任等级官方明确声明为「与 bash 等同」——不夸大隔离能力

附带：配置分层与离线审计

1. dsh.profile.bundles 列出的各 bundle patch（按列表顺序，base 在前）
2. profile 自己的 cordis.patch.yml
3. $DSH_HOME/cordis.patch.yml（机器本地共享偏好）
4. 每个 --patch <path> overlay（按 argv 顺序）

后者胜；且 patch 整体替换目标行的 config，不是深度合并。

--dump-config 不启动运行时，用 include 插件自己的 patch 算法离线组合各层，渲染成 YAML 打印退出。意义是：配置审计不依赖「跑起来再观察」，启动前就能拿到全貌。

配套的配置纪律：凡是不同部署可能取不同值的参数，都必须定义成配置字段；配置错误要在加载时响亮失败，不要静默兜底。

如果只记三条

  1. 扩展契约必须挂在抽象服务上，不能挂在实现包上——否则「可替换」是假的。
  2. 给每个能力明确标 seam 还是 core，并想清楚「哪两个组件绝不能各说各话」（如 bash 与 fs 不能各自持有沙箱根目录）。
  3. 可审计性要做成运行时断言，不是日志习惯；同时清楚它只保证一致、不保证正确。

模式 → 防的故障 对照表

模式防的是什么
自由度分布 + 契约挂抽象层换核心时扩展碎掉
可逆副作用 + 依赖即顺序热重载后残留半激活服务
seam / core 分类 + 单一策略所有者两条执行路径围栏宽度不一致
策略与执行分离策略散落在 N 个工具里，改一处要动 N 处
事件溯源 + 运行时不变量UI/回放/实际请求三者漂移
fail-closed安全组件缺失时静默降级成不安全
乐观并发 + 先读后编辑基于过期读改写，覆盖别人的修改
