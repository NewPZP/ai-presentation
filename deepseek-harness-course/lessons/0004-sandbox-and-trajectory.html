第 4 课 · DeepSeek Harness 实战

沙箱、审批与 Trajectory

控制它能做什么 + 追溯它做了什么 · 约 18 分钟

一个让你睡不着的提问

到这里，你已经把 DSH 跑起来、装好插件了。Agent 能读文件、改代码、跑命令——它拿着一个 shell。

那么问题来了：它到底能碰到什么？出了事你怎么知道它干了什么？

这一课回答这两个问题。你会先看清沙箱的真实边界（它比你想的窄），再理解审批为什么不是万能闸门，然后学会用 Trajectory 把 Agent 的每一步摊开来看。

沙箱只围住了「写」

第 2 课里你记住了三档沙箱。现在补上最关键的一列——这个旋钮管不到什么。这是官方 Features 页的原表：

SandboxMode文件效果管不到的地方
read-only 默认兜底档，写入全部拒绝 网络访问 · 进程可见性 · 凭证读取
workspace-write 只允许写会话工作区根目录和后端临时目录
danger-full-access 隔离被绕过，不再有任何隔离承诺

官方原话：默认档下写入被限制在工作区和临时目录，而「读取和网络访问不受限制」。沙箱覆盖的只有文件。

这一条能解释你之前所有的困惑——为什么官方反复强调「凭证不要放进工作区」：因为沙箱拦的是写，不是读。Agent 完全可以读到你放在家目录的 ~/.ssh、~/.aws，也可以发起网络请求把内容送出去。

心智模型修正：把沙箱理解成「防止它改坏你的文件」，而不是「防止它碰到你的东西」。这两个是完全不同的安全目标。

审批到底什么时候弹？

大多数人的直觉是「Agent 每跑一条命令，我都要点一次同意」。不是这样的。

真实的规则是：普通命令一开始就不需要批准；审批只在一条命令请求了比当前会话更大的权限时触发。

这个设计很合理——否则你每十秒就要点一次弹窗，很快就会变成闭眼点「同意」。但它留下了一个致命缝隙：

如果一次调用不「请求」更大权限，而是直接修改会话设置本身，审批就不会触发。

这不是假设。2026 年 8 月，有人真的利用了这个缝隙。

真实事故：CVE-2026-82533

一句话概括：一条 shell 命令，让 Agent 关掉了自己的沙箱，而且没有弹出任何审批。

攻击路径是这样的：

  1. Agent 读到一段攻击者提供的文本（比如一个恶意仓库里的说明文件）
  2. 文本诱导它调用本机 DSH 自己的 Web 接口
  3. 这个接口当时没有任何认证——而且 DSH 已经主动把接口地址和当前会话 ID 交给了 Agent 的 shell，它根本不用去找
  4. Agent 通过接口把会话切成 danger-full-access：沙箱关闭、审批停用

研究人员做了对照实验：同样的默认设置、同样的命令，走过这条路的那次会话成功写到了工作区之外，另一组被正常拦下。该漏洞被评级 9.4 / 10（[The Hacker News 报道](https://thehackernews.com/2026/09/deepseek-harness-flaw-let-ai-agents.html)）。

影响范围与修复版本

版本状态时间
0.1.1-rc.2 及更早受影响0.1.1-rc.2 于 8 月 21 日发布
0.1.2-alpha.1已修复，但只发布在 GitHub8 月 27 日
0.1.2-alpha.2首个带修复的 npm 版本8 月 30 日
0.1.2-rc.1当前 npm 版，已含修复9 月 3 日

修复方式：本机 Web 接口启动时打印一个一次性 token，浏览器用它换一个签名 cookie，之后每次调用接口都必须带这个 cookie——接口终于有了身份校验。

但修复的只是接口认证，不是沙箱。 在 0.1.2-rc.1 里，「读取和网络访问不受限制」这条依然成立，Agent 的 shell 依然拿得到接口地址。别把这次修复理解成「沙箱变安全了」。

三条不能忘的教训

  1. 沙箱和审批是「降险」，不是「安全边界」。 官方自己的安全声明写着：软件未经安全审计，沙箱、审批和权限预设「不保证隔离」。
  2. 在可丢弃的环境里跑。 用一次性目录、一次性容器，别把真实凭证、真实项目、真实密钥放进它的活动范围。
  3. 确认你的版本。 你的 Web UI 跑在 0.1.2-rc.1（含修复）。如果你用了第三方桌面版，要查它内置的 harness 是哪个版本——那是封装作者的锁版本，不是官方的。

Trajectory：把每一步摊开来看

既然边界靠不住，那「事前拦住」就不够了，你还需要事后看清。这就是 Trajectory。

DSH 把模型看到的一切都记进一份仅追加（append-only）的会话日志：系统提示、推理过程、每一次工具调用与结果、子代理调度、每一次上下文注入。Trajectory 就是按来源检视这份记录的界面——resume、fork、search、replay 全都基于同一条流。

0.1.2-rc.1 还给 Trajectory 补了两个实用信息：用户/助手/工具结果里的图片，以及每次回答结束后的 token 用量与耗时。

日志在磁盘上的形态是 session.jsonl.zstd——zstd 压缩的 JSONL，一行一个事件。事件类型（turn/start、step/end、tool/call、tool/result 等）我在Cordis 术语表里已经列全了。

轨迹的三个用法

用途看什么解决什么问题
复盘调试 工具报错在时间线上的确切位置 「它为什么突然改错文件了？」
成本归因 每一轮的 token 用量与耗时 「这一下午的钱烧在哪一步？」
交付审计 完整回合时间线 + 元数据 「把过程发给别人复核」

怎么读一次轨迹

别被事件流吓到。抓住这个层级就行：一个 turn（回合）里包含若干 step（步），一个 step = 一次模型调用 + 它发起的工具执行。 

turn/start
 ├─ step/start
 │   ├─ assistant/message      # 模型决定要干什么
 │   ├─ tool/call              # 调了哪个工具、参数是什么
 │   └─ tool/result            # 结果，或者 error
 └─ turn/end                   # reason: completed / blocked / error / ...

排查时优先看两处：带 error 的 tool/result（哪一步失败的），以及 turn/end 的 reason（这一回合是正常完成，还是被拦、报错、超 token）。

看轨迹的两个工具

  • 内置 Trajectory 视图（首选）：Web UI 里聊天区旁边的 Chat / Trajectory 两个 tab，直接点开就能看。
  • 导出成可分享的 HTML：dsh-trajectory 把会话日志渲染成一份自包含的 HTML（内联样式、零依赖），附带 SHA-256，适合发给别人复核。
# 把一份会话日志导出成可分享的 HTML 报告
npx --yes github:ciceroyang/dsh-trajectory#v0.4.2 ./session.jsonl.zstd --out report.html

进阶：dsh-replay 是时间旅行调试器，可以对一份 session.jsonl.zstd 做 replay / visualize / diff——等你要精修 Agent 行为时再回头看它。

动动手

本课实操任务：

  1. 在工作区里让 Agent 做一个多步任务：读一个文件 → 改一处 → 跑一条命令
  2. 打开 Trajectory tab，在时间线上找到那次 shell 调用，看它的参数和结果
  3. 看这一轮结束后的 token 用量与耗时——这就是「成本归因」的入口
  4. 故意制造一次失败：让它跑一条会报错的命令，观察 tool/result 的 error 和 turn/end 的 reason 怎么记录
  5. 把这次轨迹导出成 HTML，或者截图关键那几步，贴给我

看不懂某个事件、或者轨迹里出现了你没预期的调用，直接发我——这正是最该一起看的东西。

本节课的小测验

检验一下理解

关于默认的 workspace-write 沙箱，下列说法正确的是？

  • 只限制写入不限制读取与联网
  • 限制写入同时也限制读取联网
  • 只限制读取不限制写入与联网
  • 限制联网但不限制读取与写入

检验一下理解

审批提示（approval）通常在什么时候才会出现？

  • 命令请求超出会话现有权限时
  • 每条命令执行之前都会弹一次
  • 模型每次调用工具都会弹一次
  • 会话刚启动的时候统一弹一次
