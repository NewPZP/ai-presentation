第 3 课 · DeepSeek Harness 实战

装上你的第一批插件

生态入口 + 视觉 + 文件引用 · 约 15 分钟

上节课，你住进了毛坯房

在第 2 课里，你用 Standard 模式 + workspace-write 沙箱把 DSH 跑起来了，还让 Agent 建了一个 hello.md。

现在你手上的是一个毛坯房：极简聊天框 + 内置工具。它已经能干活，但有几个明显的缺：

  • 模型看不懂图片——你贴一张报错截图，它只能干瞪眼
  • 引用一个文件，得手动复制粘贴整段内容进聊天框
  • 想装社区插件，得手敲 npm 包名，还记不住版本号
  • 界面就是一根孤零零的聊天框，没有文件树、没有看板

这一课，你要用插件把毛坯房装成能住的屋子。记住第 1 课那句话：DSH 里一切皆插件，拼装而不是重造。

先装市场：dsh-market 是生态入口

别的插件可以先不装，但市场必须第一个装。dsh-market 就像手机上的 App Store——装好它之后，你才能在设置界面里一键搜索、安装、卸载社区插件，还能备份和还原你的插件配置。

没有市场，每装一个插件都要去记它的 npm 包名、GitHub 地址、版本号。有了市场，搜一下、点一下，搞定。

安装命令：

# 安装插件市场（装在 web profile 下）
dsh plugin --profile web add dshmarket

# 重启让市场生效
dsh web

profile 是什么？ DSH 支持多套配置档案（profile）。web 就是你在第 2 课用的那套 Web UI 配置。所有插件都装到某个 profile 下，互不干扰。

装完重启后，打开设置面板，你应该能看到一个「Market / 插件市场」的入口。看到它，就说明市场装成功了。

modlens：给模型装上眼睛

你现在用的模型大概率是纯文本的（DeepSeek 默认模型不接收图片）。这意味着表格截图、论文图表、报错弹窗，它一概看不见。

modlens 解决的就是这个：你粘贴一张图片，它先做 OCR 文字识别 + 版面分析，把图转成结构化的文字再喂给模型。等于给纯文本模型装了一双眼睛。 

# 通过 npm 装，注意 pin 住版本号（插件作者可能频繁改 API）
dsh plugin --profile web add @liustack/modlens@3.25.2

为什么要 pin 版本（@3.25.2）？ 社区插件没有 DSH 官方那样的发布纪律，新版本可能改行为、改接口。把版本号钉死，能避免「昨天还好好的，今天突然失效」。这也呼应第 2 课「锁定版本」的最佳实践。

装好后，聊天输入框附近会出现上传/粘贴图片的入口。试试把一张报错截图贴进去，看模型能不能「读」出里面的文字。

dsh-at-file：@ 一下，文件就进上下文

想让模型读一个本地文件，以前你得：找到文件 → 复制内容 → 粘到聊天框 → 再说明「这是 xx 文件」。又慢又容易出错。

dsh-at-file 让你直接在输入框打 @，弹出模糊搜索，回车就引用那个文件进上下文，不用复制粘贴。 

# 这个插件发布在 GitHub，用 tarball 地址安装
dsh plugin --profile web add https://github.com/omdsh-dev/dsh-at-file/archive/refs/tags/v0.6.8.tar.gz

装好后，在输入框敲 @ 试试——应该会弹出本地文件列表。这就是「快速引用」：让模型看到的文件越多、越准，它干的活就越靠谱。

界面增强：二选一，别都装

默认聊天框太素了。社区有两款成熟的界面插件，都能把它升级成「控制台」，但只需要装一个：

插件长什么样适合谁
dsh-web-ui 任务看板、Git 图谱、Token 实时统计、桌面宠物 想要「全功能控制台」、喜欢丰富可视化
DSH-better-sidebar VS Code 风格侧边栏：文件树、真实终端、子代理状态 熟悉 VS Code、想要轻量的「工作台」 
# 方案 A：全功能控制台
dsh plugin --profile web add @linxin666/dsh-web-all@latest

# 方案 B：VS Code 风格侧边栏
dsh plugin --profile web add dsh-better-sidebar@latest

原则上选一个。 两者都占用同一个「右侧面板」位置。新版 DSH-better-sidebar（v0.13.0+）已经内置互斥退让：你在设置里选了 dsh-web-ui 的面板，它就自动不挂载，反过来也一样。所以装两个不会崩、也不会真打架，但同一时刻只有一个面板生效——装两个只是浪费资源、增加故障面。先选一个，用着不爽再换。

装 dsh-better-sidebar 时如果失败，常见原因是它依赖的原生模块没通过构建审查。解决： 

# 手动放行构建脚本后重装
cd ~/.dsh/profiles/web && pnpm approve-builds --all

另一条路：dsh-desktop（桌面客户端）

上面两个是界面插件——装在 Web UI 里，你还是得自己开浏览器、开着终端。桌面客户端是另一层的东西：把整个 Web UI 装进一个原生外壳，双击即用、不用自己管 Node。

两者不冲突。 桌面壳内部跑的就是那个 Web UI，界面插件照常在它里面加载。DSH Desktop 甚至内置了插件市场，管理的就是本课这批插件。

社区版本很多，先按平台和许可筛

官方初期没出桌面端，社区就冒出一堆第三方封装。看着都差不多，但平台支持和许可证差别很大——你在 macOS 上、又打算做产品，这两条就能筛掉大半：

版本平台关键事实
官方桌面端 macOS（Apple Silicon + Intel）· Windows x64 即将发布，暂无成品下载；apps/desktop 已在官方主分支
anywhere-labs/dsh-desktop
DSH Desktop		 macOS Universal · Windows x64 社区采用最广（约 2.85 万 ★ / 1350 fork）；纯 MIT，可商用；Electron，macOS 包约 304MB
dsh-tauri Windows / macOS / Linux Tauri 2，macOS 包仅约 10MB、内存占用低；但许可是 MIT 附加非商用条款
Links2008 / ningbainb 等 Windows only 功能不少（内置插件商店、SSH、主题），但 macOS 用不了

star 数该怎么读？ 它衡量的是采用度，不是质量，更不是「适合你」。这次真正决定选谁的是另外四项：平台（macOS 能不能装）、许可证（能不能商用）、维护时效（最近还有没有提交）、它固定的上游内核版本（安全）。star 数只帮你判断「踩坑的人多不多、答案好不好找」——在这一点上它确实有用。

我的推荐（针对你的 macOS）：

  • 首选 → anywhere-labs/dsh-desktop（DSH Desktop）。macOS Universal 安装包（Intel / Apple Silicon 都覆盖），纯 MIT 许可——这一条对你「做产品」的目标是关键，因为好几个社区桌面版的许可里带非商用条款，不能直接进要卖的东西。它还固定上游 v0.1.5-rc.2（远在 CVE 修复线之上），并复用你已有的 ~/.dsh，会话和设置是通的。
  • 想要轻量 → dsh-tauri。Tauri 2 外壳，macOS 包只约 10MB（对比上者的 304MB），内存占用明显更低。代价是许可带非商用条款——自己玩没问题，商用要谨慎。
  • 长期正解 → 等官方。官方桌面端支持 mac 的 Apple Silicon 和 Intel，还有两个架构上的实在优势：不走本地端口，改用自定义 dsh-app:// 协议传数据（比第三方暴露 127.0.0.1:3080 更安全）；与运行时、后端整体打包，版本维护一致，不容易出「外壳和内核版本对不上」的 bug。发布后应该在 download.deepseek.com。

装任何第三方桌面壳之前，务必确认两件事：

  1. 它内置的 harness 是哪个版本。 桌面壳自带一份内核，版本由封装作者决定，不等于官方最新。这正是第 4 课 CVE-2026-82533 的教训——装之前查版本，确保在 0.1.2-rc.1 之上。查法：翻它的 Release Notes，通常写明了固定的上游版本（已核实：DSH Desktop v2.0.13 固定 v0.1.5-rc.2；dsh-tauri 要求 0.1.5-rc.1+，都过关）。
  2. 它的许可证里有没有额外条款。 别只看 GitHub 上那个 "MIT" 徽章——dsh-tauri 的仓库同为 MIT，但 README 里另有非商用条款。你的目标是做产品，这一条决定你能不能用它。

怎么确认插件「真的生效」？

装了不等于能用。判断一个插件是否真正加载成功，看三个层次的证据（来自社区插件开发实测的验收思路）：

证据层次看哪里说明
1 · 加载证据 启动日志 启动时终端打印出插件名，说明它被 Loader 挂载了
2 · UI 入口 界面 出现了市场面板 / 图片按钮 / @ 引用弹窗
3 · 真实调用 让模型做一次 让模型真的「读截图」「引用文件」，看它有没有用上这个能力

第三层才是硬证据。插件列表里出现名字 ≠ 模型会用。只有模型真的调起了它，你才算装成功了。

装插件的安全红线

插件不是「设置」，是能读写你文件系统、执行命令的代码。装一个来路不明的插件，等于把它请进你的工作区。

  1. 只装知名、有 star、有维护的插件，先看 GitHub 仓库再装
  2. 装之前审查它要哪些权限，别闭眼点同意
  3. 牢记第 2 课的沙箱：插件在你的 workspace-write 范围内活动，别为装插件去开 danger-full-access

动动手

本课实操任务：

  1. 安装 dsh-market，重启后在设置里找到「市场」入口
  2. 通过市场（或上面的命令）装 modlens 和 dsh-at-file
  3. 界面插件二选一：dsh-web-ui 或 DSH-better-sidebar
  4. 做一次「真实调用」验证：贴一张截图让模型读文字，或 @ 引用一个文件让模型总结它
  5. 把启动日志里看到的插件名，和模型实际调用的结果，一起贴给我

装不动了、或者不确定某个插件该不该装，随时把报错和仓库地址发我。

检验一下理解

「先装市场」这条起步策略的首要原因是？

  • 市场可一键搜索安装插件
  • 市场能提供图片识别能力
  • 市场能引用本地文件内容
  • 市场可让聊天界面更好看

装完插件后，判断它「真正生效」的最可靠证据是？

  • 启动日志里出现插件名
  • 界面菜单里出现新入口
  • 让模型实际调用它一次
  • 插件仓库的收藏数很高
