写你的第一个 Tool 插件

从 apply(ctx) 到模型真的调用它 · 约 20 分钟

今天你从「用」变成「造」

第 3 课你装了别人的插件，第 1 课你记住了「一切皆插件」。现在兑现那句话：自己写一个。

目标是给模型一个它原本没有的能力——一个由你定义的工具。你要走完这四步，一步都不能跳：

  1. 写一个插件的骨架（就是一个 apply 函数）
  2. 用 defineTool 注册一个工具
  3. 把它加载进 DSH，让模型看见它
  4. 用 第 4 课的 Trajectory 验证它真的被调用了

一个插件，就是一个 apply 函数

这可能是整门课最反直觉的一句话：在 Harness 里，插件的全部契约就是导出一个 name 和一个 apply 函数。框架加载时调用 apply，把 ctx（上下文对象）递给你，你通过它注册能力。 

// 这就是一个完整的插件
import type { Context } from '@deepseek-ai/cordis'

export const name = 'my-plugin'

export function apply(ctx: Context) {
  // 在这里注册能力
}

没有基类要继承，没有生命周期方法要重写。你注册什么，就得到什么；插件卸载时，通过 ctx 注册的一切（工具、事件监听、定时器）会自动清理——这就是术语表里说的「零泄漏生命周期」。

需要手动清理的资源（比如一个网络连接）才用 ctx.effect()：传入一个函数，返回一个清理函数，卸载时框架替你调用它。

第二步：声明你依赖什么

工具注册表是一个服务（tools）。你要用它，就得声明依赖： 

export const name = 'greet-tool'
export const inject = ['tools']   // 声明：我需要 tools 服务

这一行的作用是：Cordis 会等 tools 服务就绪后，才调用你的 apply。这样你在 apply 里写 ctx.tools.register(...) 时，注册表一定已经存在了。

为什么不能省？ 插件的加载顺序不是你能保证的。没有 inject，你的插件可能在工具注册表就绪之前执行，然后因为 ctx.tools 是 undefined 而崩掉。声明依赖 = 让框架替你排队。

第三步：defineTool —— 告诉模型「有这么个工具」

把 my-plugin.ts 的内容换成下面这段。这是本课的核心，请逐行读： 

import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'greet-tool'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'greet',
    description: 'Greet someone by name.',        // 模型看到的就是这句
    parameters: {
      name: { type: 'string', required: true, description: '要问候的名字' },
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args) {
      return `Hello, ${args.name}!`          // 返回「规范值」
    },
  }))
}

四个字段，各有明确的分工：

字段作用关键点
name / description 模型决定要不要调用你的依据 这就是提示词工程——描述写不清，模型就不会用
parameters 声明参数结构 defineTool 会据此自动校验模型生成的参数，并把类型推给 execute
output.schema 声明返回值的规范类型 返回结构化值，而不是拼好的字符串
output.render 把规范值转成模型可见的内容 负责「给人/模型看的自然语言」

留意 execute(args) 里的 args：它的类型是从 parameters 推导出来的。你不用自己解析 JSON，模型传进来的参数已经被校验并填好类型了。

第四步：加载它（patch 覆盖层）

插件写好了，怎么让 DSH 认识它？官方教程用一个覆盖层文件。在仓库根目录建 scratch-plugin/cordis.yml： 

- insert:
    - id: greet
      name: '/absolute/path/to/deepseek-harness/scratch-plugin/src/my-plugin.ts'

路径必须是绝对路径。 patch 文件只贡献配置，它不会改变 loader 解析模块路径时用的基准目录——写相对路径会找不到文件。

用这个覆盖层启动：

# 官方教程路线：在 deepseek-harness 仓库 checkout 里运行
pnpm dsh web --patch ./scratch-plugin/cordis.yml

为什么官方教程要求源码 checkout？ 因为 defineTool 来自 @deepseek-ai/dsh-tools，TypeScript 的类型也从工作区解析。你前几课用的 npx 安装版适合用插件；写插件时，按官方教程克隆仓库（git clone + pnpm install）是最稳的路径。写完之后要装进你日常那个 DSH，走本节最后的「打包」。

验证它真的生效：还是那三层证据

第 3 课我们用「三层证据」判断一个插件有没有真正生效。这次你写的是自己的插件，照样套：

证据怎么看
1 · 加载了 在 apply 里写一句 console.log('[greet-tool] loaded')，启动时终端应打印出来
2 · 工具进表了 工具的 schema 会自动流入系统提示词的组装过程——模型「看得见」它
3 · 真的被调用了 输入 Use the greet tool to greet Ada.，模型调用后返回 Hello, Ada!

第三层才是最硬的证据，而且这次你有了第 4 课的武器：打开 Trajectory，你应该能看到一次 tool/call（name 是 greet、参数是 {"name":"Ada"}）和对应的 tool/result。看不到这两条事件，就说明你的工具没真正跑起来——这正是第 4 课教的读法。

第 3 课的验收思路、第 4 课的 Trajectory、这一课的插件——三课在这里合上了。以后每写一个工具，都走这条验证链。

execute 的三条硬规则

工具能跑起来之后，这四条约定决定了它「生产可用」还是「玩具」（来自官方工具编写参考）：

  1. 参数已替你校验，但业务约束要自己查。 defineTool 会校验类型、必填键、字面量、联合类型和嵌套值。但「非空字符串」「必须是正数」「A 字段和 B 字段不能同时出现」这类规则它管不了，得你在 execute 里手动检查。
  2. 返回「规范值」，不要返回内容块。 execute 只返回 output.schema 声明的那个值；转成自然语言是 output.render 的事。这样 PTC 模式下模型才能以编程方式拿到结构化结果，而不是去解析一段文字。
  3. 抛异常 = isError。 基础设施故障就抛异常，注册表会捕获。但业务上的「不理想结果」不该抛异常——比如命令以非零状态退出，那是个合法的领域结果，写进规范值让渲染器去解释。
  4. 遵守 exec.signal。 信号触发时，取消你正在进行的工作。长任务不要无视它。

让它可配置：官方的一条设计原则

硬编码的问候语只配当教学示例。Harness 有一条明确约定：

凡是不同部署可能需要取不同值的参数，都必须定义成配置字段。 检验标准是：能不能在 cordis.yml 里改掉它，而不用动代码？

做法是导出一个 Config 类型和同名的 schema，默认值写在 schema 里：

import Schema from '@deepseek-ai/schemastery'

export interface Config {
  greeting: string
}

export const Config: Schema<Config> = Schema.object({
  greeting: Schema.string().default('Hello'),
})

export function apply(ctx: Context, config: Config) {
  // config.greeting 已被 schema 校验、并填好默认值
}

然后在 cordis.yml 里传值：

- insert:
    - id: greet
      name: '/absolute/path/.../my-plugin.ts'
      config:
        greeting: '你好'

配置写错要响亮地失败。 schema 在插件加载时校验，配置不合法就让插件加载失败并给出明确错误——不要静默用默认值兜底，那样你会在几小时后才发现配错了。顺带一提：改 config 会触发插件热替换（卸载旧实例、加载新实例），因为注册都是 effect，不会残留旧注册。

从本地脚本到可安装插件

--patch 适合开发。要让插件进到你日常那个 DSH（比如 npx 装的那个），得把它打包成组合包（bundle）。两个概念，别再混：

概念回答什么问题manifest
组合包 bundle 「这个包贡献什么？」——一份配置补丁 dsh.bundle
profile 「这套配置由哪些包按什么顺序组成？」 dsh.profile 
// package.json：声明你是一个组合包
{
  "name": "dsh-hello-plugin",
  "type": "module",
  "main": "index.js",
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
# 安装进 profile，然后先验证再启动
dsh plugin --profile web add ./hello-plugin
dsh --profile web --dump-config   # 应能看到 "# == dsh-hello-plugin" 这一层

从 GitHub 装的坑（务必知道）： dsh plugin add github:you/hello-plugin 拉的是源码，不是构建产物——没有任何环节运行你的 build，TypeScript 包到手时没有 lib/，加载会失败。作者要提供 prepare 脚本，用户要显式授权构建（pnpm ≥10 默认拦截），把包键写进该 profile 的 pnpm-workspace.yaml 的 allowBuilds。请把这项授权理解为「允许该包的代码在安装时于你机器上执行，且不在任何沙箱之内」——只对源码可信的包授权，并锁死 commit。更省事的做法是直接分发构建产物：发到 npm，或 pnpm pack 出 tarball 再装。

完整的打包步骤、四层加载顺序、以及「patch 会整体替换 config 而不是深度合并」这些细节，我整理在本课的Tool 插件开发速查表里。

动动手

本课实操任务：

  1. 克隆 deepseek-harness 仓库，pnpm install，建好 scratch-plugin/
  2. 写上面的 greet 工具，用 --patch 启动，确认终端打印了加载日志
  3. 输入 Use the greet tool to greet Ada.，拿到 Hello, Ada!
  4. 打开 Trajectory，找到 greet 的 tool/call 和 tool/result——截图给我
  5. 把问候语改成可配置的 Config，在 cordis.yml 里改成中文，确认热替换生效

卡在哪一步、或者 Trajectory 里出现了意外事件，把代码和截图发我，我们一起看。

本节课的小测验

检验一下理解

为什么插件要声明 inject = ['tools']？

  • 让框架等工具服务就绪再加载
  • 让框架在卸载时自动清理工具
  • 让模型优先调用本插件的工具
  • 让插件可以读取用户的配置文件

检验一下理解

官方对「可调参数」的设计原则是？

  • 一律定义成配置字段
  • 一律硬编码进代码里
  • 一律写在注释说明里
  • 一律让模型自行决定
