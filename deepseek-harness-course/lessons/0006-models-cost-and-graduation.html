模型、成本与毕业

换模型、看懂账本、把它用下去 · 约 20 分钟

最后一课，解决「跑得久、跑得起」

前五课你已经能：跑起 DSH、装插件、看懂沙箱与轨迹、写出自己的工具。但这些都还只是「它能干活」。真正决定它能不能长期为你所用的，是两件很现实的事：

  • 模型能不能换——换供应商、换档位，别被一家锁死
  • 钱花在哪、怎么少花——Agent 是会持续烧钱的

这一课讲完这两件，再把六课串成一套能天天用的工作流，然后送你出门。

换模型：在 DSH 里为什么很便宜

回到第 1 课那句话：模型适配器也是插件。所以「换模型」在 DSH 里有三个层次，成本递增：

层次怎么做适合
换配置 Settings → Models 里改供应商和模型 已经支持的供应商，99% 的情况
换 provider 在 cordis.yml 里改 provider / model 按任务分派不同模型
写适配器 继承 LlmAdapter、实现 stream() 供应商还没有适配器

第三层才是「写代码」，而且模板很小——核心就是把 Harness 的请求转成供应商 API、再把响应转回分片： 

import { LlmAdapter, type GenerateOptions, type StreamChunk } from '@deepseek-ai/dsh-llm'

class MyAdapter extends LlmAdapter {
  async *stream(options: GenerateOptions): AsyncIterable<StreamChunk> {
    // 1. 把 options.messages 转成供应商格式
    // 2. 调流式 API
    // 3. 把响应转成 StreamChunk 分片
  }
}

export const name = 'my-llm-adapter'
export const inject = ['llm']

export function apply(ctx: Context, config: Config) {
  ctx.llm.registerAdapter(config.providers, new MyAdapter(config.apiKey))
}

然后在 cordis.yml 里把 provider 和 model 接上：

- id: my-llm
  name: './src/my-llm-adapter.ts'
  config:
    apiKey: !!js process.env.MY_API_KEY      # 从环境变量读，别写死
    providers: [my-provider]

- id: agent-loop
  name: '@deepseek-ai/dsh-agent-loop'
  config:
    agents:
      - id: main
        provider: my-provider
        model: my-model-v1

别从零写。 官方仓库里有两个可直接对照的完整实现：llm-deepseek（OpenAI 兼容格式）和 llm-pi-ai（另一种格式）。绝大多数国产模型都走 OpenAI 兼容协议——照着 llm-deepseek 改 endpoint 和 model id 就能跑。注意：适配器遇到传输/协议故障要抛带稳定 code 的 LlmError，并透传 options.signal，别用普通 Error。

看懂成本：token 账本里的两个数字

从 0.1.2-rc.1 起，每次回答结束后会直接显示 token 用量和耗时。但「用量」其实有两个口径，分清它们是你控制成本的前提：

数字含义
totalTokens 这一次调用的请求 + 响应压力
surfaceTokens 当前「表层」（上下文里所有节点）的路由定价总量，等于各节点价格之和

最关键的一句话：每一次模型调用，都要把整个 surface 重新发一遍。 所以上下文越长，不是贵一次，而是之后每一步都更贵。上下文成本是累积的。

这解释了一个常见困惑：为什么你只是多聊了几轮，账单却涨得比预期快。因为你每多留一段无关内容在上下文里，它都会在后续每一次调用中重复计费。

另一个要知道的细节：计量里的 baseline 分两种——usage 表示最近一次成功的供应商调用有相同的请求结构，用的是真实 usage（准）；estimated 表示没有可复用的锚点，服务自己按启发式估算（仅供方向参考）。

省钱的四个动作

  1. 控制 surface，而不是控制回复。 省钱的主战场是上下文：任务做完就开新会话，别在一个会话里堆一整天的活；长任务靠压缩上下文而不是硬扛。
  2. 按任务选模型。 粗活（改格式、写样板、批量重命名）用便宜快的模型；难活（架构设计、疑难调试）才上强模型。用 cordis.yml 里的 provider/model 分派。
  3. 利用峰谷定价。 DeepSeek 有高峰/闲时两档费率（闲时半价）。把可延迟的批量任务挪到闲时跑——社区插件 dsh-peak-indicator 会在会话头部用徽标显示当前档期（⚡高峰 / 🌙闲时）和距下次切换的倒计时。
  4. 装个成本看板。 实时看会话花费和当日预算，比月底看账单才发现超支好得多（第 3 课速查表里的 dsh-cost-meter）。

排查「钱到底烧在哪一步」，就回到第 4 课的 Trajectory：每一轮的 token 用量都在时间线上，归因到具体某次工具调用。

官方最佳实践：五条

来自官方 Guides，每条都值得贴在你工作区旁边：

  1. 在空的可丢弃目录里开始，不要选家目录或客户的 monorepo。
  2. 保持 workspace-write + ask，不要一上来就 danger-full-access。
  3. 锁定版本。 不带版本号的 npx 跟随 latest。
  4. 审查插件、MCP 服务器、Skills、Hooks再让它们执行。
  5. 凭证不要放进工作区——沙箱限制的是写，不是读（第 4 课的核心）。

一条架构最佳实践：能力的三层拆分

这是 DSH 自己组织代码的方式，也是最值得你抄走的架构习惯。当一项能力需要支持可替换的提供方时，官方把它拆成三种角色： 

┌─────────────┐     ┌──────────────────┐     ┌──────────────┐
│  dsh-shell  │────▶│  dsh-bash-local  │     │ dsh-tool-bash│
│ (definition)│     │    (provider)    │     │(consumer/tool)│
└─────────────┘     └──────────────────┘     └──────────────┘
       ▲                                            │
       └────────────────────────────────────────────┘
                    inject: ['shell']
角色负责Bash 例子
Service Definition定义服务接口 + 请求/结果类型dsh-shell
Service Provider真正执行dsh-bash-local（本地执行）
Consumer把它暴露成模型可调用的工具dsh-tool-bash

好处是：换提供方时，Definition 和工具都不用动——只换 cordis.yml 里那一行。这也正好是你 mission 里「可扩展」的具体含义。

但不要预防性拆分。 官方明确说了：只有角色需要独立演进时才拆成不同包。一个简单的工具插件就写在一个包里，别为了「架构好看」拆出三个空壳。另一条：显式优于隐式——默认值用显式的 resolve(request) 处理，不要在 run() 里藏一个 ?? default。

最后一步：去社区

这门课能给你知识和技能，但智慧只能从真实使用和别人身上来。你现在最该做的不是再学一课，而是拿一个真实的小项目去用它，然后把遇到的问题带回来。

  • GitHub Discussions — 官方问答区。踩坑、版本问题、插件开发，先在这里搜，再提问。
  • GitHub dsh-plugin topic — 社区插件索引，发现新插件。
  • 把你写的第一个插件开源出去——这是检验你是否真的学会了最快的方式。

DSH 仍是 Developer Preview，API 和版本都还会变。你手上这几份速查表就是为这个准备的：过几个月回来对一下，比重新读一遍文档快得多。
