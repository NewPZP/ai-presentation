踩坑与调试：用反馈回路把 bug 逼到死角

预计 15 分钟 · 基于真实 SKILL.md（diagnosing-bugs）+ 本工程真实 bug · 目标：遇到 bug 时不再「盯着代码猜」，而是先建一条会红的回路

这节课的终点

实现循环不是永远一帆风顺。当测试红了却不知道为什么、当 Agent 改了 A 坏了 B，diagnosing-bugs skill 提供一套反直觉但极其有效的调试纪律。

一句话记住

建一条会红的回路，bug 就修好了 90%。盯着代码猜是最没用的事——先有一条「能复现这个 bug、几秒跑完、可无人值守」的命令，再谈假设。

diagnosing-bugs 的六阶段

阶段做什么
1. 建反馈回路造一个能复现 bug 的命令（测试/curl/脚本），红、快、确定、可无人值守
2. 复现 + 最小化确认它复现的是用户说的那个 bug，然后砍到最小
3. 提假设列 3–5 个可证伪的假设，排好序再测
4. 探针验证一次改一个变量，用日志/调试器验证预测
5. 修复 + 回归测试先写回归测试再修；没有合适的 seam 本身就是发现
6. 清理 + 复盘删调试日志、删临时原型、在 commit 里写清真正原因

Phase 1 是整个 skill 的灵魂

skill 原文：「This is the skill. Everything else is mechanical.」

反馈回路的构造方式（按优先级）：失败测试 → curl/HTTP 脚本 → CLI + 快照 diff → 无头浏览器脚本 → 重放捕获的 trace → 临时 harness → fuzz/property → git bisect → 差异对比 → 最后才是人肉点击。

没有红能力的命令，不许进 Phase 2。如果忍不住开始读代码建假设，停下来——这正是这个 skill 要防止的失败模式。

回路造好后还要收紧：更快、信号更锐（断言具体症状而非「没崩」）、更确定（固定时间/种子/网络）。一个 30 秒的 flaky 回路几乎等于没有；一个 2 秒的确定性回路是调试超能力。

本工程真实踩过的坑

坑一：浏览器 CORS 拦截 AI 接口

现象：从 localhost 直接调 OpenAI 兼容接口被浏览器 CORS 策略拦死。

回路：一条 curl 命令直连接口 200，但浏览器 fetch 报 CORS——差异本身就是诊断线索。

根因：浏览器同源策略，不是接口问题。

修复：开发模式走 Vite dev server proxy（/dev-proxy），由服务端转发请求绕过 CORS。这条教训进了项目记忆，后续所有 AI 调用都遵守。

坑二：火山 TTS 资源 ID 格式

现象：TTS 接口返回错误，但 HTTP 状态是 200+ 的 JSON 错误体。

回路：用最短文本「Hi.」做端到端最小验证（火山没有 /models 端点可探测）。

根因：资源 ID 必须用 volc.seedicl.default 格式，不是模型名 seed-icl-2.0。

修复：适配器里硬编码正确格式；错误处理覆盖 200+ JSON error 类型；文本按 500 字符切块请求。

坑三：工厂函数引用不稳定导致 effect 反复执行

现象：音频播放/测验生成的 effect 在每次渲染都重新触发，状态错乱。

回路：页面级测试里观察到 effect 调用次数异常。

根因：createAudio、测验生成等工厂函数每次渲染返回新引用，作为 effect 依赖导致重复执行。

修复：用 useMemo 稳定工厂引用。这条也进了项目记忆。

坑四：mock 时间线与真实 TTS 时长冲突

现象：mock 句子时间线固定 51 秒，但真实 TTS 短文本只有 ~2 秒，播放定位全错。

修复：fitSentencesToDuration 把时间线按真实 TTS 时长等比缩放。

这些坑的共同点

它们都不是靠「盯着代码想」解决的，而是靠一条具体的反馈回路（curl 差异、端到端最小验证、effect 计数测试）把根因逼出来的。这就是 diagnosing-bugs 的核心：用回路代替猜测。

把教训沉淀进项目记忆

本工程的一个关键习惯：每修好一个坑，就把「现象 → 根因 → 修复」记进项目记忆。后续会话开头 Agent 会自动加载这些记忆，同样的坑不会踩第二次。

项目记忆里的硬约束（节选）：

  • 开发环境必须用 Vite proxy /dev-proxy 绕过 CORS
  • 火山 TTS 资源 ID 用 volc.seedicl.default
  • 工厂函数引用用 useMemo 稳定
  • 所有 middleware 用 async/await，不用 callback
