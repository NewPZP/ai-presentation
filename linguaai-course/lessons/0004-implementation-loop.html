实现循环：从一张工单到一次干净的提交

预计 15 分钟 · 基于真实 SKILL.md（implement / tdd / code-review）· 目标：跑通「读工单 → 测试先行 → 实现 → 审查 → 提交」的完整循环

这节课的终点

第 2 课结束时你有了一张 ready-for-agent 的工单。这节课结束时，它会变成 一次已提交、已审查、测试全绿的 git commit。

工单（ready-for-agent）
   ↓ implement
   ├─ 读工单 + 确认 seams（测试边界）
   ├─ /tdd：红 → 绿，一个垂直切片一个切片地推进
   ├─ 定期类型检查 + 单测
   ├─ 收尾跑全量测试
   ├─ /code-review：双轴审查（Standards + Spec）
   └─ 提交
结果：一次干净的 commit，工单可关闭
一句话记住实现循环

先写会失败的测试，再写刚好让它通过的代码，最后让一个独立的审查者挑刺。「红→绿→审查」三步，比「想到啥写啥」可靠得多。

implement：循环的指挥者

implement 本身很短——它不写代码，它只编排循环：

  1. 读 spec 或工单
  2. 用 /tdd 在事先约定的 seams 上测试先行
  3. 定期跑类型检查、单文件测试
  4. 收尾跑一次全量测试
  5. 用 /code-review 审查
  6. 提交

它的价值不在「能写代码」，而在强制按节奏走：测试不先写就不许实现、不审查就不许提交。这正是「管理初级工程师」的体现——你给它 SOP，它按 SOP 执行。

tdd：红 → 绿，一次一个垂直切片

Seam：先约定测试边界

TDD 的第一步不是写测试，而是先和你确认 seam（接缝）——也就是「在哪个公共接口上测」。

为什么 seam 要先确认

测试只该打在公共边界上，不该伸进内部实现。如果不先约定 seam，Agent 可能去测私有方法、mock 内部协作者——这种测试一重构就碎，等于白写。所以 tdd skill 的第一动作是问你：「公共接口是什么？哪些 seam 该测？」

红 → 绿循环

  • 红：先写一个会失败的测试（断言来自独立的事实源——已知字面量、手算例子、spec，不是从实现反推）
  • 绿：只写刚好让它通过的代码，不预判未来、不加 speculative 功能
  • 一次一个垂直切片：一个 seam、一个测试、一点实现，然后重复

三个反模式（考试重点）

反模式特征正确做法
实现耦合mock 内部协作者、测私有方法只测公共接口行为
同义反复断言用和实现一样的算法重算期望值期望值来自独立来源（spec/手算）
水平切片先把所有测试写完再写实现一个测试 → 一点实现，垂直推进

注意：重构不属于红绿循环，它属于 review 阶段——别在实现时顺手优化。

code-review：双轴审查，不让一轴掩盖另一轴

提交前最后一关。code-review 沿两条独立轴并行审查：

轴问的问题
Standards 规范代码符合仓库的编码规范吗？（外加 Fowler 代码坏味道基线）
Spec 需求代码忠实实现了工单/PRD 要求的东西吗？有没有漏做或多做？
为什么是两个独立的轴

因为一个改动可以过一轴挂一轴：代码很规范但做错了事（Spec 挂），或者做对了事但违反约定（Standards 挂）。两条轴用并行子代理跑、并列汇报，就是为了不让一轴的「通过」掩盖另一轴的「失败」。

Standards 轴除了读仓库规范，还带一套固定的「坏味道基线」（重复代码、Feature Envy、Shotgun Surgery、Speculative Generality……）——即使仓库没写规范，这套基线也生效。

本工程的真实案例

LinguaAI 的 50 次提交基本都走了这个循环。举两个有代表性的：

  1. PDF 导入（issue #33）：纯函数解析模块先写测试再实现，页面级测试验收；末尾 code-review 修掉了超限禁选、实时校验等遗漏。结果：374 测试全绿才提交。
  2. AI 预处理正文可编辑（issue #36）：实现时工厂函数引用不稳定导致 effect 重复执行——这个坑在测试里被抓到，靠 useMemo 稳定引用后才绿。项目记忆里专门记了这条教训。

共同特征：每个 commit 都对应一张已关闭的工单，且「红→绿→审查」一步没省。这是 36 张工单都能干净关闭的底层原因。

整条循环的验收标准

  1. 所有测试通过（单测 + 全量）
  2. 类型检查无错误
  3. code-review 的 Standards 和 Spec 两轴都无阻塞问题
  4. commit message 引用了对应工单（如 Closes #36）
  5. 范围严格对应工单，没有顺手做的「改进」
动手练习
  1. 读 .agents/skills/tdd/SKILL.md 的「Anti-patterns」一节，对照你自己写过的测试，有没有中过「同义反复」的招？
  2. 读 .agents/skills/code-review/SKILL.md 的 smell baseline 列表，挑一个你最常犯的坏味道（比如 Duplicated Code），想一个最近写过的代码例子。
  3. 思考题：如果 implement 跳过 tdd 直接写实现，会发生什么？（提示：回忆第 1 课「被放弃的第一版」）
