原型设计：用 solo-design 先把「长什么样」定下来

预计 15 分钟 · 基于真实 SKILL.md（~/.trae-cn/builtin/design/default/skills/solo-design/）· 目标：理解原型在流水线中的位置，以及 solo-design skill 是怎么工作的

原型在流水线中的位置

回忆第 1 课的「先画原型比先写代码便宜一个数量级」。原型设计发生在需求讨论之前——你先把应用「长什么样」用可视化方式定下来，再去讨论「要做什么」。

想法（"AI 学英语"）
   ↓ ① 原型设计（solo-design）  ← 本课
   ↓ ② setup → grill-me → to-spec → to-tickets（第 3 课）
   ↓ ③ implement + tdd + code-review（第 4 课）
   ...

为什么先原型？因为视觉比文字更容易暴露需求漏洞。你画出来一看就知道「这里少个按钮」「那个流程走不通」，比写一千字 PRD 都管用。

一句话记住

原型是需求的「可视化初稿」，solo-design 是把它变成可交互 HTML 画布的 skill。它产出的不是代码，是一个你能点、能看、能改的设计稿——后面所有开发都围绕它展开。

solo-design 是什么

solo-design 是 TRAE Work 内置的设计 skill（路径 ~/.trae-cn/builtin/design/default/skills/solo-design/）。它不是简单的「帮你画个页面」，而是一套有路由、有分工、有验证门的精密系统。

核心路由链

solo-design 遵循一条固定链路：

decision（判断意图）
  → load（只加载选定泳道的文件）
  → preflight（CSS 预检 + 派发清单）
  → dispatch（主代理派子代理生成页面）
  → validate（验证 .design 和渲染）
  → readiness（交付就绪门）

关键设计：不扫描所有 workflow 文件夹。选定一个泳道后，只读那个泳道的 INTENT_WORKFLOW.md 和它声明的上下文文件。这避免了上下文爆炸。

顶层分流：先判断是不是 solo-design 的活

solo-design 不包办所有设计。它先做两次顶层移交：

  • 像素级编辑已有位图 → 移交 solo-image-edit
  • 纯位图产出（海报、banner、KV、封面、插画）→ 移交 solo-graphic-generation

只有「可编辑的 HTML 页面/UI/原型」才留在 solo-design 里。

九条泳道（P1–P9）：按优先级匹配

剩下的请求按 P1 到 P9 优先级匹配，命中即停：

优先级场景泳道
P1编辑已有项目/页面、加状态、加对比页existing_edit
P2重新设计、复制项目、转设备redesign
P3生成多方案变体对比variants
P4主题/色板/字体定制theme_customize
P51:1 复刻、像素级还原restore_1to1
P6绑定 Design Library（设计系统）library_bound
P7长文案/PPT/表格/法律文本（静态排版）graphic_layout_static
P8长 PRD、多页面、复杂交互complex_html_page
P9无 Library、无还原目标的开放式创作free_exploration

本工程的原型设计走的是 P9 free_exploration——从零开始画桌面版应用界面。

主代理 vs 页面子代理：严格分工

solo-design 的一个精妙设计是角色分离：

角色职责禁止做
主代理路由、写 .design、注册图片/交互、验证、交付不直接写页面 HTML
页面子代理只生成页面 HTML，消费泳道运行时指南和派发包不写 .design、不跑验证、不开预览服务器、不生成图片

为什么这么分？因为生成 HTML 和管理设计文件是两种不同的关注点。子代理专注把一个页面画好，主代理保证整个项目的一致性和有效性。

.design 文件：画布优先的产物格式

solo-design 的核心产物是 .design 文件——一个 JSON，每个页面/图片都必须在里面登记：

{
  "name": "LinguaAI",
  "config": { "deviceType": "desktop", "autoLayout": true },
  "data": [
    {
      "id": "page-article-list",
      "title": "文章列表",
      "type": "page",
      "devMetadata": {
        "htmlSrc": "pages/article-list.html",
        "interactions": []
      }
    }
  ]
}

.design 有效性是阻塞性的：JSON 必须合法、data 非空、每个页面节点指向存在的 HTML、图片资产已注册。不过关就不许交付。

自由探索的快速路径（本工程实际走的路）

P9 free_exploration 有一个「快速路径」，专为普通单页/少状态设计优化：

  1. 建路由卡：模式、复杂度、是否需要提问/图片
  2. 写项目简报：用户意图、创意配方、CSS 合约、页面计划
  3. CSS 预检：生成 colors_and_type.css（定义品牌色、语义变量、圆角），跑 apply-html-head-contract.mjs 验证能注入主题变量
  4. 派发子代理生成页面：每页一个 packet，含 nodeId、htmlSrc、区块、domIds
  5. 冒烟验证：跑 validate-design-workspace.mjs，只修渲染阻塞错误，软警告（圆角、阴影等）不修

CSS 合约预检：为什么 colors_and_type.css 是视觉权威

solo-design 要求在生成任何页面前，先写一份 colors_and_type.css，定义一组语义变量（background、foreground、card、primary、border、muted 等）。然后跑一个脚本验证这些变量能被正确注入 HTML head。

这和 LinguaAI 工程的呼应

本工程的 colors_and_type.css 就是原型阶段定下的视觉权威——后续所有页面的样式都基于这套语义变量，连明暗模式都是通过切换这些变量实现的。这就是为什么第 5 课提到「colors_and_type.css 作为视觉权威」。

验证门：不验证完不许交付

solo-design 有两道硬性验证：

  • validate-design-workspace.mjs：检查 .design 合法性、页面 HTML 存在性、head 基础设施、图片引用、交互注册
  • validate-finish-readiness.mjs --check=all：设计工件就绪门，检查验证报告完整性、注册一致性、交付文本策略

这和第 3 课的「code-review 提交前审查」是同一个哲学：自动化的门比人工检查可靠。

原型产出后怎么用

solo-design 产出的是可交互的 HTML 原型（在 .design 画布中）。你可以：

  • 在 TRAE Work 的设计预览里直接点击交互
  • 把原型截图作为 PRD 的配图
  • 把 colors_and_type.css 直接搬进工程作为视觉基线
  • 把页面结构作为 to-spec/to-tickets 的输入

本工程就是这么做的：原型先确认了「侧边栏 + 内容区」的布局和 Teal 色系，后面开发时直接沿用。

动手练习
  1. 读 ~/.trae-cn/builtin/design/default/skills/solo-design/SKILL.md 的「Route Priority」表，理解 P1–P9 的优先级逻辑。问：为什么「编辑已有项目」优先级最高？
  2. 找一个你自己的项目（或一个想法），用 solo-design 画一个单页原型。体会「先视觉、后需求」的感觉。
  3. 思考题：solo-design 的主代理/子代理分工，和第 3 课 implement 的「测试先行」有什么共同的设计哲学？（提示：关注点分离）
