需求产出：一个想法如何变成一组 Agent 能直接领取的工单

预计 15 分钟 · 基于真实 SKILL.md · 目标：跑通 setup → grill-me → to-spec → to-tickets 四步流水线

这节课的终点

你脑子里有个模糊的想法：「我想做个 AI 英语学习应用」。这节课结束时，它会变成 一组带验收标准、Agent 可以无人值守领取的 GitHub issue。

用 LinguaAI 的真实经历串起来：

想法（"AI 学英语"）
   ↓ ① setup-matt-pocock-skills   把"工单放哪、标签叫啥"写进仓库
   ↓ ② grill-me (/grilling)        把想法烤问到不能再模糊
   ↓ ③ to-spec                     整理成 PRD，发 Issue #1
   ↓ ④ to-tickets                  拆成 #2~#11 十张可独立验收的工单
结果：十张 ready-for-agent 的 issue，每张都写清了"做什么、算通过、边界在哪"

① setup：先把合同的纸张买好

正式写需求前，先回答三个「以后所有 skill 都会问」的问题：

问题配置写到哪
issue 放哪里？怎么建/读/关？docs/agents/issue-tracker.md
五个 triage 状态（needs-triage / needs-info / ready-for-agent / ready-for-human / wontfix）在你仓库里叫什么？docs/agents/triage-labels.md
术语表和 ADR 放哪、怎么读？docs/agents/domain.md
关键设计

这个 skill 会先探索仓库再提问：读 git remote 自动发现 tracker 是 GitHub（用 gh CLI），找已有的 AGENTS.md……能查到的事实不问你。每个问题给推荐答案，你一个字「好」就能过。写之前还会让你看草稿。

诚实案例：LinguaAI 仓库没提交 docs/agents/，但流水线照跑——因为 remote 指向 GitHub、标签用了默认词汇，skill 的探索逻辑能推出答案。但只要你的约定偏离默认（换 tracker、改标签名），不跑 setup 就会让所有后续 skill 用错约定。

② grill-me：把模糊想法「烤」到冒烟

grill-me 内部调用 /grilling，它的动作设计非常反直觉——也非常有效：

  • 无休止：不写完验收标准不结束
  • 一次只问一个问题：不让你被问题淹没
  • 每个问题附推荐答案：你只需确认或微调，不必从零想
  • 事实查环境，决策问人：能从仓库查到的不问你，问的都是需要你拍板的取舍
为什么要「烤」

你以为你要的是「英语学习 App」，但 grilling 会逼你回答：是读文章还是看视频？AI 怎么介入？生词怎么复习？离线要不要？ 这些问题不烤清楚，后面 to-spec 写出的 PRD 就会漏，to-tickets 拆出的工单就会返工。在 grilling 阶段改一个字，等于在实现阶段省一小时。

本工程的真实产物：经过多轮 grilling，需求被锁定为「文章导入 → AI 加工（句子翻译/生词/讲解）→ 播放学习 → 复习」四段式流程，每段都有明确的验收描述。

③ to-spec：把讨论结果冻结成 PRD

grilling 结束后，你已经在对话里把需求说清楚了。to-spec 做一件事：不访谈，直接把对话综合成一份 spec，发布到 issue tracker。

它的输出结构固定：

# Spec: [标题]
## Problem          要解决什么问题
## Solution         方案概述
## User Stories     长列表的用户故事（每条都是验收点）
## Implementation Decisions  已敲定的技术决策
## Testing Decisions         测试策略
## Out of Scope     明确不做什么
## Further Notes    备注

发布后打 ready-for-agent 标签——这是流水线的目标状态：规格已写清，Agent 可以领取。

本工程案例：Issue #1 就是这份 PRD，包含完整功能清单和十张主工单的验收标准骨架。后续所有工单都以它为母本。

④ to-tickets：把 PRD 拆成可独立交付的工单

PRD 是全景图，Agent 拿不走——太大，塞不进一个上下文窗口。to-tickets 把它拆成 tracer-bullet（曳光弹）垂直切片：

  • 每张工单贯穿整个栈（数据模型 → 接口 → UI → 测试），不是按层拆
  • 每张工单可独立演示：做完这一张，就能跑通一条完整的用户路径
  • 每张工单声明阻塞边（依赖关系），按依赖序发布
  • 发布后同样打 ready-for-agent
为什么是垂直切片

水平切片（先做全部数据层，再做全部 UI）的问题：Agent 做完数据层时没有可验证的东西，容易堆出一堆没人用的接口。垂直切片保证每完成一张工单，就能肉眼看到一段真实功能，验收成本低、返工面小。

本工程案例：PRD 被拆成十张主工单（#2 应用壳 → #3 配置页 → #4 文章导入 → ... → #11 复习页），外加 25 张后续增强/修复工单（#12–#36）。每张都能独立验收、独立关闭。

整条流水线的验收标准

走完这四步，你应该得到：

  1. 仓库里有 docs/agents/ 配置（或约定与默认一致）
  2. 一张 PRD issue（#1），含 Problem / Solution / User Stories / Out of Scope
  3. 一组 ready-for-agent 标签的工单，每张：
    • 标题清晰
    • 正文含验收标准（能据此判断 done）
    • 声明了阻塞它的工单
    • 范围足够小，能塞进一次实现循环
动手练习
  1. 打开 本仓库 Issue #1，对照 to-spec 的七段结构（Problem/Solution/User Stories/...），看每段写了什么。
  2. 找一张主工单（比如 #4 文章导入），读它的验收标准——体会「什么算 done」是怎么写清的。
  3. 读 .agents/skills/grilling/SKILL.md，数一数它列了多少种「要问的问题类型」，思考为什么 grilling 是流水线里耗时最长、但最值钱的一步。
