第 2 课 · RAG 面试冲刺

切分与索引：chunk 策略决定召回上限

为什么「chunk 多大」没有标准答案，以及怎么用数据回答它 · 约 18 分钟

一、切分是上限，不是细节

第 1 课说「离线决定召回上限」。这句话最具体的落点就是切分—— 因为检索的最小单位就是 chunk。如果答案在文档里，但没被切进任何一个 chunk， 或者切进去了却看不出在讲什么，那么后面 rerank 再强、模型再好，都变不出它来。

切分有两个方向的失败，它们对称且都很常见：

切太小 → 向量检索不到，模型也用不了
一段话脱离上下文就失去了意义。Anthropic 举的例子是财务文件里的 「The company's revenue grew by 3% over the previous quarter.」—— 单看这一段，不知道是哪家公司，也不知道是哪个季度。它检索不到，就算被检索到也没法用来回答。
切太大 → 语义被平均掉，精确问题匹配不上
Pinecone 的说法是： 块越大越可能引入噪声、稀释单句的重要性，于是查询时更难命中精确匹配。 一个块里混了三个主题，它的向量就是这三个主题的平均值——离哪个都不近。

判断一个 chunk 好不好，用这条判据： 如果这段文本脱离上下文，人还能看懂，那么模型也能看懂。 （Pinecone 原文：if the chunk of text makes sense without the surrounding context to a human, it will make sense to the language model as well.）

这条判据值得背下来。它把「chunk 质量」这个模糊问题，变成了一个你能立刻执行的检查动作—— 面试时说出来，面试官会知道你有一套可操作的判断标准，而不是记住了几个参数。

二、决定怎么切的四个问题

在动手切之前，Pinecone 建议先回答四个问题。这四个问题本身就是面试时你该展开的框架—— 直接答「我切 512 字」是背书，按这四个维度答才是在做设计：

  1. 切的是什么数据？书籍文章这类长文档，和推文、商品描述这类短内容，处理方式完全不同——短内容可能根本不该切。长文档往往自带结构（章节、小标题），而结构就是免费的切分依据。
  2. 用哪个 embedding 模型？不同模型的信息容量不同，在代码、金融、医疗、法律这些专业领域差异更大；模型是怎么训的，会直接影响你该怎么切。
  3. 用户的查询长什么样？短而具体的查询，和长而复杂的查询，需要的粒度不一样。目标是让 query 的向量和 chunk 的向量「对得上」。
  4. 检索结果拿来干什么？做语义搜索、问答、还是喂给 agent？人能看的搜索结果条数，和模型生成需要的条数，不是一回事。

三、策略阶梯，以及一个反直觉的结论

从最省事到最强，切分策略大致分五档：

策略做法什么时候用
固定长度 按固定 token / 字符数硬切，块间加 overlap 默认起点。最简单、最快、行为可预测
递归字符 按分隔符优先级递归切，尽量落在自然边界：["\n\n", "\n", " ", ""]（LangChain 的 RecursiveCharacterTextSplitter 就这么做） 想保住段落和句子完整，又不想上重方案
结构感知 按文档自身的结构切：Markdown 标题、HTML 标签、PDF 章节、LaTeX 环境 文档有清晰结构（这是最被低估的一档）
语义切分 把句子成组做 embedding，比较相邻组的语义距离，在「话题转折处」下刀 结构混乱、话题频繁切换的文档；实验性，成本高
上下文增强 让 LLM 为每个 chunk 生成 50–100 token 的定位说明，前置到 chunk 上，再去做 embedding 和建 BM25 索引 前面的手段都试过、仍然丢上下文时

本课最重要的判断，是反直觉的那一个：从固定长度开始，别一上来就上花的。

Pinecone 的原话是：Fixed-sized chunking will be the best path in most cases, and we recommend starting here and iterating only after determining it insufficient.

注意说这话的是一家卖向量数据库的公司——它最有动机让你相信 RAG 很复杂。它却劝你先用最土的办法。 理由是工程上的：花哨策略引入的是不可解释的变量。你不知道收益来自策略本身，还是来自它顺带改变了块大小。

那上下文增强到底有没有用？有，而且是被量出来的：Anthropic 实测单独的上下文 embedding 把 top-20 检索失败率降低了 35%，叠加上下文 BM25 后降低 49%，再加 rerank 后降低 67%。 但请注意它是叠加上去的，不是替代品——它建立在「切分已经合理」的前提之上，而且有成本（约 $1.02 / 百万文档 token，靠 prompt caching 压下来）。

「上下文增强切分听起来很好，你为什么不在项目里用它？」

这是一个陷阱题：它在测你会不会无脑追新。可用的答法是—— 「我会先用固定长度和结构切分把基线跑出来，量到 Recall@k 的天花板在哪；如果瓶颈确实在「块丢失上下文」而不是在检索环节，我再上上下文增强， 因为它的代价是索引期要跑一遍 LLM、成本随文档量线性增长。没有基线就上它，我没法证明它值这个钱。」

四、三个几乎所有人都会漏的点

1. overlap：为什么加，加多少

加 overlap 的唯一目的是防止答案正好横跨两块边界——切在句子中间的损失，靠让相邻块共享一段文本来弥补。 代价有两个：索引变大（存储与构建成本），以及同一段内容被多个块召回，挤占 top-k 名额。 常见起点是块大小的 10–20%，然后靠评测调——又是评测。

2. 元数据：切分时顺手要做的事

每个 chunk 除了文本，还应该带上来源、标题路径、页码、时间和权限标签。这不是洁癖，它在三个地方都要用：

  • 检索时过滤——按权限、按时间、按文档类型缩小范围。企业场景里这一条是刚需，不是加分项。
  • 组装上下文时定位——告诉模型「这段出自哪一章」，它更不容易误用。
  • 引用溯源——答案要能指回原文，否则用户不会信。

一个能让你答案变亮的观察：结构感知切分 + 标题路径前缀，就是「穷人版的上下文增强」。

Anthropic 花 LLM 调用给每个块生成定位说明；而如果你的文档本来就有标题层级， 把 产品文档 > 定价 > 企业版 直接前置到块里，拿到的是同一类上下文—— 零额外成本。真正需要花钱的场景是文档本身没有结构，或者结构细到标题不足以定位。 能讲清这个取舍，比单纯背「上下文增强能降 49%」高一个层次。

3. chunk expansion：小块检索，大块生成

你并不需要为「检索要小、生成要大」这个矛盾二选一。Pinecone 给的做法是 chunk expansion：检索时照常用小块保证精度和低延迟，命中之后， 把它的邻近块（前后各一段、整页、甚至整篇）一起带进上下文。

这就是 parent-child（也叫 small-to-big）的同一个思想。面试里能主动说出「检索粒度和生成粒度不必相同」， 说明你理解了 RAG 里一个很本质的解耦。

五、别猜 chunk size，测出来

「chunk 设多大合适？」

这是本课最高频的面试题，而它不是一道知识题，是一道实验设计题。 凡是直接报数字的答案都输了，因为正确开头只有一种： 「取决于文档形态和查询类型。我会这样测——」

具体怎么做（Pinecone 的方法，我把它整理成了可执行的四步）：

  1. 定候选尺寸区间：小到 128 / 256 token（抓细粒度语义），大到 512 / 1024 token（保上下文）。
  2. 并行建索引：用多个索引，或同一索引下的多个 namespace，每个尺寸建一份。
  3. 用一批有代表性的 query 跑评测：比较各尺寸的 Recall@k。
  4. 迭代：在胜出的区间里继续细分，直到收益不再明显。

第 3 步藏着一个前提，而它才是真正的答案：你得有一个带标注的评测集—— 一批 query，以及每个 query 应该被召回的 chunk。

没有它，上面四步一步都跑不动，你就只能靠感觉。面试时主动把这个前提说出来， 等于当场告诉面试官：我知道 RAG 的优化是评测驱动的，不是调参驱动的。 这也正是阶段二要专门解决的事。

还有一个细节值得提：chunk size 用字符还是 token？ 不同 embedding 模型的分词方式不同，估算 token 数时必须按你实际用的模型来算，别拿字符数糊弄过去。

六、面试官原话

「你的文档里有表格，怎么切？」

表格是结构破坏最严重的地方。按固定长度硬切会把行列关系切断——一行数据失去表头，就彻底没有意义了。 可用的答法：先把表格解析成 Markdown 或 HTML 以保住结构；整表作为一个块，如果超长就按行分组切， 并且每一块都要重复表头；元数据里记下表名和列名，检索时可以按列名匹配。

「为什么要加 overlap？加多少合适？」

不要答「为了更准」。要点是它防的是哪一种损失：答案正好横跨边界被切断。 代价是索引膨胀加上重复召回挤占 top-k。所以 10–20% 起步，再用评测调—— 如果你的评测显示块边界从来不是失败原因，那 overlap 就是纯粹的浪费。

八、真练一次：手写结构感知切分器

这是「手撕代码」轮次的高频题型：给你一篇 Markdown，按结构切分，并保留定位信息。 先自己写，再展开对照。要求我觉得你应该自己先定一遍，然后再看我是怎么定的。

规格：① 按 # 标题层级切；② 每个块带上完整标题路径；③ 超长节按段落二次切，并带 overlap；④ 块之间不丢内容。

先自己写，再展开参考实现 
import re
from dataclasses import dataclass

@dataclass
class Chunk:
    text: str          # 送去 embedding 的正文（含标题路径前缀）
    heading_path: str  # "产品文档 > 定价 > 企业版"
    source: str        # 文件名 / URL，做引用用

HEADING = re.compile(r"^(#{1,6})\s+(.*)$")

def split_markdown(md, source, max_chars=800, overlap_chars=80):
    """按标题层级切 Markdown，块内保留标题路径，超长节再按段落二次切分。"""
    stack = []   # 当前标题栈：[(level, title), ...]
    body = []    # 当前节的正文行
    chunks = []

    def flush():
        if not body:
            return
        path = " > ".join(t for _, t in stack)
        text = "\n".join(body).strip()
        body.clear()
        if not text:
            return
        if len(text) <= max_chars:
            chunks.append(Chunk(f"{path}\n{text}" if path else text, path, source))
        else:
            chunks.extend(_split_long(text, path, source, max_chars, overlap_chars))

    for line in md.splitlines():
        m = HEADING.match(line)
        if m:
            flush()                      # 遇到新标题，先把上一节交出去
            level = len(m.group(1))
            stack[:] = [(l, t) for l, t in stack if l < level]
            stack.append((level, m.group(2).strip()))
        else:
            body.append(line)

    flush()                              # 别忘了最后一节
    return chunks


def _split_long(text, path, source, max_chars, overlap_chars):
    """按段落聚合到 max_chars 以内；单段本身超长时按字符硬切兜底。"""
    paras = [p for p in text.split("\n\n") if p.strip()]
    out, buf = [], ""

    def push(c):
        if c.strip():
            out.append(c.strip())

    for p in paras:
        # 单段就超过 max_chars（长表格、密集条款）：冲掉缓冲，再硬切
        if len(p) > max_chars:
            push(buf); buf = ""
            step = max(1, max_chars - overlap_chars)
            for i in range(0, len(p), step):
                push(p[i:i + max_chars])
                if i + max_chars >= len(p):
                    break
            continue
        if buf and len(buf) + len(p) + 2 > max_chars:
            push(buf)
            buf = (buf[-overlap_chars:] + "\n\n" if overlap_chars else "") + p
        else:
            buf = f"{buf}\n\n{p}" if buf else p

    push(buf)
    prefix = f"{path}\n" if path else ""
    return [Chunk(prefix + c, path, source) for c in out]

我写这段代码时踩的坑，你一定要知道。第一版我只按段落聚合，没有那个「单段就超长」的分支。 结果是：普通文档切得好好的，但只要出现一个超长段落（长表格、密集条款、一整段没换行的正文）， 它就会原样变成一个远超上限的块——我实测一个 200 字符上限的配置产出了 373 字符的块。

更值得说的是我是怎么发现它的：我在测试里加了一句断言 assert all(len(c.text) <= max_chars + len(prefix) for c in cs)。 没有这句断言，我不会注意到——因为切出来的块「看起来」都挺正常。 写切分器必须带不变量断言：每块不超上限、块间不丢内容、标题路径不为空。这三条就是你的测试。

接着自己动手改：① 加一个 min_chars，把过小的碎块向相邻同父节点合并（实践中碎块很常见）； ② 用真实 tokenizer 替换字符计数；③ 把 source 换成完整的元数据字典（页码、时间、权限标签）。 改完发我，我给你看有没有漏掉的边界情况。

九、本课要带走的三句话

  1. 切分决定召回上限。后面所有环节都在这个上限之下工作——切丢了的东西，谁都救不回来。
  2. 从固定长度开始，只在被证明不够用时才升级。说这话的是卖向量数据库的公司，这个细节本身就是答案的说服力。
  3. 「chunk 多大」是实验设计题，不是知识题。候选尺寸 × 标注 query 集 × Recall@k——而且你得先有那个评测集。
