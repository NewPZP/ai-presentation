检索与查询改写：为什么纯向量不够

一、两种检索在互补的地方失败

第 1 课说过纯向量对「型号、错误码」这类精确串不敏感。但光知道「向量会漏精确匹配」还不够， 面试官会接着问：那加什么、怎么加、加了有什么用。这三点就是本课。

Qdrant 用一组真实商品检索查询把这件事讲得最清楚—— 同一个查询，两种检索谁把相关商品排第一：

查询稠密（向量）检索排第一的稀疏（BM25）检索排第一的
french molding french curves rosette applique 相关 french bread mold toast tray 不相关
wayfair comforters wayfair basics comforter set 相关 wayfair basics peva shower curtain liner 不相关
bathroom vanity knobs carran 30'' single bathroom vanity set 不相关 damask mushroom knob 相关
farmhouse cabinet rustic storage cabinet 不相关 farmhouse 2 door accent cabinet 相关

看第一行：查「french molding」，稀疏检索跟着 french 和 mold 两个词， 一路跑到了「法式面包模具」上——它把 mold 理解成了模具，而用户要的是装饰线条（molding）。 稀疏检索对词形和词义是盲的。

再看第三行：查「浴室柜旋钮」，稠密检索找到了「浴室柜」这个领域，却选了一个不带旋钮的整体柜； 稀疏检索跟着 knobs 这个词，精准命中了旋钮商品。稠密检索对精确词项是盲的。

两种盲区是对称的，所以它们能互相补。Qdrant 有一句话说到了要害： 无论哪种检索失败，「你的日志都会记下一次『成功』的查询」—— 检索失败是静默的，用户拿到了看着很合理的结果，而你以为系统跑得很好。

这也是为什么 BEIR 那篇基准论文的结论值得记住： BM25 是一个极强的基线，很多复杂方案在零样本设定下并不能稳定赢过它。 面试里主动说「BM25 是强基线，所以我会先量它」比一上来就吹稠密检索稳得多。

二、BM25：为什么它三十年不倒

BM25 不是「关键词匹配」这么含糊的东西，它有一个精确的公式，而且面试官（尤其算法岗）会问。 下面是 Stanford IR 教材给的标准形式： 

              # 对查询里每个词 t 求和
              ⎛ N ⎞   (k₁ + 1) · tf(t,d)
score(d, q) = Σ log│───│ · ─────────────────────────────
              ⎝df_t⎠   k₁·((1 - b) + b · L_d / L_avg) + tf(t,d)

逐项拆开看，每一项都在解决一个具体问题——这样你就不用死记：

  • log(N / df_t) —— IDF，稀有词更值钱。出现在半数以上文档里的词权重会趋近 0。 （教材提到一个更精细的变体 log((N - df_t + 0.5)/(df_t + 0.5))，它在词出现于超过一半文档时会变成负数，所以通常要加一个 0 下限。）
  • tf(t,d) —— 词频，但带饱和。这是 BM25 最精妙的地方：一个词出现 10 次， 并不比出现 2 次重要 5 倍。看公式右边的分式，当 tf 增大时它趋近于上限 (k₁+1)，也就是收益递减。
  • L_d / L_avg —— 文档长度归一化。长文档天然更容易命中任何词，所以要惩罚长度。 b 就是控制这个惩罚强度的开关。

两个参数的语义，教材写得很明确：

参数取值含义实践默认
k₁ 调节词频的缩放。k₁ = 0 退化成「只看出没出现」的二值模型（完全不管出现几次）；k₁ 很大则等于直接拿原始词频来用 1.2 – 2
b 文档长度缩放。b = 1 完全按长度归一化，b = 0 完全不归一化 0.75

这两个默认值（k₁ 取 1.2–2、b 取 0.75）是教材在没有做参数优化时的推荐值。 更规范的做法是在一个开发集上用网格搜索调——这一点和 chunk size 是同一个道理：可调的参数都应该被测量，而不是被继承。

BM25 有一个被低估的工程优势：它不做任何模型推理。 索引期不需要 GPU，在线查询只算词频加权，延迟和成本都极低。这就是为什么「加一路稀疏检索」是一件性价比很高的事—— 但也仅此而已，别把它当成万能药，代价在第五节。

在 BM25 之上还有学习式稀疏检索，面试里能提一句会显得你读过论文： SPLADE 会补上原文里根本没出现过的相关词（召回同义词）， miniCOIL 则保留 BM25 的词项匹配但按上下文重新加权—— 让体育文章里的 bat（球棒）和动物指南里的 bat（蝙蝠）不再共享同一个权重。 Qdrant 给的建议很克制，我建议你照抄：先用 BM25，再拿学习式模型跟它比，比过了才换。

三、融合的真正难题不是「相加」，是「量纲」

现在你有了两路结果，要把它们合成一个排序。第一反应是加权求和，比如 0.5 × 余弦 + 0.5 × BM25。这个做法会翻车，原因值得你记一辈子：

余弦相似度是有界的（大致 0–1），而 BM25 的量纲取决于「命中了几个查询词、这些词有多稀有」。

所以同一个权重，在查询 A 上刚好平衡，在查询 B 上可能让 BM25 一边倒—— 没有任何一组固定权重能对所有查询保持同样的平衡。 Qdrant 用两张散点图说明这件事：余弦分数稳定在 0.6–0.9，而 BM25 在查询 A 上全都不超过 20，在查询 B 上却有 20–80 的跨度。

于是融合分成两派，理解这两派的差别，比记住任何一个公式都重要：

派别做法代表
按名次融合 丢掉分数大小，只看每个文档在各路里排第几 RRF（倒数排名融合）
按分数融合 先按查询把每一路的分数归一化到同一尺度，再加权相加 DBSF、Weaviate 的 relativeScoreFusion

四、RRF：只用名次的好处

RRF 的公式短到可以背下来，出自 Cormack、Clarke 与 Büttcher 2009 年的两页短文： 

RRF(d) = Σ        1 / (k + r(d))
         r ∈ R

r(d) 是文档 d 在第 r 路结果里的名次（原文用 1 起始的名次）。 注意公式里没有分数——这就是它的全部卖点： 它能把「余弦 0.7」和「BM25 12.4」放在一起融合，因为它从不需要比较这两个值。量纲问题直接消失了。

k = 60 不是拍脑袋来的，原文有交代。 Cormack 等人的原话是：k = 60 在一次先导实验中被固定下来，之后的验证里没有再改动。 他们给的直觉是——「高度靠前的文档更重要，但靠后文档的重要性不应该像指数函数那样迅速消失； 常数 k 用来缓和异常系统给出的高排名所带来的影响。」

最后那句话值得你反复读，因为它直接解释了 RRF 的行为偏好。我们用一个手算得出来的例子看： 稠密检索给出 D3, D1, D7, D2, D9，稀疏检索给出 D5, D3, D2, D8, D1。 （分数也一并给出，下一节要用来对比：稠密余弦 D3 0.82 / D1 0.79 / D7 0.78 / D2 0.77 / D9 0.76； 稀疏 BM25 D5 18.4 / D3 12.1 / D2 9.7 / D8 4.2 / D1 3.9。）

请盯着 D5 看。它是稀疏检索的第一名——两路里唯一一个被某一路排到榜首的文档—— 但最终只排第 4，输给了稠密第 2、稀疏第 5 的 D1，也输给了两边都只是中游的 D2。

这不是 bug，这是 RRF 的设计意图。因为 k=60 把名次的差别压得很平： 第 1 名是 1/61 ≈ 0.0164，第 5 名是 1/65 ≈ 0.0154，只差 6% 左右。 于是一个文档的最终得分，主要取决于它被几路同时看好，而不是它在某一路里多靠前。 换句话说：RRF 是一个共识机制，它奖励「都认可」，惩罚「一枝独秀」。

这个性质既是优点也是风险，而风险才是面试的考点。 如果用户查的正是那个冷门型号，稠密检索完全没召回、只有 BM25 找到了它——RRF 会因为稠密那边投了反对票，把它压到中游。 你引入混合检索本来就是为了救这种查询，RRF 却可能把它埋掉。

那怎么救它？最直觉的答案是「给稀疏那一路加权重」。我实际算过，这个办法是钝器，基本没用—— 因为加大稀疏权重的同时，也抬高了 D1（它同样在稀疏列表里，只是排 #5）。 在这个例子里，要让 D5 压过 D1，稀疏权重得大到约 16 倍；而那时整个排序已经被稀疏一路主导， 混合检索的意义也就没了。权重调 3 倍、10 倍，D5 都还稳稳待在第 4 位。

真正能救它的不是调参数，而是换融合的「派别」——下一节的按分数融合会保留 D5 那个 18.4 对 12.1 的巨大领先， 不需要任何权重就能把它送到第 2 位。能讲清这一段，你就和背公式的人分开了。

五、另一条路：按分数融合

Weaviate 把两派都实现了， 这是理解差别最好的现成材料：

算法做法特点
rankedFusion（旧默认） 按名次给分，1/(rank + 60)，两路相加 就是 RRF。只用名次，对量纲免疫
relativeScoreFusion（1.24 起默认） 按查询把每路分数归一化——最高分变 1、最低分变 0，中间按相对距离缩放——再按 alpha 加权相加 保留分数差距，所以一路的「压倒性领先」能影响最终排序

回到 D5 那个例子。稀疏检索给 D5 的分数是 18.4，而第二名只有 12.1——这是一个压倒性的领先。 按分数融合会把它保留下来：各自归一化之后，D5 拿到 1.0，而稀疏那一列的第二名只有 0.57。 我把同一组分数用 DBSF（按查询分别归一化再相加）实算了一遍，结果和 RRF 差别很大：

这就是两派最本质的区别：要不要保留「赢多少」的信息。 RRF 只记下「D5 是稀疏第 1 名」，却看不见它领先了 6 分；DBSF 看得见，所以 D5 从第 4 名升到第 2 名， 而且不需要调任何权重。反过来说，DBSF 的脆弱点也在这里：它依赖分数分布， 所以当某一路的分数分布本身不可靠（比如 BM25 在长查询下的量纲漂移）时，它会把这种不可靠也一起放大。

Weaviate 在 1.24 把默认从 rankedFusion 换成了 relativeScoreFusion， 理由是内部基准（FIQA 数据集）上召回率提升了约 6%，且它保留了更多原始信息；alpha 参数则让你控制偏向关键词还是偏向向量。 但请记住这是厂商内部基准、非第三方复现——面试引用时把这句话带上。

六、融合有一个硬边界，这一条最能拉开差距

「我用了混合检索加 RRF，为什么还是漏了那篇文档？」

Qdrant 有一句话我认为是整个混合检索话题里最重要的： 融合只做重排。它作用在两路候选的并集上，所以两路都没找到的文档，不可能出现在结果里的任何位置。

这句话的含义是：融合不能创造候选，它只能重新分配已有候选的顺序。 你花了力气调融合算法，但如果正确答案在两路的前 100 条之外，所有融合算法都一样无能为力。 这时候该动的是候选深度（prefetch 的 limit），而不是融合方法—— 而且加深度也有代价：检索工作量变大，而且如果两路在更深处依然找不到它，加深也没用。

这个「先看候选集有没有、再看排序对不对」的排查顺序，同样是你第 5 课做评测和归因时的基本框架。

七、混合检索不是免费的

面试里如果你只说「混合检索能提升效果」，那只是一半答案。另一半是代价，而代价让这个方案变得需要论证：

  • 存储与索引：每个文档要多存一个稀疏向量，多建一个索引，每次查询多跑一路检索。
  • 延迟：Qdrant 在一个容器、单请求、无并发的条件下测得中位延迟增加 0.60 – 1.47 毫秒。 注意这个前提——它明确提醒要在你自己的并发与分片条件下重新测，别把这个数字搬到你自己的容量规划里。
  • 改造代价：给一个已经在跑的纯稠密库加上稀疏向量，必须新建 collection 并全量重建索引，因为向量配置在创建时就固定了。
  • 一个容易忽略的坑：稀疏向量要打开 IDF 修饰，让稀有词权重更高。 Qdrant 的原话很有画面感——没有它，一个常见词可能和一个零件编号得到同样的权重。

然后是最重要的一条：混合检索不是稳赚的。Qdrant 在五个公开数据集上用 nDCG@10 对比了纯稠密、纯稀疏和 RRF 融合：

八、查询改写：让用户的问法更像文档的说法

检索失败的另一个源头在查询这一侧：用户的问题短、口语化、用的是他自己的词，而语料用的是另一套词。 查询改写就是为了弥合这个鸿沟。两种常见做法：

多路查询（multi-query）

让 LLM 把原问题改写成几个不同角度的查询，各自检索，再融合（正好用上本课学的融合）。 好处是覆盖面变宽；代价是检索次数变成 N 倍，外加一次 LLM 调用，延迟和成本都上去。

HyDE：先编一个假答案，再拿它去检索

HyDE 的做法有点反直觉： 先让 LLM 针对问题生成一段假想的答案文档，再把这篇文章向量化去检索。 理由是——答案的写法天然比问题的写法更像文档，所以在向量空间里离真实文档更近； 而假答案里编造的具体细节，会被编码器的稠密瓶颈过滤掉，不会污染检索方向。

但别把 HyDE 说过头。Anthropic 在 Contextual Retrieval 那篇里明确提到， 他们评估过同类思路（包括假想文档嵌入与基于摘要的索引），收益有限。 所以稳妥的表述是：「HyDE 在零样本、领域外检索上是有依据的方案，但它的收益依赖场景，我会先量再上。」

最后补一个反向考点：查询改写也会帮倒忙。 如果用户的查询本身就是一个精确的型号或错误码，改写可能把它「顺滑」成一个语义相近但丢掉关键串的句子—— 本来 BM25 能一击命中的，反而查不到了。知道什么时候不该改写，和知道怎么写，是同一件事的两面。

九、面试官原话

「你为什么要在项目里上混合检索？给我讲讲收益和代价。」

完整答法应当含四个部分：① 动机（稠密漏精确串、稀疏漏同义改写，两种盲区互补）； ② 机制（RRF 融合，因为余弦有界而 BM25 量纲随查询漂移，不能直接加权求和）； ③ 代价（多一个索引与一路检索、中位延迟增加若干毫秒、已有库要全量重建、稀疏向量必须开 IDF 修饰）； ④ 验证（在我们自己的带标注查询集上比 nDCG@10 或 Recall@k，并说明它不一定赢——公开数据集上就有一个反例）。 四段齐了，这一题就是满分。

「RRF 里的 k 是干什么用的？你会调它吗？」

答「60 是论文里固定的值，作用是缓和异常系统的高排名影响」——这是及格。 加分的是接着说：调小 k 会让单路的高排名更值钱。我在上面的例子里实算过： k 从 60 调到 1，D5（稀疏第 1）的分数从 0.01639 涨到 0.50，确实超过了「两路都中游」的 D2（0.45）。

但更值得说的是它救不了全部：同一个 k=1 下，D1 和 D5 的分数正好打平（都是 0.50）， 谁排前面完全取决于你的兜底排序规则——这正是下面代码里要专门处理的问题。 所以我的结论是：k 和权重都是钝器；要让「某一路独占命中」的文档拿到应有的地位，换融合派别比调参数有效得多。

十一、真练一次：手撕 RRF 并手算一遍

「手撕代码」轮次的高频题就是实现 RRF。它代码很短，所以面试官会追问边界条件——那才是真正的考点。

先自己写，再展开参考实现与三个追问 
def rrf(ranked_lists, k=60, weights=None):
    """把多路检索结果按名次融合。

    ranked_lists: [[doc_id, ...], ...]，每一路已按相关度降序。
    weights:      每路的权重，默认等权。想偏向稀疏那路时就用它。
    """
    if weights is None:
        weights = [1.0] * len(ranked_lists)

    scores = {}
    for lst, w in zip(ranked_lists, weights):
        for i, doc in enumerate(lst):
            rank = i + 1                       # 原始论文用 1 起始的名次
            scores[doc] = scores.get(doc, 0.0) + w / (k + rank)

    # 分数相同时按 doc_id 定序，保证结果可复现（否则依赖字典序，难复现）
    return sorted(scores.items(), key=lambda kv: (-kv[1], str(kv[0])))

面试官紧接着会问的三个问题，先想好再往下看：

① 名次从 0 还是从 1 开始？原始论文定义名次是 1 到 |D| 的排列，所以上面用 i + 1。 有些实现用 0 起始。两种只让所有分数整体平移一点，通常不改变排序， 但你得知道自己在用哪种——被追问时答不上来，会显得你只是抄了一段代码。

② 分数打了平手怎么办？上面的例子算出来 D1（0.03151）和 D2（0.03150）非常接近， 现实中打平很常见。如果不显式定序，返回顺序会依赖字典的遍历顺序，同一个查询两次跑出不同结果。 这是评测里最难查的一类问题：你的指标会莫名其妙地抖。所以我加了 str(doc_id) 作为兜底排序键。

③ 怎么让它偏向某一路？加权重（上面已支持）。但要意识到： 权重和 k 是两种不同的杠杆——k 改变「名次差距被压平多少」，权重改变「哪一路说话更响」。 调之前先想清楚你要修的是哪一种失败。

再加一个练习，这个练习会让你真正理解 RRF 的局限：拿本课第四节的例子 （稠密 D3,D1,D7,D2,D9；稀疏 D5,D3,D2,D8,D1），先用手算验证表格里的 RRF 分数，再跑代码对齐。

然后把稀疏那一路的权重依次设成 3、10、25，观察 D5 的排名。 你会看到一个反直觉的结果：权重加到 10 倍，D5 还是第 4 位；要到约 16 倍它才超过 D1—— 而这时排序已经被稀疏一路主导了。

原因值得你想清楚：加大某一路的权重，会同时抬高这一路里的所有文档，包括你并不想抬的那个。 D1 虽然在稀疏里只排 #5，但它额外拿到稠密那一路的 #2，所以它跟着水涨船高。 权重是个钝器，它无法只挑出「那一个独占命中的文档」。

最后把同一组分数丢给按分数融合（DBSF），你会看到 D5 直接升到第 2 名，一次权重都不用调。 这三步做完，「RRF 用名次换取稳健、代价是丢掉赢多少」这句话对你就不是知识，而是经验了。

十二、本课要带走的三句话

  1. 稠密与稀疏的盲区是对称的，所以混合检索有价值——但这个价值必须在你自己的带标注查询集上验证，公开数据集上就有反例。
  2. 融合的真问题是量纲，不是加法。RRF 用「只看名次」绕开它，代价是丢掉「赢多少」的信息，因此会埋掉一枝独秀的文档。
  3. 融合不能创造候选。两路都没找到的文档，换什么融合算法都没用——该动的是候选深度。
