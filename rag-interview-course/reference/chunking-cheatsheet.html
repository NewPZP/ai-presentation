切分策略速查

策略阶梯 · 参数起点 · 特殊文档 · 不变量断言 · 打印友好

第一判据：如果这段文本脱离上下文，人还能看懂，那么模型也能看懂。 任何切分参数在报出来之前，先拿这句话过一遍。

策略阶梯

档策略做法代价 / 何时上
1 固定长度 按固定 token / 字符数硬切 + overlap 最省事、可预测。默认起点，不必先证明它不够用
2 递归字符 按分隔符优先级递归下刀：["\n\n", "\n", " ", ""] 保住段落句子完整。想在档 1 上小步改进时用
3 结构感知 按 Markdown 标题 / HTML 标签 / PDF 章节 / LaTeX 环境切，块内保留标题路径 文档有结构时性价比最高。标题路径前缀 = 免费的上下文增强
4 语义切分 句子成组做 embedding，在相邻组语义距离的转折处下刀 实验性、成本高。结构混乱、话题频繁切换时才考虑
5 上下文增强 LLM 为每块生成 50–100 token 定位说明，前置后再 embedding + 建 BM25 索引期成本约 $1.02 / 百万文档 token（靠 prompt caching）。前四档都不够用时才上

反直觉但重要：Pinecone（一家卖向量数据库的公司）明确建议先固定长度起步， 只在被证明不够用时才迭代。花哨策略引入的是不可解释的变量—— 你分不清收益来自策略本身，还是它顺带改变了块大小。

参数起点

参数起点说明
chunk size256 / 512 token候选区间取 128–1024：小的抓细粒度语义，大的保上下文
overlap块大小的 10–20%只防「答案横跨边界」。代价：索引膨胀 + 重复召回挤占 top-k
块上限≤ embedding 模型上下文窗口超了会被截断丢弃，丢掉的部分等于不存在
最小块设一个 min_chars碎块很常见，应向相邻同父节点合并

单位陷阱：不同 embedding 模型分词方式不同，token 数必须按你实际用的模型估。 拿字符数当 token 数用，是在给自己埋雷。

四个决策问题（动手前先答）

  1. 切的是什么数据？长文档 vs 短内容；后者可能根本不该切。长文档常自带结构。
  2. 用哪个 embedding 模型？信息容量与训练方式因领域（代码 / 金融 / 医疗 / 法律）差异很大。
  3. 查询长什么样？短而具体 vs 长而复杂——目标是让 query 向量与 chunk 向量「对得上」。
  4. 检索结果拿来干什么？语义搜索 / 问答 / 喂 agent，需要的粒度不同。

特殊文档怎么切

类型做法坑
表格 解析成 Markdown / HTML 保住结构；整表为一块，超长按行分组且每块重复表头；元数据记表名与列名 硬切会切断行列关系——一行失去表头就彻底没意义
PDF 优先按章节 / 页眉页脚 / 目录层级解析，别直接抽纯文本 双栏排版、页眉页脚、脚注会混进正文；扫描件要先 OCR
代码 按函数 / 类 / 文件边界切，块内保留文件路径与导入 按字符数切会把函数劈成两半，上下文对不上
HTML / Markdown 按标签 / 标题层级切，把标题路径写进块 导航栏、广告、页脚会被当成正文切进去

用数据定 chunk size（四步）

  1. 定候选区间：128 / 256 / 512 / 1024 token。
  2. 并行建索引：多个索引，或同一索引的多个 namespace，每个尺寸一份。
  3. 跑评测：用一批有代表性的 query，比较各尺寸的 Recall@k。
  4. 迭代：在胜出区间里继续细分，直到收益不再明显。

前提是有一个带标注的评测集（query → 应该被召回的 chunk）。 没有它，这四步一步都跑不动——面试时主动说出这个前提，等于当场证明你懂评测驱动。

切分器的不变量断言（写完就测）

# 三条不变量，缺一条你就发现不了 bug
# 注意 text = "标题路径\n" + 正文，算上限时要把前缀减掉，否则差一个字符
prefix = lambda c: len(c.heading_path) + 1 if c.heading_path else 0

assert all(len(c.text) - prefix(c) <= max_chars for c in chunks)      # ① 正文不超上限
assert "".join(c.text for c in chunks).find(first_sentence) >= 0    # ② 不丢内容
assert all(c.heading_path for c in structured_chunks)                  # ③ 路径不为空

① 为什么必须有：一个超长段落（长表格、密集条款）会原样穿透段落级切分，产出远超上限的块， 而它「看起来」完全正常——没有断言你不会注意到。

检索粒度 ≠ 生成粒度

不必为「检索要小、生成要大」二选一。做法是 chunk expansion （也叫 parent-child / small-to-big）：用小块检索保证精度与低延迟， 命中后把邻近块或父块一起带进上下文。Pinecone 原话：把切分策略与 query 时的 chunk expansion 配起来， 能在不牺牲上下文的前提下拿到低延迟检索。

故障 → 药方

块检索不到，但文档里明明有
先看块是否脱离上下文就没了意义（指代、省略主语）。加标题路径前缀，或上上下文增强。
精确查询（型号、错误码）搜不到
这可能不是切分问题，而是检索方式问题——纯向量对低频精确串不敏感，见第 3 课的混合检索。
同一条内容反复出现在结果里
overlap 过大，或被切成多块后重复召回。调小 overlap，检索后做去重。
答案总差最后一句 / 半个表格
边界切断。加 overlap，或改用 chunk expansion 带上邻近块。
块里混了好几个主题
块太大、语义被平均。调小 chunk size，或改用结构感知切分。
