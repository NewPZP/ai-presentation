重排与两段式速查

排序差距诊断 · 三步测法 · 选型与排错 · 成本表 · 打印友好

本页第一判据：先量「把候选集当作完美排序能得多少分」，再和你当前得分比。 差距大 → 值得动排序；差距小或为 0 → 该去改候选本身。 在你伸手去拿重排模型之前，先做这一步。

排序差距诊断（这是上不上重排的判据）

def ranking_gap(ranked_ids, relevance, k=10):
    """返回 (当前 nDCG@k, 最优可能, 差距)。差距 = 更好的排序能捞回的全部。"""
    now = ndcg_at_k(ranked_ids, relevance, k)
    perfect = sorted(set(ranked_ids), key=lambda d: -relevance.get(d, 0))
    best = ndcg_at_k(perfect, relevance, k)
    return now, best, best - now

手算过的例子：200 个候选，三篇相关文档被排在第 4、30、180 名 → 当前 0.2021 / 最优 1.0000 / 差距 0.7979。 （完整实现见第 4 课的钻取练习。）

k 是台阶状的：只有当 k 跨过某篇相关文档的位置，它才开始计分。 k 越大指标越宽容、差距越小——所以横向比较必须固定 k，且取小值（10）， 因为它代表「模型和用户实际会用到多少条」。

三种编码架构

双塔（bi-encoder）后期交互（ColBERT）交叉编码器
交互位置只在最后比一次向量距离MaxSim 逐 token 对匹配每层注意力都做逐词交叉
文档侧可否预算可以（一个向量）可以（每 token 一个向量）不行（分数依赖整对）
在线代价一次编码 + 一次搜索仅查询过模型每个候选一次前向
存储一个向量/块涨到每 token 一个向量无索引存储
定位第一级粗召回交叉编码器太慢时的替代第二级精排

为什么交叉编码器不能做第一级：每个候选都要过一次前向，一百万篇文档就是一百万次。 这不是设计选择，是成本结构的必然结果。

三步测法（可直接当面试答案）

  1. 建基线：用调好的融合，不是默认配置。 并先确认相关文档确实进了候选列表——重排只能重排它收到的东西，缺失的文档是候选深度或检索的问题。
  2. 只用 10 个候选测，用你真正要上线的那个模型（模型选择比其他任何设置影响都大）。 读 model card 确认语言、领域、上下文窗口。在留出的标注查询上和基线比。 CPU 上这一步约 47–156 ms/查询，代价很低，所以先做它。
  3. 赢了才加候选数，且在放进服务链路前先测吞吐。

输了怎么诊断：两个不匹配

截断（窗口不够）
用模型自己的 tokenizer 对一批 query-document 对分词，比较长度的 95 分位与模型窗口。 超窗口的对会被截断，模型只读了一部分文档就打分。 例：ArguAna 查询平均 168 词，512 token 截断下留给文档的空间极小；换 1024 窗口后失败变胜利。
训练领域不匹配
对照 model card 的语言与领域。表里三个较老模型都没在代码上训过；换成含代码训练数据的模型后， CodeSearchNet 从失败翻成全表最大的确认胜利——评的是同一批候选。

选型原则：按贴合度选，不按大小选。 bge-reranker-base 与 jina-reranker-v2 体积几乎相同，但只有后者赢过调好的融合。 训练数据与上下文窗口把它们分开了，体积没有。

候选数怎么定

  • 在 10 个候选上就输的配置，加到 200 个还是输。所有在浅处落后的配置在深处依然落后—— nDCG@10 评的始终是同样的前 10 名。
  • 只在「相关文档命中率还在上升」的区间里加重排。
  • ArguAna：90% 的查询在前 25 个候选内就含那唯一的答案；加到 200 命中率升到 98%，增益反而变成损失（新候选把相关的挤出了前 10）。
  • CodeSearchNet：25 → 200 时命中率从 80.5% 升到 90.5%，仍在上升，增益一路涨到 200。
  • DBPedia-entity：到 50 个候选就拿到最终增益的 96%，走到 200 等于为最后 4% 付四倍算力。
  • 取「能拿到大部分增益的最小候选数」，并在自己的标注集上量。

分片陷阱：候选深度是按分片计的。 每个分片各自接收 limit 并搜自己的数据，所以12 个分片 + limit=200，集合级别那一层最多会收到 2400 个候选。 重排挂在集合级别，它要打分的就是 2400 个，不是 200 个——这直接决定成本与延迟预算。

数量级对比（同一套环境）：100 个候选下，CPU 上三个较小模型要 0.5–5 秒/查询； 而加第二路检索（混合检索）只增加 0.6–1.5 毫秒。 重排的在线代价比「再加一路检索」高约三个数量级——这就是为什么先调融合、后考虑重排。

  • 有些模型在 CPU 上不可用：jina-reranker-v2 的 ONNX 导出在 CPU 上同时只跑一个注意力线程 → 低于 2 文档/秒；GPU（PyTorch）下 32–310 文档/秒。 质量与吞吐数字必须来自同一套部署条件。
  • 许可证：jina-reranker-v2 为 CC-BY-NC-4.0（非商用）。选型必查许可证额外条款。

面试答题骨架（四段，缺一段就扣分）

  1. 机制：交叉编码器把查询与文档拼成一条序列联合编码，靠逐词交叉注意拿到双塔「分别编码」时丢掉的信息；代价是每个候选一次前向，所以只能做第二级。
  2. 判据：把候选集当完美排序打分，与当前得分的差距 = 排序能捞回的上限。差距大才动排序，差距小/为 0 就去改候选。
  3. 验证纪律：基线用调好的融合而非默认；只在 10 个候选上测；赢了才加候选数；必须过留出集（公开数据集五个只有两个站住；WANDS 对默认 RRF +0.039、对调好的融合 −0.008）。
  4. 成本：100 候选下 CPU 每查询 0.5–5 秒，比加一路检索贵约三个数量级；注意部署条件与许可证。
