检索与融合速查

BM25 参数 · RRF 手算 · 两派融合的取舍 · 调参顺序 · 打印友好

一句话记住两派的分野：RRF 只看「你排第几」，按分数融合还看「你赢了多少」。 RRF 更稳健、不用调参；按分数融合保留更多信息，但也把分数分布本身的不可靠一起放大。

两种检索的盲区是对称的

稠密（向量）稀疏（BM25）
擅长语义相近、同义改写、口语 query精确词项、型号、错误码、人名、条款号
盲区低频精确串（在向量空间几乎无区分度）词形与词义（molding vs mold 分不清）
推理开销需要 embedding 模型无模型推理，索引期与在线都极便宜

Qdrant 的实例（同一查询，两种检索谁把相关商品排第一）：

查询稠密排第一稀疏排第一
french molding装饰线条 相关法式面包模具 不相关
bathroom vanity knobs整体浴室柜 不相关旋钮单品 相关

检索失败是静默的——Qdrant 原话：无论哪种检索失败，「你的日志都会记下一次成功的查询」。

BM25 公式与参数

              ⎛ N ⎞   (k₁ + 1) · tf(t,d)
score(d, q) = Σ log│───│ · ─────────────────────────────
              ⎝df_t⎠   k₁·((1 - b) + b · L_d / L_avg) + tf(t,d)
项作用参数语义
log(N/df_t)IDF：稀有词更值钱精细变体 log((N-df_t+0.5)/(df_t+0.5)) 在词出现于过半文档时会变负，需加 0 下限
tf(t,d)词频，带饱和（收益递减）k₁=0 退化为二值模型；k₁ 很大 ≈ 用原始词频。默认 1.2–2
L_d/L_avg文档长度归一化b=1 完全归一化；b=0 不归一化。默认 0.75

默认值来自 Stanford IR 教材在没有做参数优化时的推荐。规范做法是在开发集上网格搜索—— 和 chunk size 同理：可调的参数都应该被测量，而不是被继承。

学习式稀疏检索：SPLADE 会补上原文没出现的相关词（召回同义词）； miniCOIL 保留词项匹配但按上下文重新加权（体育的 bat ≠ 动物的 bat）。 Qdrant 的建议：先用 BM25，再用学习式模型跟它比，比过了才换。

融合的核心难题：量纲

余弦相似度有界（大致 0–1），BM25 的量纲随查询漂移—— 取决于命中了几个查询词、这些词多稀有。 所以没有任何一组固定权重能对所有查询保持同样的平衡：一个权重在查询 A 上刚好，在查询 B 上就让 BM25 一边倒。

RRF：只用名次

RRF(d) = Σ        1 / (k + r(d))          k = 60
         r ∈ R

r(d) 是文档在第 r 路结果里的名次（原始论文用 1 起始名次）。 公式里没有分数——所以能把「余弦 0.7」和「BM25 12.4」放在一起融合，因为从不需要比较这两个值。

k=60 的出处与意图（Cormack et al., SIGIR 2009 原文）： k=60 在一次先导实验中固定，之后验证未改动。 直觉是「高度靠前的文档更重要，但靠后文档的重要性不应像指数函数那样迅速消失； 常数 k 用来缓和异常系统给出的高排名所带来的影响」。

从这个例子要记住的两件事

  1. RRF 是共识机制，奖励「都认可」、惩罚「一枝独秀」。 D5 是稀疏第 1（两路里唯一的榜首），却排第 4，输给两边中游的 D2。 因为 k=60 把名次差距压平了：第 1 名 1/61 与第 5 名 1/65 只差约 6%。
  2. 加权重是钝器，救不了「一枝独秀」。 稀疏权重加到 3 倍、10 倍，D5 都还在第 4 位；要到约 16 倍才超过 D1—— 而那时排序已被稀疏一路主导。原因：加大某一路权重会同时抬高这一路的所有文档，包括你不想抬的那个。

换派别才是有效杠杆：同一组分数交给按分数融合，D5 直接升到第 2 名，零权重调参。

两派融合对照

按名次（RRF / rankedFusion）按分数（DBSF / relativeScoreFusion）
做法1/(k + rank)，两路相加按查询把每路归一化（最高→1、最低→0），再按 alpha 加权相加
优势对量纲免疫，几乎不用调参，行为稳健保留分数差距，单路的压倒性领先能被看见
风险丢掉「赢多少」，会埋掉单路独占命中的文档依赖分数分布，会把分布本身的不可靠一起放大
调参k（钝器）、各路权重（钝器）alpha（偏向关键词或向量）

Weaviate 在 1.24 把默认从 rankedFusion 换为 relativeScoreFusion， 理由是内部基准（FIQA）召回提升约 6%。厂商内部基准、非第三方复现——引用时请带上这句。

调小 k 的效果（同一组例子）：k=1 时 D5 从 0.01639 涨到 0.50，超过两边中游的 D2（0.45）； 但同一设定下 D1 与 D5 正好打平在 0.50，谁在前面完全取决于兜底排序规则。

硬边界：融合不能创造候选

融合只做重排，作用在两路候选的并集上。 两路都没找到的文档，不可能出现在结果的任何位置——换任何融合算法都一样。

这时该动的是候选深度（prefetch 的 limit），不是融合方法。 但加深也有代价：检索量变大；且若两路在更深处依然找不到它，加深也没用。

排查顺序因此永远是：① 候选集里有没有它 → ② 排序对不对。 这个顺序就是第 5 课评测与归因的基本框架。

混合检索的代价清单（面试必答的另一半）

  • 存储与索引：每文档多存一个稀疏向量，多建一个索引，每查询多跑一路检索。
  • 延迟：Qdrant 测得中位延迟增加 0.60–1.47 ms（单容器、单请求、无并发）。 必须在自己的并发与分片条件下重测，别把这个数字直接搬进容量规划。
  • 改造代价：给已运行的纯稠密库加稀疏向量，必须新建 collection 并全量重建（向量配置在创建时固定）。
  • 易漏的坑：稀疏向量要开 IDF 修饰。 Qdrant 原话：没有它，一个常见词可能和一个零件编号得到同样的权重。

调参顺序（照这个顺序试，别乱）

  1. 先建基线：纯稠密、纯稀疏各跑一遍，用同一批标注查询、同一套候选深度。
  2. 再上融合：默认先用 RRF，看它是否同时赢过两路。若只赢一路，先查候选深度。
  3. 看分歧查询：重点看两路排序不一致的那些 query，判断胜负是否集中在某一类查询上。
  4. 换派别：出现「单路独占命中被埋掉」时，试按分数融合，而不是猛调权重。
  5. 最后才调参数：k、权重、alpha。每次只动一个。
  6. 留出集复验：在 held-out 查询上复查胜出的配置，否则你只是过拟合了调参集。

查询改写

做法机制代价 / 风险
多路查询 LLM 改写成若干不同角度的查询，各自检索后融合 检索次数 ×N，外加一次 LLM 调用
HyDE 先让 LLM 生成假想答案文档，用它去检索（答案的写法天然比问题更像文档；假细节被编码器稠密瓶颈过滤） Anthropic 报告同类思路收益有限。表述要平衡：有依据，但依赖场景，先量再上

反向考点：查询改写也会帮倒忙。 如果 query 本身是精确型号或错误码，改写可能把它「顺滑」成语义相近但丢掉关键串的句子， 本来 BM25 能一击命中的反而查不到。知道什么时候不该改写，和知道怎么写，是同一件事的两面。

融合代码的不变量断言

# ① 名次基准要明确（论文用 1 起始；0 起始不改变通常排序，但必须自知）
rank = i + 1

# ② 分数打平必须显式定序，否则同一查询两次跑出不同结果，指标会莫名抖动
return sorted(scores.items(), key=lambda kv: (-kv[1], str(kv[0])))

# ③ 融合结果必须是两路并集的子集——越界说明你创造了候选
assert set(d for d, _ in fused) <= set(dense) | set(sparse)

故障 → 药方

冷门型号 / 错误码搜不到
加稀疏这一路（BM25），并确认开了 IDF 修饰。这是混合检索最典型的收益场景。
上了混合检索，某类查询反而变差
大概率是 RRF 埋掉了「单路独占命中」。试按分数融合，或检查该类查询是否本就不该走混合。
两路都召回不到那篇文档
融合救不了。加大候选深度；仍不行则回去查切分与解析（第 2 课）。
同一查询两次结果不一致
分数打平后依赖了字典序。给排序加稳定的兜底键。这类问题会让评测指标抖动，最难查。
调权重怎么调都没起色
权重是钝器，会同时抬高整路文档。先确认你要修的是「排序」还是「候选缺失」—— 候选缺失调权重永远无效。
